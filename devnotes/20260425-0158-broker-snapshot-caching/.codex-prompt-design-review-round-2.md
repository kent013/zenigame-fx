### 差分 1: 施策 0 新設（Position frozen 化）

`src/broker/orders.py:20` の Position dataclass に `frozen=True` 追加。
事前調査結果:
- `Position` 生成箇所: `src/broker/mock.py:302` + tests/ 5 箇所
- **Position field 書き込み: 0 箇所**（全 consumer は read-only: `pos.side` / `pos.entry_time` / `pos.units` / `pos.entry_price` / `pos.entry_margin` / `pos.id`）
- 既存テスト: constructor 呼び出しのみ → frozen 化しても全合格見込み

### 差分 2: 施策 1 cache 単一 slot 化

**Before**:
```python
self._cached_snapshot: PortfolioSnapshot | None = None
self._cached_bar: PriceBar | None = None
```

**After**:
```python
self._snapshot_cache: tuple[PriceBar, PortfolioSnapshot] | None = None
```

**Before (cache hit check)**:
```python
if self._cached_snapshot is not None and bar is self._cached_bar:
    return self._cached_snapshot
```

**After**:
```python
cache = self._snapshot_cache
if cache is not None and cache[0] is bar:
    return cache[1]
```

**Before (write / invalidate)**:
```python
self._cached_snapshot = snapshot
self._cached_bar = bar
# ...
def _invalidate_snapshot_cache(self) -> None:
    self._cached_snapshot = None
    self._cached_bar = None
```

**After**:
```python
self._snapshot_cache = (bar, snapshot)
# ...
def _invalidate_snapshot_cache(self) -> None:
    self._snapshot_cache = None
```

これで 1 代入で atomic に更新・invalidate。例外時の中間状態リスクが消える。

### 差分 4: 施策 2 に long/short parametrize 追加

```python
@pytest.mark.parametrize("side", ["open_long", "open_short"])
def test_snapshot_cache_hit_returns_identical_object(side: str) -> None:
    broker, bar = _broker_with_position(side=side)
    s1 = broker._snapshot_at(bar)
    s2 = broker._snapshot_at(bar)
    assert s1 is s2


@pytest.mark.parametrize("side", ["open_long", "open_short"])
def test_snapshot_cache_values_symmetric_for_long_short(side: str) -> None:
    broker, bar = _broker_with_position(side=side)
    s1 = broker._snapshot_at(bar)
    broker._invalidate_snapshot_cache()
    s2 = broker._snapshot_at(bar)
    assert s1.cash == s2.cash
    assert s1.equity == s2.equity
    assert s1.margin_used == s2.margin_used
    assert s1.margin_level_pct == s2.margin_level_pct
```

### Suggestion 非採用の根拠

`_mutate_cash` / `_add_position` / `_remove_position` wrapper を作って invalidate を集約する案は:
- `_close_one` のような複合操作で wrapper を 2 回呼ぶ / 順序依存でバグが入るリスク
- 単純な代入に比べて可読性が落ちる（`self._cash += amount` → `self._mutate_cash(amount)` の抽象化利益は invalidate 強制のみ）
- **代替**: conceptual-design の「実装開始条件チェックリスト」で `grep -n "self\._cash\|self\._positions\[" src/broker/mock.py` の全 hit を invalidate 呼び出しと 1:1 対応させることを mandated。この grep は 4 箇所固定（mock.py は新規拡張予定なし）で、漏れ検知は CI 等で機械化可能

採用しない場合のリスク: 将来の mock.py 拡張で invalidate 呼び忘れ。**mitigation**: (a) mock.py は stable API で拡張予定低い、(b) checklist grep を runbook 化、(c) 問題発生時は施策 2 の `test_snapshot_values_bit_identical_cache_vs_no_cache` で即座に FAIL する。
