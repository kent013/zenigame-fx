# 使命 / 制約
live_criteria 全達成個体を見つける。イントラデイ前提 / ロング・ショート両方向 / スワップ・スプレッド控除後純益。default 挙動不変が絶対条件。

# 背景
Stage C の「spread×1.5 stress」は max_spread_bps（spread フィルタ閾値）を緩めるだけで per-trade コストを増やさず stress_pnl_degradation 全個体0（cost robustness 未検証）。P2 はこれを「実効スプレッド（約定コスト）を 1.5 倍に広げる」方式に直す整合性修正。

# 重大: fill 経路は 2 つ（両方配線必須）
- numba kernel `_sim_kernel.simulate()`（本番 engine=kernel、PRICE_SCALE=1e5 整数）。fill: long entry=ask_o[i], short entry=bid_o[i], long exit=bid_o[i], short exit=ask_o[i]。
- MockBroker（Decimal、fail-safe）: long entry=bar.ask.open, short entry=bar.bid.open, long exit=bar.bid.{open,close}, short exit=bar.ask.{open,close}。
kernel 漏れると本番で degradation=0 のまま（falsification 条件）。

# レビュー観点（重点）
1. spread_cost_multiplier を整数比 (num/den, 例 3/2) で kernel に渡し、(m_num-m_den)=0 で加算0=ビット同一を保証する設計の妥当性。整数 floor 除算の丸めが long/short で非対称な不利を生まないか。
2. adverse 方向の符号: long entry は高く(ask+)、short entry は安く(bid-)、long exit は安く(bid-)、short exit は高く(ask+)。half_spread=(ask-bid)/2。符号が全て「個体に不利」方向で正しいか。
3. mark-to-market（kernel line168-170/232-234 は bid_c/ask_c で含み損益、margin call 判定にも使用）に multiplier を適用すべきか否か（realized fill のみ広げる設計で十分か、margin call 整合性は崩れないか）。
4. default 1.0 の数値同一性（kernel + MockBroker 両経路、既存テスト regression）。
5. _exit_price の staticmethod→instance 化の波及。
6. bid>ask 異常時の half_spread clamp。
7. BacktestConfig 新フィールドの config 伝搬（4段: config→GaConfig→...）と frozen dataclass 整合。
8. テスト網羅性。

## P2 詳細

### target_metric / failure_mode / causal_path / falsification / success_criterion
- target_metric: stress_pnl_degradation 分布（非ゼロ化）、stress 下の Stage C 通過個体数。
- failure_mode: 現行 Stage C stress は max_spread_bps（spread フィルタ閾値）を 1.5 倍に緩めるだけで per-trade コストを増やさず、stress_pnl_degradation 全個体 0（cost robustness 未検証）。
- causal_path: broker fill 時に実効スプレッドを multiplier 倍に広げる（adverse 方向へ (m-1)×half_spread 上乗せ）→ 往復取引コストが m 倍 → cost 増が PnL に反映 → cost fragile 個体は stress で PnL 悪化 → 真に cost robust な個体のみ stress gate 通過。
- falsification: P2 導入後も stress_pnl_degradation が 0 のまま → 配線/実装不整合。
- success_criterion: R85 で stress_pnl_degradation が多数個体で >0、stress 下 Stage C 通過が cost robust 個体に限定。

### 現状の事実（調査済）
- fill は bid/ask 約定: long entry=`bar.ask.open`, short entry=`bar.bid.open`（mock.py:232,241）、long exit=`bar.bid.{open,close}`, short exit=`bar.ask.{open,close}`（mock.py `_exit_price`）。spread は fill で自然発生。
- `max_spread_bps` は `set_spread_filter`（spread>閾値 の trade を reject するフィルタ、mock.py:165-208）であり cost ではない。
- `_compute_trade_spread_cost`（mock.py:436-460）は往復 spread cost（2×exit_spread）を**記録のみ**（PnL 未反映、line 439 明記）。
- Stage C stress（stage_gate.py:1950-1996）は `replace(backtest_config, max_spread_bps=new_max)` で **フィルタ閾値のみ** 1.5 倍 → cost 不変 → degradation=0。

#### (1) `src/backtest/engine.py` — BacktestConfig に spread_cost_multiplier 追加

#### (2) `src/broker/mock.py` — fill 価格に multiplier を適用
- `__init__` に `self._spread_cost_multiplier: Decimal = Decimal("1.0")` 追加。
- `set_spread_cost_multiplier(self, m: Decimal)` 追加（検証: m>=1）。
- **entry fill**（fill_pending 内、mock.py:232/241）:
  - long entry: `eff = bar.ask.open + (m-1) * half_spread_open` where `half_spread_open=(bar.ask.open-bar.bid.open)/2`
  - short entry: `eff = bar.bid.open - (m-1) * half_spread_open`
- **exit fill**（`_exit_price`）: side/exit_kind に応じ adverse 方向へ (m-1)×half_spread:
  - long exit: `bid.{open|close} - (m-1)*half_spread_{open|close}`
  - short exit: `ask.{open|close} + (m-1)*half_spread_{open|close}`
  - half_spread は対応する bar 時点の `(ask-bid)/2`。
- `_exit_price` は現在 staticmethod。multiplier を使うため instance method 化（または multiplier を引数で渡す）。呼び出し元 mock.py:404 を更新。
- m=1.0 のとき全ての (m-1)=0 → 加算 0 → 現行と完全同一（数値同一性をテストで保証）。
- 符号: long は「高く買い・安く売り」、short は「安く売り建て・高く買い戻し」が adverse。half_spread>=0（ask>=bid）前提だが bid>ask 異常時は clamp（half_spread を max(0,...)）。

#### (3) `src/alpha_factory/stage_gate.py` — stress 経路で multiplier を設定

### ★★ 重大: fill 経路は 2 つ（kernel + MockBroker）— 両方の改修が必須 ★★
調査確定（src/backtest/engine.py:140-159, src/backtest/_sim_kernel.py）:
- **① numba kernel 経路** `_sim_kernel.simulate()`: `_can_use_kernel` 成立時に使われる高速経路（T108、最近マージ）。**R83/R84 は engine=kernel で実行されており、本番で実際に使われるのはこちら**。fill は `out_entry_px`/`out_exit_px` に bid/ask 配列（PRICE_SCALE 整数化）で出力。
- **② Decimal/MockBroker 経路** `_run_backtest_decimal()`: kernel preflight 不成立/overflow 時の fail-safe。
- **P2 は両経路に spread_cost_multiplier を配線必須**。kernel 経路だけ漏らすと、本番（engine=kernel）では stress が依然 toothless（degradation=0）= falsification 条件に直撃。
- kernel 改修の難所: (a) `simulate()` の njit シグネチャに multiplier（または広げ済み価格配列）を追加、(b) 整数 PRICE_SCALE 空間で (m-1)×half_spread を加算（half_spread = (ask-bid)/2 を整数スケールで）、(c) m=1.0 で既存と**ビット同一**を保証（整数演算なので (m-1)=0 で加算 0 が厳密）、(d) entry/exit の long/short 符号。
- 実装順序推奨: まず MockBroker（②）で設計検証 → kernel（①）に同ロジック移植 → 両経路の数値一致テスト（同一 genome で kernel と decimal が一致、かつ m=1.0 で現行一致）。
