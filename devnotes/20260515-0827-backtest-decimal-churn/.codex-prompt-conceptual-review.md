## 概念設計

# 概念設計: backtest hot path の Decimal churn 削減 (T105)

## 背景・課題

### 前提（確定済み・出典付き）

- GA 並列 worker の per-worker RSS が実測 5.5〜8.7GB に肥大していた。`devnotes/20260514-2045-ga-worker-memory/` でライブ RUN を vmmap + 実測調査し、**root cause = pymalloc アリーナの断片化**を確定済み（worker RESIDENT 5.4GB のうちシステム malloc は ~490MB のみ、残りは `VM_ALLOCATE` 7,241 領域 × 1024K = pymalloc アリーナ。CPython 3.11 のアリーナサイズ 1MB）。
- 緩和策 `maxtasksperchild`（worker 定期リサイクル）は実装済み（commit `a1ed996`、Codex impl-review APPROVED）。これは断片化が溜まり切る前に worker を退役させて peak を頭打ちする**対症療法**であり、**churn そのものは減っていない**。
- 本 T105 は churn の発生源を構造的に断つ**根本対応**。

### Decimal churn 連鎖（コード調査で確認した Fact）

| 箇所 | churn の内容 |
|---|---|
| `src/backtest/engine.py:180` | `run_backtest` が bar ごとに `equity_curve.append((bar.bar_time, broker.snapshot().equity))`。型は `list[tuple[datetime, Decimal]]`。Stage B IS monitor は約 20 万 bars、fold backtest は約 33 本 × 約 2 万 bars。1 genome の Stage B 評価で `equity_curve` だけで約 90 万要素（tuple + datetime + Decimal） |
| `src/broker/mock.py`（523 行） | `MockBroker` が cash / equity / margin / pnl の全演算を `Decimal` で実行。`snapshot()` が返す `PortfolioSnapshot` の 4 フィールドが全て Decimal。`mark_to_market` / `apply_bar_holding_cost` / `force_close_if_margin_call` 等が bar ごとに Decimal 中間オブジェクトを生成 |
| `src/broker/orders.py` | `Trade`（frozen dataclass）が `entry_price` / `exit_price` / `pnl` / `equity_at_entry` / `spread_cost` / `holding_cost` の 6 個の Decimal を保持。`Position` も Decimal 多用 |
| `src/domain/price.py` | `PriceBar` / `Ohlc` が Decimal × 8（bid/ask OHLC） |
| `src/backtest/metrics.py` | `compute_metrics` が `equity_curve` / `trades` を消費。**統計系（`_bar_returns` / `_sharpe` / `_sortino` / `_trade_returns`）は既に `float` 化済み**だが、`max_drawdown` / `max_drawdown_pct` / `final_equity` / `_calmar` は Decimal 演算 |

### Interpretation（解釈）

`Decimal` / `datetime` / 小 `tuple` は ≤512 byte の小オブジェクトで pymalloc アリーナに入る。GC 自体は効くが、pymalloc は **アリーナが 100% 空になるまで OS に返さない**ため、大量 churn が断片化として残存する（前 devnotes の再現テストで実証済み）。

churn の量的支配項は **`equity_curve` の per-bar 蓄積**（1 genome Stage B で約 90 万要素）と推定する。`Trade` は `live_criteria.trade_count_max` で件数が上限（数千）に抑えられるため相対的に小さい。`MockBroker` 内部の per-bar Decimal 中間オブジェクトの churn 量は未計測（要 Phase 0 計測 or 推定）。

## 改善アイデア

backtest engine 内の Decimal 演算を **「精度 load-bearing」と「精度非要求」に切り分け**、後者を numpy 配列化して小オブジェクト churn を構造的に削減する。

### 精度 load-bearing（Decimal 維持・変更しない）

金額の正しさに直結し、float 化すると約定・損益が静かに狂う領域:

- 約定価格の計算（`MockBroker.fill_pending` の fill price 決定）
- margin / leverage 判定（`force_close_if_margin_call`、`submit` の validate）
- 手数料・スプレッドコスト・holding cost の計算
- `Trade.pnl` / `entry_price` / `exit_price` 等の確定値

→ これらは `Decimal` のまま。本 T105 では触らない。

### 精度非要求（numpy 化の対象）

時系列として蓄積され、消費側が統計・集計に使うだけの領域:

- **`equity_curve`（主対象）**: `compute_metrics` での用途は ① `max_drawdown` / `max_drawdown_pct`（peak からの下落幅）② `final_equity` ③ `_bar_returns` → 既に `float` 化済み ④ `_calmar`（始点・終点 equity）のみ。**GA fitness の本命指標 `trade_sharpe_raw` は `equity_curve` ではなく `Trade` から計算される**ため、`equity_curve` 表現変更は GA 選抜の基底指標に影響しない。

### 改善方針: `equity_curve` を lossless な numpy 配列へ

`equity_curve: list[tuple[datetime, Decimal]]` を、`run_backtest` が **bar 数を起動時に知っている**（`bars_list = list(bars)`）ことを利用して **事前確保した numpy 配列 2 本**に置き換える:

- `bar_time_epoch: np.ndarray[int64]` — bar_time を epoch 整数（ns or s）に
- `equity_scaled: np.ndarray[int64]` — equity を**固定スケール整数**（equity × 10^k、k は home currency の Decimal 精度を loss なく収める値）に

**lossless 性が鍵**: `MockBroker` の equity は有限精度の Decimal。固定スケール整数化が lossless なら、`max_drawdown` / `max_drawdown_pct` / `final_equity` を**整数比較・整数演算で計算でき、現行 Decimal 計算と bit-exact に一致**する（ステージゲート・live_criteria への影響ゼロ）。`int64` overflow は equity の現実的上限（初期資金 100 万 + 利益）× スケールが `2^63` に収まることを設計で確認する。

per-bar の `broker.snapshot().equity`（Decimal）→ scaled-int64 への変換は 1 bar 1 回の transient Decimal で、結果は事前確保済み配列へ index 代入（**新規 Python オブジェクトを蓄積しない**）。蓄積される実体が「90 万個の小オブジェクト」→「numpy 配列 2 本（連続バッファ）」になる。

### `MockBroker` 内部 churn・`Trade` の扱い

- `MockBroker` 内部の per-bar Decimal 中間オブジェクト churn は、Phase 0 で `equity_curve` 改修後の残存 RSS を計測してから要否判断する（精度 load-bearing 領域なので安易に float 化しない）。
- `Trade` は件数上限があり相対的に小さいため本 T105 のスコープ外（必要なら別タスク）。

## 期待効果

- **直接効果**: 1 backtest あたり最大の churn 源（`equity_curve` 約 90 万小オブジェクト/genome）を numpy 連続バッファ化し、pymalloc アリーナ断片化の発生源を構造的に削減。`maxtasksperchild`（対症療法）への依存度を下げ、per-worker RSS のベースラインを下げる。
- **使命への寄与（間接）**: `devnotes/20260514-2045-ga-worker-memory/` と同じく探索基盤の制約解除（OOM/swap リスク除去、複数ペア swim-lane 拡張の前提、population/generations を増やせる余地）。live_criteria を直接動かすものではない。
- **lossless 設計のため、ステージゲート・live_criteria 判定は不変**（`max_drawdown_pct` / `final_equity` / `calmar` を bit-exact 維持）。

| 対象 | 変更概要 |

| `src/backtest/engine.py` | `equity_curve` を事前確保 numpy 配列 2 本へ。`BacktestResult.equity_curve` の型変更 |

## 制約・前提

- **決定論契約 L1/L2 の維持**: equity_curve 表現変更は worker 数非依存。lossless 設計により gate 判定が変わらないことを「同一 seed・同一 dataset で改修前後の archive を比較し `max_drawdown_pct` / stage pass-fail / live_criteria 判定が完全一致」で verify する。
- **金額計算の正しさを変えない**: 精度 load-bearing 領域（約定・margin・手数料）は Decimal のまま。本 T105 は触らない。
- **スワップ・スプレッド反映の維持**: `spread_cost` / `holding_cost` の計算経路は不変。
- **`BacktestResult.equity_curve` の型変更は公開構造の変更**: 8 つの consumer 全てを追従させる（4 段接続漏れ禁止）。`BacktestResult` を参照する他経路（paper_trading 等）も grep で洗う。
- スケール係数は dataset/instrument の Decimal 精度から lossless に決定し、`int64` overflow を設計時に検証する。

## スコープ外

- `MockBroker` 内部の per-bar Decimal 演算の float 化（精度 load-bearing。Phase 0 計測で必要性が出たら別タスク）。
- `Trade` / `Position` の Decimal 表現変更（件数上限ありで churn 寄与が小さい。別タスク）。
- `PriceBar` / `Ohlc` の Decimal 表現変更（src/ 36 ファイル参照の大規模波及。`devnotes/20260514-2045-ga-worker-memory/` でも明示スコープ外）。
- `maxtasksperchild` 自体の調整（実装済み・別管理）。
- `compute_metrics` 出力 `BacktestMetrics` の型変更（Decimal のまま。consumer 影響を最小化）。
