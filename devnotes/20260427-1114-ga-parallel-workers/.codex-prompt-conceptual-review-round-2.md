## 1. 目的 / Why

zenigame-fx の GA RUN は現状 1 process 1 core でシーケンシャル評価しているため、core 数を増やしても wall-time が短縮されない。

zenigame 側は `ga.max_workers` を YAML/CLI で指定し `multiprocessing.Pool` で個体評価を並列化する設計が既に運用されている。

**仮説**: zenigame-fx でも同等の `max_workers` を導入すれば RUN wall-time が短縮され、改善サイクルの回転速度を上げられる。具体倍率は性能観測フェーズで実測。

**位置付け**: 本機能は **副次目標 (運用効率改善)** であり、live_criteria 達成 (= North Star) を直接前進させるものではない。
ただし以下の経路で間接的に寄与:
- 1 RUN の wall-time 短縮 → 改善サイクルの試行回数増 → live_criteria 探索空間の被覆率向上
- 並列化の前提として「評価関数の純粋性」を強制 → 既存の隠れた副作用を可視化

**成功条件 (再定義)**:
1. `--max-workers N` (alias `--workers N`) または `ga.max_workers: N` で指定した process 数で評価が並列実行される
2. **L1 selection determinism (必須)**: `cache[name].fitness_pen` / `_select_best` の `best_name` / `live_criteria_passed: bool` が完全一致
3. **L2 row-order determinism (必須)**: archive Parquet 数値 column が `(lane_id, generation, genome_name)` ソート下で一致
4. **L3 artifact bit equivalence (非保証)**: `summary.json` / `archive.parquet` の生 byte 列の一致は保証しない
5. `max_workers=1` 時の動作経路は現行と同一 (regression: 既存テストがそのまま pass)

## 3. 現状把握 (Fact)
（v1 から変更なし — 評価フローの構造、worker pickle 可否分類、決定性の所在）

### 3.3 決定性の所在 (補強)
- Stage A/B/C 評価は genome 単位で **数値的に純粋** (副作用は archive/diagnostics 書き出しのみ)
- `StageResult.metrics["wall_time_seconds"]` 等の **非数値 metadata は wall time 依存** → L3 (bit 一致) では除外

## 4. 設計方針 / How

### 4.0 決定論性の三段階定義
| Level | 内容 | 本機能での扱い |
|---|---|---|
| L1 selection determinism | 数値評価 (`fitness_pen` / `live_criteria_passed` / `best_name`) が seed 固定下で worker 数に依存しない | **必須保証** |
| L2 row-order determinism | archive Parquet を `(lane_id, generation, genome_name)` でソート時、評価値 column が完全一致 | **必須保証** |
| L3 artifact bit equivalence | `summary.json` / `archive.parquet` の生 byte 列が一致 | **保証しない** |

### 4.1 副作用と評価の分離
worker は **数値評価のみ** を行う純粋関数。**副作用は main process** が一手に持つ。

```python
@dataclass(frozen=True)
class GenomeStageResult:
    genome_name: str
    stage_a: StageResult
    stage_b: StageResult | None
    stage_c: StageResult | None
    cross_pair: CrossPairResult | None
    error: GenomeEvalError | None

@dataclass(frozen=True)
class GenomeEvalError:
    """生 traceback は logger 専用。artifact 非含。"""
    stage: Literal["A", "B", "C"]
    error_code: str
    short_message: str  # 1 行 (PII / runtime 依存情報を除く)
```

main は結果 list を **population 順** に並べ直して archive.collect_* / diagnostics.record_* / graduation 判定。

### 4.2 二層分離

```
evaluation 層: parallel_eval.evaluate_genome(genome, ctx, ...) -> GenomeStageResult
  - 純粋関数、直列/並列共通、副作用なし

task transport 層: ParallelEvaluator
  - multiprocessing.Pool 起動・寿命管理
  - lane context broadcast
  - 将来 SharedBarStore / HistStats 導入時の差し替え点
```

`LaneManager` は ParallelEvaluator (or SequentialEvaluator with same API) を 1 個保持。

### 4.3 並列モードの context 配布 — multiprocessing.Pool 採用

```
ParallelEvaluator.__init__:
  if max_workers > 1:
    pool = multiprocessing.get_context("spawn").Pool(
        processes=max_workers,
        initializer=_init_worker,
        initargs=(stage_gate_cfg, cross_pair_cfg, prim_evaluator),
    )

ParallelEvaluator.set_lane_context(lane_id, bars_a, bars_b, bars_holdout, meta, bt_cfg, cp_inputs):
  # 前世代と同 bars id なら no-op (memo)
  pool.map(_set_lane_ctx_worker, [args] * max_workers)

ParallelEvaluator.evaluate_population(lane_id, generation, population):
  args = [(lane_id, generation, g) for g in population]
  results = pool.map(_eval_genome_worker, args)
  return results  # population 順
```

ProcessPoolExecutor は不採用。

### 4.4 cross-pair shadow
Phase 2 では `cp_inputs=None` 経路。adapter の純粋性は詳細設計で grep verify、未達なら INCONCLUSIVE。

### 4.5 設定の追加

```yaml
ga:
  max_workers: 1   # default. autopilot/improve-cycle は変更しない
```

CLI: `--max-workers N` (canonical), `--workers N` (alias)

### 4.6 fallback / failure handling
- worker 内例外 → `GenomeEvalError` に正規化、artifact には正規化済み構造のみ
- main で fail-closed StageResult (`reason_codes=("worker_error",)`) に変換
- pool 起動失敗 → RuntimeError fail-fast
- pool 寿命 → `LaneManager.close()` で `pool.terminate()` + `pool.join()`

### 4.7 L3 非保証 — 除外 field 一覧
- `summary.json.generated_at` / `run_id`
- `summary.json.per_generation[*].wall_time_seconds`
- `summary.json.best.metrics.wall_time_seconds`
- `archive.parquet` writer metadata
- `StageResult.metrics["wall_time_seconds"]`
- `diagnostics.parquet` の logger 由来 timestamp 系

L1/L2 保証対象: `fitness`, `fitness_pen`, `sharpe`, `total_pnl`, `max_drawdown`, `trade_count`, `live_criteria_passed`, `stage_*_passed`, `cross_pair_passed`

## 6. リスク
（v1 表 + 「メモリ試算楽観的」「cross-pair adapter 副作用」「Parquet writer 非決定性」を追加）

### 6.1 メモリ試算 (保守的上限)

EUR_JPY 6ヶ月 M1 ≈ 260,000 bars 前提、1 worker:

| 項目 | サイズ概算 |
|---|---|
| raw bars (Stage B 18m) | ~50-100 MB |
| raw bars (Stage A 60d) | ~17 MB |
| raw bars (Stage C holdout) | ~17 MB |
| `_bars_cache` derived ndarray | ~25 MB |
| primitive_evaluator + aux dict | ~10 MB |
| Python interpreter / numpy / pandas | ~150 MB |
| その他 (cp_inputs / cfg / 局所バッファ) | ~50 MB |
| **合計 / worker** | **~320-370 MB (保守的上限)** |

24GB / 1 worker 3GB 制約に対して 12% 程度。6 worker × 370MB ≈ 2.2GB + main = 2.6GB。
multi-pair (6 通貨ペア) になると ~6 倍に膨らむため SharedBarStore 再検討。
