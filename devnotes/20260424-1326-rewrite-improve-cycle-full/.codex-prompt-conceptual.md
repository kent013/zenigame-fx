# 概念設計: zenigame-fx-improve-cycle full version (Phase 2 architecture)

## 背景

現行 `.claude/skills/zenigame-fx-improve-cycle/SKILL.md`（214 行）は cycle 0 / T001 以前に作成された **縮小版** で、`scripts/alpha_factory/run_ga.py` 等を直接叩く 1 スキル完結型。Phase 2 architecture（Stage A/B/C / GenomeArchive / cross-pair shadow / swim-lane / 32 primitive）導入後の 改善サイクルを表現できておらず、T020-T023 で port した sub-skill 群（analyze-run / plan-and-design / run-alpha-factory / run-report）を一切活用していない。

zenigame 版 `.claude/skills/_archived/zenigame-improve-cycle/skill.md`（476 行）は Phase 0-5 + 5.5 の full orchestrator として設計されており、これを **base** に zenigame-fx 用に port + Phase 2 統合する。

## 使命と制約（FX 版固有）

### 使命

> `config/alpha_factory/default.yaml` の `live_criteria` を全て満たす **FX イントラデイ戦略個体** を 1 つ見つけ出す。達成後は閾値を引き上げて次の水準を設定する。

zenigame 版（日本株、ロングオンリー）と異なり、FX は **ロング・ショート両方向許容**。ただしショート禁止の継承削除は live_criteria 緩和とは別物として扱う（C9 falsification）。

### 絶対制約

- **イントラデイ前提** — オーバーナイト保有を前提にする設計を避ける
- **スワップ・スプレッドを fitness に反映** — 見かけの PnL ではなく純利益
- **live_criteria 緩和注意** — 引き上げは可、緩和は禁止（達成後に閾値を上げて次サイクル）

### 禁止事項（codex-review 継承）

1. ショート（空売り）売買の導入 → **削除**（FX では許容、ただしコスト控除後評価）
2. A・B・C 評価期間を強い根拠なしに延長する
3. 見た目の数値をよくしようとする改善
4. GA をハックしてステージを進めようとする
5. 閾値をいたずらに緩和してステージを飛ばす
6. やたらに複雑な案を提案する
7. 取引回数を削減して見かけの成績を上げようとする

## 引数

| 引数 | 必須 | 説明 |
|------|------|------|
| `run_id` ($1) | No | 分析対象の run_id（例: run_20260424_093015）。省略時は最新 Run を自動検出 |
| `run_args` | No | RUN 実行時の引数（省略時は前 Run と同一設定。skill が判断する場合 default） |
| `--repeat` | No | 繰り返しモード。1 サイクル完了後に自動で次サイクル開始 |
| `--max-cycles N` | No | 最大サイクル数（`--repeat` なし → 1 / あり省略 → 無制限） |
| `--skip-todo` | No | TODO 実装スキップ。Phase 2 の TODO 選定・Phase 3 の implement 全体を skip。GA 分析由来改善のみ |
| `--skip-consensus` | No | Codex 合議スキップ。**ユーザー明示指定時のみ**。自動付与禁止 |
| `--observe-only` | No | 観測のみ。Phase 2/3 を skip し analyze → run → report に直行。Emergency Fix 検出時のみ修正実施。`--skip-todo` / `--skip-consensus` を暗黙的に含む |

## 設計上の判断

### 1. zenigame-fx-analyze-run 経由統一

縮小版は `scripts/alpha_factory/analyze_run.py` を直接叩いていたが、**T020 で port した skill 経由に切替**。skill 内で Codex 独立分析（gpt-5.3-codex medium）も自動実行され、`analysis-codex.md` も生成される。

### 2. zenigame-fx-run-alpha-factory 経由統一

縮小版は `scripts/alpha_factory/run_ga.py` を直接叩き、独自に BG 監視を行っていたが、**T023 で port した skill 経由に切替**。BG 起動・監視・4 点整合・state 管理は run-alpha-factory skill 側に任せる（責務分離）。

### 3. zenigame-fx-plan-and-design 必須引数

T022 の plan-and-design は `tmp_dir` を**必須引数**として受け取る。improve-cycle は Step 0 で生成した `tmp_dir` をそのまま渡す。`run_id` は第 2 引数で渡す（plan-and-design 内で state file から自動取得もされるが、明示渡しが堅牢）。

### 4. Phase 2.5 / Phase 5.5 / post-run-review コメント化方針

「削除」ではなく **コメント化**（`<!-- TODO(...-port): ... 整備後に接続 -->` 形式）。SKILL.md 内に明記することで:
- 整備優先度の見える化
- 復活時の挿入位置が明確
- レビュー時に「忘れ去り」を防止

整備時は当該 TODO で「コメント解除」だけで接続できる。

### 5. Emergency Fix モード継承

zenigame 版は `analyze-run` が `state.emergency_fix.detected = true` を立てた場合、Phase 2 で改善策合議の代わりにバグ根本原因特定、Phase 3 でバグ修正のみを実施する。zenigame-fx でも analyze-run skill が同 key を立てる前提で同経路を維持。

> 補足: `zenigame-fx-analyze-run` SKILL.md には emergency_fix 書き込み仕様が明記されていないため、本サイクルでは「key が存在すれば尊重、存在しなければ通常モード」のフェイルソフトで実装。analyze-run 側に emergency_fix 機構を組み込むのは別 TODO。

### 6. 繰り返しモードの自律性

`--repeat` 指定時は **ユーザーへの問い合わせを一切行わない**。以下を自律判断:
- Codex API 失敗時 → Codex なしで自動続行
- テスト失敗が解消しない施策 → revert / skip
- 各フェーズ報告は log として出力するが、ユーザー応答を待たずに次フェーズへ進む

`--max-cycles N` 指定時は N サイクル達成で終了。未指定なら無制限（autopilot から呼ばれることを想定）。

### 7. context 圧縮対策

`current_cycle_state.json` を各 Phase 開始・完了時に Write で更新。圧縮復帰時は state file を Read → `completed_phases` から未完了 Phase を特定 → `tmp_dir` 内成果物を Read して中断点から再開。

### 8. 後方互換不要

既存の縮小版 SKILL.md は **完全破棄して書き換え**。autopilot 等の呼び出し元は本 skill を直接叩く設計（`/zenigame-fx-improve-cycle` がエントリポイント）であり、縮小版の挙動に依存している部分はない（縮小版自体が cycle 0 で 1 度も使われていない）。

## ループ収束ルール

zenigame-fx-codex-review / plan-and-design / implement の各 skill が個別に Codex 合議ループを持つ。improve-cycle 自身は **オーケストレータ** であり、Codex 呼び出しは行わない。各 sub-skill 内のループは:

- 通常モード: 最大 3 ラウンド
- `--repeat`: 最大 5 ラウンド

未解決事項は当該 skill の出力に「保留事項」として記録され、improve-cycle はそれを次サイクルに引き継ぐ責務はない（人間 / autopilot 側で TODO 化する）。

## エラーハンドリング

### Workflow 失敗

各 sub-skill が失敗した場合:
- **通常モード**: ユーザーに報告し、対応を確認
- **繰り返しモード**: エラーをログに記録し、可能であれば次のフェーズに進む。致命的エラー（state file 破損 / 必須成果物欠落等）の場合のみ停止

### 各 sub-skill のエラーハンドリング

| sub-skill | 失敗時挙動 | improve-cycle 側の処理 |
|-----------|----------|---------------------|
| analyze-run | `analysis-claude.md` 出力されない | Phase 1 失敗報告、Phase 2 移行不可 |
| plan-and-design | `improvement-plan.md` / `detailed-design.md` 出力されない | Phase 2 失敗報告、Phase 3 移行不可 |
| implement | TODO 実装失敗 | 該当 TODO のみ skip、他 TODO は続行 |
| run-alpha-factory | `status=failed` | Phase 4 失敗報告、Phase 5 は手動 run-id で継続可能 |
| run-report | レポート生成失敗 | warning ログのみ、サイクル続行 |

### コンテキスト圧縮からの復帰

1. `.cache/alpha_factory/current_cycle_state.json` を `Read`
2. `completed_phases` を確認し、未完了の最初のフェーズから再開
3. `tmp_dir` 内の中間成果物を `Read` して状態を把握
