## 質問事項

[Critical] [Warning] [Suggestion] で診断:

1. **dataset_epoch_id 生成式の deterministic 性**: `f"epoch_{end.strftime('%Y%m%d')}_p{epoch_index}"` で同一 window → 同一 ID、 window 違えば ID 変化。 衝突回避の `epoch_index` suffix は適切か。 例えば dataset.end が同日でも anchor_date 変更で ID 衝突する経路はあるか
2. **state file の atomic write**: synthesis 全体で複数 worker が同時 register_run しないか? 並行 Run 制御は本 TODO で必要か (= file lock)、 それとも別 TODO に分離か
3. **anchor_date の管理**: config から渡す default `cfg.dataset.end` は妥当か。 anchor 変更時の影響 (warning のみで進む) で十分か
4. **state file 破損時の挙動**: パースエラー → warning + 新規初期化 は T058 LOG_ONLY 思想と整合するが、 過去 archive (epoch_id に紐づく) との不整合リスクは?
5. **`can_start_new_run` の RUN abort**: max_runs/epoch=6 超過時は RuntimeError raise で abort。 これは「synthesis 確定値で 6 Run/epoch」 の cap に対する強制力として正しいか、 それとも warning + 強行で良いか
6. **stride=4w 固定**: synthesis 確定値だが、 過去設計 (旧議論) との整合性で問題ないか
7. **見落とし論点**: 同時並行 Run / CLI override / anchor_date 変更検出 / epoch 巻き戻し以外に、 設計上の盲点があるか

これらに加えて、 設計の本質的誤り / 禁止事項違反 / 反証可能仮定があれば identify。
