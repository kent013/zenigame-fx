## 検証してほしい観点

### A. Blocker 修正の妥当性

1. `reserve_run_slot` の新しい順序 (compatibility verify → advance → dataset_match verify) が、 advance 経路 / 非 advance 経路の両方で意図通り動くか。
2. cfg_e1 (新 window 一致) を渡した場合に advance + 新 window verify が pass するか。
3. cfg_e0 (旧 window 一致) を advance 直後に渡した場合に `EpochDatasetMismatch` raise されるか (= 新規テストの想定挙動)。
4. `EpochCapExceeded` の raise 条件は変わっていないか (= `slots_consumed >= MAX_RUNS_PER_EPOCH` ∧ `next_window.end > latest_data_end_floor` で raise、 advance も verify もまだ走らない経路)。

### B. NIT 修正の妥当性

1. `except ValueError` の narrowing が `EpochWindow.__post_init__` の唯一の raise 条件と整合しているか (broad catch を避けつつ、 想定外の `RuntimeError` 等は main 上方に伝播)。
2. `make_epoch_id` 自体は `strftime` のみで例外を出さないため、 narrow catch でも実用上 fallback 経路がほぼ走らないことを納得感のあるトレードオフと判定するか。

### C. 新規テストの網羅性

1. `test_reserve_raises_epoch_dataset_mismatch_after_advance_when_cfg_matches_old_window` が H4 Blocker の修正後挙動を verifying テストとして十分か (= advance 経路の dataset_match guard を機械検証)。

### D. 主要 38 + 1 = 39 テストの全 pass 確認

- Round 2 までに `uv run pytest tests/alpha_factory/test_epoch_manager.py` で 39 テスト全 pass を確認済。

### E. その他

- 既存 1210 テスト (alpha_factory + scripts) regression なし。 ruff / mypy clean。
