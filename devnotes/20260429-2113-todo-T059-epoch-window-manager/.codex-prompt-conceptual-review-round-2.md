## 残検証ポイント

1. **fcntl file lock の実用性**: macOS/Linux では fcntl で実用、 Windows 非対応で問題ないか (zenigame-fx は macOS 開発前提)
2. **`latest_data_end_floor` の safety margin 1 week**: 妥当か (DB 更新タイミングと M1 取得頻度から)
3. **`compatibility_fingerprint` の項目選択**: instrument/window_length_weeks/stride_days/max_runs_per_epoch/anchor_origin で網羅的か、 抜けている項目あるか
4. **anchor_origin の意味確定**: 「epoch 0 の window.end」 として state に固定。 後から anchor 変えると fail-closed。 これで 6m → 24m 移行時の挙動は正しいか
5. **`mark_run_status` 経路**: file lock を再取得して status update するが、 これも `reserve_run_slot` と同じ fcntl-based 排他で済ませて良いか
6. **`--reset-epoch-state` CLI flag の権限**: production で誤操作を防ぐため、 flag だけでは不足で confirm 入力 (`y/N`) や監査ログ (audit_log.jsonl 追記) が必要か
7. **24m 有効化の memory gate を T059 DoD に含めるか**: synthesis に従えば T070 以降の memory profile 系で実施だが、 T059 approval 条件として「24m 化前に RSS 実測」 を明記する必要があるか
8. **見落とし論点**: file lock timeout 10s の妥当性、 state schema_version の bump policy、 epoch_index の使用範囲
