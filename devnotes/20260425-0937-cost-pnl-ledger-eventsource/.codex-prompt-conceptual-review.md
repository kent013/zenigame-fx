## 概念設計

# 概念設計: cost-pnl-ledger-eventsource

## 背景・課題

Run 9 (run_20260425_002330) の Codex 独立分析で、コスト/PnL 集計経路の構造的な不整合が観測された。

**観測事実 (Fact)**:
- 全 120 個体で `total_pnl == 0.0` (min=max=mean=0.0)
- そのうち `trade_count > 0` を持つ個体が 30 個 (25%) 存在する
- `trade_count_max = 1331`、取引した個体の sharpe は全て負 (-93.10 〜 -4.76)

**解釈 (Interpretation)**:
- `trade_count > 0` ∧ `total_pnl == 0.0` は構造的矛盾。戦略性能の問題ではなく、コスト/PnL 集計経路に丸め・別系列参照・保存欠落のいずれかが発生している
- この矛盾が解消されない限り、cost-efficiency 改善のいずれも効果測定が不可能
- 加えて、無取引個体の `fitness_pen=0` が、取引する個体 (負 Sharpe) より相対優位になる「無取引へ収束」のループ (禁止事項 #6 構造的再発) の根本原因の一部でもある

## 改善アイデア

Fill (約定) を Single Source of Truth とした **イベントソーシング型 PnL 単一台帳** を導入する。

1. **Fill イベント記録**: 全約定を時系列イベントとして単一ストア (in-memory ledger) に記録
2. **コスト分解の標準化**: 各 Fill に対し `gross_pnl / spread_cost / slippage_cost / swap_cost / fee_cost / net_pnl` を必ず保存
3. **集計 = 純粋関数**: backtest summary の `total_pnl` 等は ledger からの reduce のみで導出
4. **不変条件監査 (invariant audit)**:
   - I1: `trade_count > 0` ⇒ `total_pnl != 0.0`
   - I2: `gross_pnl - sum(costs) == net_pnl` (各 Fill 単位)
   - I3: `sum(net_pnl per Fill) == total_pnl`
   - I4: `net_pnl` の符号が方向と一致
5. **archive Parquet 拡張**: `spread_total / slippage_total / swap_total / fee_total / gross_pnl_total` を個体単位で保存

## 期待効果

- **直接効果**: Run 9 で観測された `trade_count>0 ∧ total_pnl=0` を実行時 invariant assertion で検出・遮断
- **副次効果**: 後続 cost-efficiency 改善の効果測定土台、live/backtest 乖離分析の Fill 単位粒度

## 実装方針 (概要)

- `src/backtest/engine.py`: Fill 生成箇所で ledger エントリ
- `src/backtest/metrics.py`: `total_pnl` を ledger reduce に置換
- `src/broker/mock.py`: Fill 通知時にコスト各要素を attach
- `src/alpha_factory/archive.py`: 拡張列を Parquet schema に追加
- 新規: `src/backtest/pnl_ledger.py` (Ledger / FillEvent / invariant 検査)

invariant assertion 戦略:
- 開発/CI モード: assertion fail → raise
- production GA モード: violation を summary.diagnostics に記録、`fitness_pen` で減点 (120 個体評価を完走させる)

## 制約・前提

- 後方互換: 既存 archive Parquet schema は touch せず追記のみ
- イントラデイ / ロング・ショート両方向 / スワップ・スプレッド反映と整合
- trade_count 不変
- Stage A/B/C ゲートは touch しない
- メモリ: Fill 数は典型 1 個体 0〜数千、worker-local
