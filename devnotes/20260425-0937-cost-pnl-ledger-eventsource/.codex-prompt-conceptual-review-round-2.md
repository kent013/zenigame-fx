## 改訂版 概念設計

# 概念設計: cost-pnl-ledger-eventsource

> **Round 1 Codex review 反映** (CHANGES_REQUESTED → 縮小スコープに改訂)
> 当初「PnL 集計バグ」を仮定していたが、現行コード調査の結果、これは Stage A archive 投影仕様による未記録問題であることが判明。スコープを「Stage A 記録整合性監査 + コスト分解の可視化基盤」に縮小する。

## 背景・課題

Run 9 (run_20260425_002330) の Codex 独立分析で `trade_count > 0 ∧ archive.total_pnl == 0.0` が観測された。

**前提検証 (verified)**:
- 現行 backtest 側では `total_pnl = sum(Trade.pnl)` で正しく集計されている (`src/backtest/metrics.py#L85-L89`)
- `Trade.pnl` には closing 時点で `raw_pnl - holding_cost` の net_pnl が入る (`src/broker/mock.py#L327-L353`)
- Stage A の payload は `trade_count` と `sharpe_raw` のみで `total_pnl` を持たない (`src/alpha_factory/stage_gate.py#L268-L333`)
- archive への Stage A collect も `trade_count / sharpe` のみで `total_pnl` を書かない (`src/alpha_factory/archive.py#L322-L346`)
- 設計文書もこの仕様を明示している (`docs/alpha_factory/clause-architecture.md#L356-L365` — Stage A: `total_pnl - / trade_count ○`、Stage B/C で上書き)
- 既存合意は「Run 10 では監査のみ、挙動非変更」 (`devnotes/20260425-0931-fx-improve/improvement-plan.md#L7-L10`)

**前提検証 (unverified, 棄却された旧仮説)**:
- 「PnL 集計経路の破綻」を当初疑ったが、最新コード上では成立しない (集計自体は正しく動いている)

**真の課題**:
- Stage A 段階で archive に `total_pnl` が転記されない設計のため、Stage A で落ちた個体 (Run 9 では 120/120) は archive 上 `total_pnl=0.0` のように見える
- これにより post-run 分析で「PnL 集計バグなのか」「Stage A 落ち個体なのか」「コスト過大計上なのか」の切り分けが困難
- さらに後続 cost-efficiency 改善において「コスト要素ごとに何 pip 取られているか」を可視化する基盤が現状存在しない

## 改善アイデア (縮小スコープ)

### Phase A: Stage A 記録整合性監査 (audit-only, fail-open)

1. **Stage A archive 行に診断列を追加** (副作用ゼロ):
   - `metric_stage` (str): "stage_a_only" / "stage_b_evaluated" / "stage_c_evaluated"
   - `total_pnl_stage_a` (float, optional): Stage A 段階の total_pnl を**記録のみ** (既存 `total_pnl` 列は touch しない)
2. **archive consumer (run-report / analyze-run / sieve) は既存列のみ参照**: 後方互換維持
3. **Stage A backtest 結果から total_pnl を payload に追加** (`stage_gate.py` payload 拡張のみ、ゲート判定ロジックは不変)

### Phase B: コスト分解の可視化基盤 (taxonomy 確立)

1. **コスト taxonomy の確定**:
   - `holding_cost`: 既に明示分解済み (`src/broker/mock.py`)
   - `spread_implicit`: bid/ask 価格差として暗黙に埋まっている → entry/exit の mid-price と fill price の差から事後算出
   - `slippage`: MockBroker は現状ゼロ (price=fill price)
   - `swap`: イントラデイ前提のため通常ゼロ (持越し時のみ)
   - `fee`: 現状ゼロ
2. **archive Parquet に追記列**:
   - `spread_implicit_total` (mid-fill 差から再構成)
   - `holding_cost_total` (既存値の集約)
   - `gross_pnl_total` = `total_pnl + spread_implicit_total + holding_cost_total`
3. **既存列 (`total_pnl`) は touch しない**: 後方互換完全維持

### Phase C: invariant 監査 (CI 限定、fail-open)

1. **CI invariant**:
   - I1': `trade_count > 0 ⇒ archive 行が metric_stage を持つ` (どの段階の値か明示)
   - I2': `gross_pnl - holding_cost - spread_implicit ≈ total_pnl` (許容誤差付き)
2. **production GA invariant**:
   - violation を `summary.diagnostics.invariant_violations` に記録のみ
   - **fitness や選抜には一切影響させない** (旧設計の penalty 接続は削除)

## 期待効果

- **直接効果**: Run 9 で観測された `trade_count>0 ∧ archive.total_pnl=0` が「Stage A 投影仕様」によるものなのか「真のバグ」なのかが Run report 上で即座に切り分け可能になる
- **副次効果1**: 後続 5 件の cost-efficiency 改善のベースラインが定量化できる
- **副次効果2**: live execution との乖離分析が「コスト要素単位」で可能になる

## 制約・前提

- **後方互換完全維持**: 既存 archive 列 (特に `total_pnl`) を touch しない
- **fitness / 選抜への影響ゼロ**: invariant は production では fail-open のログのみ
- **絶対制約**: イントラデイ / ロング・ショート両方向 / スワップ・スプレッド反映と整合
- **trade_count 不変**: 集計経路の可視化のみで戦略の取引頻度には影響しない
- **既存 Stage A/B/C ゲートロジックは touch しない**
- **永続 Fill ledger は不採用**: 集計関数 (純粋関数) で再計算する方式
