まず仮説を立てろ。何を検証したいのか、なぜそう考えるのか、どうなれば成功と判断するのかを明確にしてから手を動かせ。

データに真摯に向き合え。数値を見て即座に閾値を弄るな。何が起きているのかを理解し、なぜそうなったのかを考え、どの方向に進むべきかを判断してから手を動かせ。

先人の知恵を探せ。学術論文・実務文献の引用を歓迎する（著者・年・タイトルを明記。記憶が曖昧なら「要確認」と明記）。

機能の名前に立ち返れ。名前はその機能が果たすべき役割を示している。

仕組みが機能していない段階で値を弄るな。設計の方向性が正しいと確認できてから値を弄れ。

因果ループを切断するな。「XはYに影響しない」という主張に出会ったら、間接経路を含む因果ループ全体を追え。

【使命（North Star）— 絶対遵守】
zenigame-fx Alpha Factory の使命は「config/alpha_factory/default.yaml → live_criteria を全て満たす FX イントラデイ戦略ゲノム個体を 1 つ見つけ出すこと」。
Stage C 通過は最低条件。使命達成 = live_criteria の全指標（Sharpe, Total PnL, Max Drawdown, Trade Count 範囲）を同時に満たし、Cross-pair (ii-lite) 評価も通過した個体の出現。
達成後は閾値を引き上げて次の水準を設定する（漸進的目標更新）。

【絶対制約】
- イントラデイ前提（オーバーナイト保有を前提にする設計は避ける）
- ロング・ショート両方向許容（FX の性質上）
- スワップ・スプレッドを fitness に反映（見かけの PnL ではなく純利益）

【禁止事項】
1. A・B・C 評価期間を強い根拠なしに延長する（過学習の隠蔽）
2. 見た目の数値をよくしようとする改善（Sharpe / WR 等の数値操作）
3. GA をハックしてステージを進めようとする（fitness 関数の歪曲等）
4. live_criteria 閾値をいたずらに緩和してステージを飛ばす
5. やたらに複雑な案を提案する（大規模リファクタリング、新フレームワーク導入等）
6. 取引回数を削減して見かけの成績を上げようとする（entry_threshold 過剰引き上げ等）
7. オーバーナイト保有前提の設計（スイングトレード化）
8. ゲノム archive スキーマ変更時の値伝搬漏れ（config → GaConfig → meta → consumer の 4 段接続漏れ）

【ツール使用制限】
コマンド実行・ファイル書き込みは一切行わず、提供されたテキストの分析に集中すること。ファイル読み込みは許可。

## レビュー観点 (Falsification-first、 Round 1)

以下の観点で**反証**を探してください。 単なる賛成は不要。

### 1. 数式の synthesis § 6 厳密準拠
- canonical 5 = (SR_session_worst, net_pnl_after_cost, max_dd, trade_count, session_block_win_rate_worst) で正しいか
- HAC Bartlett q=5 の式 (gamma 計算 + sigma2_LR + SR) が synthesis § 6.2 と一致するか
- session_block_win_rate_worst の trade=0 → 0.5 neutral 規約が synthesis § 6.3 と一致するか
- gate_worst_gap = max_m max(0, -slack_m)、 gate_pass <=> gate_worst_gap == 0 が § 6.4 と一致するか
- mission_inf_gap (T062 担当) を T061 で**計算しない**判断は § 6.4 の「win_rate を含まない」 制約と整合するか

### 2. 入力契約の責務分離
- session_bucket と business_day_index を **T070 (backtest engine) が割当**、 T061 は consume のみという責務分離は妥当か
- TradeRecord の field 過不足 (entry_time / exit_time / pnl_net / session_bucket / business_day_index / is_session_close_drop / is_negative_equity_drop_open)
- BarEquityPoint の equity 1 列で max_dd 計算が成立するか (timestamp_utc 単調増加が前提だが invariant 化が必要か)

### 3. 出力契約の網羅性
- CanonicalFiveResult が synthesis § 6 で必要な全出力を含むか
- per_bucket_sr / per_bucket_wr の diagnostic 出力は monitor 層 (T071/T915) で必要か (過剰でないか)
- log_pf_clip を T061 で計算する判断 (archive 末端 tie-break 用) は synthesis § 6.4 の「補助 metric」 位置づけと整合するか

### 4. 設計判断の妥当性
- **判断 1**: trade attribution rule = `exit_time_utc` (intraday 制約下で entry/exit attribution の差は最小だが、 別案 `entry_time_utc` の方が strategy intent 寄り)
- **判断 2**: block scale → annual scale 換算 = `SR_block * sqrt(756)` (756 = 252 営業日 × 3 bucket)
- **判断 3**: invariant fail-fast = `is_feasible=False` で `gate_pass=False` 強制 (caller の見落とし防止)
- **判断 4**: SessionBucket = StrEnum 3 値固定 (Tokyo/London/NY、 6 bucket 不採用)
- **判断 5**: denom floor の SSOT 定義 (zenigame `GAP_DENOM_FLOOR` と整合)
- **判断 6**: T062 (mission_inf_gap) との分離 (T061 では mission_inf_gap を計算しない)

### 5. C7 sample size 取扱い
- HAC q=5 が成立する block 数下限 (>=30) を engine 内で guard するか、 caller 側 guard か
- block 数 < 30 時の SR = -inf 強制 vs. 計算継続 + warn log

### 6. Phase 1 / Phase 2 分離の妥当性
- Phase 1 (T061 PR) スコープ = 新 module + test のみ、 既存 stage_gate / swim_lane / archive に touch しない
- Phase 2 申し送り 5 箇所 (`stage_gate.evaluate_stage_a/b/c` + 新規 `evaluate_stage_c_lite` + `cross_pair.shadow_validation`) は T063-T064 と同時更新で十分か
- T060 の Phase 2 申し送りで判明した「漏れ箇所」 (`calibrate_state.py:74` / `aux_preflight.py:52,189` / `inspect_stage_b_folds.py:83` / `tests/alpha_factory/test_config.py:333`) と類似の漏れが T061 にも存在しないか

### 7. C2 parallel-path 防止
- DoD に「旧経路 stage_gate.py に T061 import 入れない」「新 canonical_metrics.py を runtime 未配線」 を明示しているが、 grep 確認の精度は十分か
- 並走 path で「T061 calc」 と「stage_gate.py 旧 calc」 が duplicate computation する期間 (Phase 1 で merge 後 Phase 2 まで) のリスクは許容範囲か

### 8. 学術引用の正確性
- Lo (2002) "The Statistics of Sharpe Ratios" の引用は HAC 補正の根拠として妥当か (Lo は serial correlation 警告を出した側で、 HAC は Newey-West)
- Newey & West (1987) Bartlett kernel HAC の引用が正確か
- Bailey & López de Prado (2014) DSR が「HAC 補正後 SR を入力に取る」 と書いているか (要確認、 記憶曖昧なら明記)
