Round 1 の総合判定「(b)×(i) 採用可、ただし (ii-lite) 常設ベンチマーク並走」を受けて、実装レベルまで具体化したい。以下 5 つの論点に深く踏み込んでほしい。各質問では Round 1 と同様に **観察事実 → 解釈 → 判定** の構成で答えてほしい。

## Q5. Clause 複雑度制約の定量設計
Round 1 で「Clause 導入時は `max_clause`, `max_depth`, 複雑度ペナルティを必須」との指摘があった。
zenigame は経験的に max_clause=3、max_depth は primitive 再帰でなく合成式の深さとして制御している。

以下を FX 1 銘柄学習向けに具体化してほしい:
1. **max_clause の推奨値**: zenigame は 1-3 だが、FX 1 銘柄・3 年データ（有効サンプル ~200-300 営業日）では何が妥当か? Akaike / Bayesian 情報量基準の観点で粗い推定でもよい。
2. **複雑度ペナルティの具体形**:
   - Koza の parsimony pressure `fitness' = fitness - α × size` は bloat 抑制の古典
   - どのような α 設定・size 定義（primitive 数 / 深さ / 総ノード数）が FX で妥当か?
   - Allen & Karjalainen (1999) は TDL (Tree Depth Limit) だけで十分だったか? それとも補正項が必要だったか?
3. **ペナルティ導入時期**: Stage A（fast screen）でペナルティありにすべきか、Stage B/C だけ適用か?
4. **反証**: ペナルティ強めで champion 変動率が高まる・top-K 集団が退化するなら、ペナルティ設計自体の見直し条件は何か?

## Q6. (ii-lite) 常設ベンチマークの具体設計
Round 1 で「per-instrument champion 昇格時に必ず横断 fitness 集約をゲートとして実施」との提言あり。
これを実装レベルで具体化したい:

1. **実行タイミング**: Stage B (OOS) 直後か、Stage C (live_criteria) 前か?
2. **評価ペア集合**: 6 ペア全部か、それとも `アンカーペア` を別途定義すべきか?
   - 例: EUR_JPY で GA → 最終候補を {EUR_JPY, USD_JPY, EUR_USD} の 3 ペアで横断評価（currency 分散性を確保）
3. **集約関数の選択**:
   - mean / min / weighted mean / portfolio sharpe / rank IC
   - Round 1 で I3 "集約関数を変えても champion が安定なら目的関数依存性は小さい" との言及あり。FX でこれを検証する実験設計は?
4. **通過基準**: 集約 fitness のしきい値は per-instrument fitness の何% or 絶対値何以上にすべきか?
5. **反証**: (ii-lite) を課したことで per-instrument Sharpe が顕著に劣化するなら、(ii-lite) は `二重罰` になる可能性。そのときの判断基準は?

## Q7. 移行トリガーの事前固定（CONDITIONAL の条件化）
Round 1 で「連続 run で DSR 非正、PBO 高止まり、fold 符号反転多発なら (ii) へ移行」との指針あり。
具体的なしきい値を提案してほしい:

1. **DSR (Deflated Sharpe Ratio)** 非正の判断:
   - 何 Run 連続で DSR < 0 なら移行検討か? (Bailey & López de Prado の元論文で示唆される値があれば引用)
   - 単発 DSR 非正と、連続 k 回非正では扱いが違うはず。k の目安は?
2. **PBO (Probability of Backtest Overfitting)** 高止まり:
   - PBO > 0.5 は overfitting 強とされるが、Alpha Factory 運用で何 % を移行トリガーに?
   - 計算に必要な fold 分割数・sub-sample 数は実用上どれくらい?
3. **Fold 符号反転率**:
   - N fold 中 m fold で OOS Sharpe の符号が反転した場合を trigger とする。m/N のしきい値は?
   - walk-forward の window 長・step 長をどう設計するか?
4. **Reality Check / SPA**:
   - White (2000) の Reality Check は bootstrap サンプリング必要。計算コスト許容範囲で何回サンプリングすれば実用か?
5. **複合トリガー**: 上記 4 指標を AND/OR でどう組み合わせるか? 単一指標での判断は誤判定リスク。

## Q8. Currency common factor への対応
Round 1 I2 (Q2) で「FX 6ペアでも USD 共通因子・リスクオン/オフがあり、完全分離最適化は情報共有を捨てる」との指摘。

1. **共通ファクター明示化**: 以下のいずれがよいか?
   - (α) DSL 変数として `dxy`, `vix`, `risk_on_index` などを導入し、全 primitive がアクセスできる
   - (β) 評価時だけ共通因子フィルタリング（例: DXY 上昇時の USD_XXX trade をフィルタ）
   - (γ) 何もせず GA が自力で発見することを期待
2. **三角裁定制約の扱い**: EUR_JPY ≈ EUR_USD × USD_JPY という恒等式。6 ペア同時運用で portfolio 制約を入れないと実運用で整合しない取引が出る可能性。Per-instrument GA ではこの問題は顕在化するか?
3. **反証**: 共通因子導入で per-instrument Sharpe 改善が見られなければ、共通因子は不要 or 実装が不適切。

## Q9. 実装順序と「最小動く状態」
Skill 移植の Phase 0-5 計画（要旨）:
- Phase 0: DROP skill 退避
- Phase 1: 基盤 skill RENAME-ONLY
- Phase 2: FX Alpha Factory 基盤構築（Clause / Stage A/B/C / archive / TODO / focus-theme）
- Phase 3: CONTENT-ADAPT 15 skill 移植
- Phase 4: INFRA-ADAPT 4 skill 実装（calibrate-gate, post-run-review, alpha-sieve, primitive-ic）
- Phase 5: 通し動作確認

Round 1 の提言を組み込むと Phase 2-4 のスコープが膨らむ。
以下を決めたい:

1. **最小動く (MVP) 状態**: どこまで実装すれば「improve-cycle が 1 サイクル回る」と言えるか?
   - 例: Phase 2 の Clause 実装は必須だが、DSR/PBO/Reality Check は Phase 4 に回す、など
2. **(ii-lite) 組み込み時期**: Phase 2 で実装すべきか、Phase 4 まで後回しにできるか?
3. **移行トリガー実装時期**: 事前固定は必須だが、実測値が溜まるまで仮値でよいか? 何 Run 分溜めてから発動か?

   - Phase 2 末時点で「max_clause=1（実質フラット合成）」で始め、Phase 3 で max_clause=3 に段階展開するのは妥当か?
   - これは zenigame 移植の忠実性を一部犠牲にするがデバッグ容易性を高める
5. **反証**: 上記の段階的アプローチが「結局フラット式と同じになる」恐れはないか?
