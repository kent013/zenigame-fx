## 背景・課題

直近 Run 7-9 で以下が観測された:

- **Fact**: Run 7-9 archive `fold_sign_ratio: n=0`、`dsr: n=0` が連続 (上表 #9)
- **Fact**: Run 7/8 は Stage A pass=48-66/120、Stage B pass=0/120 (上表 #8)
- **Fact**: Run 7-9 dataset は 14351 bar (約 15 日)、`stage_b_window_months=18` の典型 WF 要件 (train_days + test_days × n_folds + embargo) を物理的に満たさない可能性 (上表 #11-13、要 Verified 化)
- **Fact**: Stage B `oos_sharpes` が length=0 の場合、archive は `fold_sign_ratio=None` を書き込む経路あり (上表 #5)
- **Fact**: Stage B `dsr` は現行 hard-coded `None` (上表 #6)

**Interpretation**:

- Stage B は「弱い個体を落とす」より前段で「**入力窓不足 + 統計未計算**」のため意味のある fold 計算に到達していない可能性が高い (Unverified だが整合的)
- 結果として、Stage B 通過率の構造改善には gate 単体の semantics 変更ではなく
  1. **upstream**: `bars_stage_b` の WF 最小要件充足を runner 側で契約化
  2. **gate**: 有効 fold 数 (`n_fold_effective = n_fold - n_fold_unavailable`) を独立メトリクスとして可視化
  3. **archive/report**: 失敗理由の **世代別** 集計を可観測化

の 3 点を **観測 → 監査 → (実測後) hard 化** の順で進める必要がある。

C7 警告: 3 Run の観測のみで因果を断定する設計は不可。本案は「**観察可能性確保 + 入力契約検査**」を優先し、新たな hard threshold は実測分布が出るまで導入しない。

## 改善アイデア

**設計方針**: 既存の reason code・metric semantics は破壊しない。観測経路と入力契約のみ追加する。

### A. Stage B 入力窓充足契約 (runner 側)

- `scripts/alpha_factory/run_ga.py` の dataset bundle 構築時に `bars_stage_b` 長と `stage_b_window_months` から **WF 最小必要 bar 数** を逆算し、不足時に明示 `reason_code="stage_b_window_underfilled"` で Stage B を no-op fail させる
- WF 最小要件式: `min_bars = bars_per_day * (wf_train_days + wf_test_days + wf_embargo_days)` (1 fold 最小)。fold 3 取るなら `+ 2 * wf_step_days`
- 不足時、`run_ga` は warning ログを出し、`evaluate_stage_b` 呼び出しを skip して `StageResult(passed=False, reason_codes=("stage_b_window_underfilled",))` 相当を返す

### B. Stage B 観察可能性メトリクス追加 (monitor only、hard gate なし)

- `evaluate_stage_b` の `metrics.payload` に以下を追加:
  - `n_fold_effective: int` (= `n_fold - n_fold_unavailable`)
  - `positive_fold_ratio_effective: float | None` (= 有効 fold のうち sharpe>0 の割合。`fold_sign_ratio` とは別物)
- 既存 `fold_sign_ratio` (隣接符号反転比率) 意味は **一切変更しない**
- 既存 `no_folds` / `insufficient_folds` / `all_folds_unavailable` reason は維持
- 補助タグ `stats_unavailable` は **追加しない** (上記 3 reason で粒度十分。本ラウンドの最小修正方針に合わせる)

### C. archive schema 拡張

- archive Parquet に `n_fold_effective: int64?`、`positive_fold_ratio_effective: float64?` を **追加** (削除・型変更なし)
- 既存行は `null` で前方互換

### D. run-report 強化

- run-report の Stage B セクションに「**世代別 Stage B failure reason 集計**」テーブルを追加
- 例: `gen | n_total | n_pass | reason: no_folds | insufficient_folds | all_folds_unavailable | window_underfilled`
- `n_fold_effective` 分布も追加 (今後の hard gate 化判断のため)

### E. テスト追加

- `tests/alpha_factory/test_stage_gate.py`:
  - `n_fold_effective` / `positive_fold_ratio_effective` の値が `metrics.payload` に正しく入る
  - 全 fold unavailable のとき `n_fold_effective=0` かつ既存 `all_folds_unavailable` reason が継続発火
- `tests/alpha_factory/test_run_ga.py` (or 同等):
  - `bars_stage_b` 不足時に `stage_b_window_underfilled` reason で fail し、`evaluate_stage_b` が呼ばれない

## 期待効果

- live_criteria 達成への貢献:
  - Stage B = 0 連続の根本原因 (window 不足 vs fold 評価失敗 vs 弱さ) を世代別 reason 集計で診断可能化 → 次サイクルの改善ターゲットを正確に絞れる
  - upstream 入力契約により「測定不能個体」が Stage B を通過判定の余地に残らないことを保証
- 過学習耐性:
  - `n_fold_effective` 分布が実測されることで、将来の `dsr` / `pbo` hard gate 化に必要な「サンプル数の現実分布」を把握できる
  - 本提案自体は新 threshold を導入しないため fail-open / fail-closed の semantics 反転は起こさない (現行を維持)
