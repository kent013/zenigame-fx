【思考原則 — 全議論に適用】
まず仮説を立てろ。何を検証したいのか、なぜそう考えるのか、どうなれば成功と判断するのかを明確にしてから手を動かせ。

データに真摯に向き合え。数値を見て即座に閾値を弄るな。何が起きているのかを理解し、なぜそうなったのかを考え、どの方向に進むべきかを判断してから手を動かせ。

先人の知恵を探せ。学術論文・実務文献の引用を歓迎する（著者・年・タイトルを明記。記憶が曖昧なら「要確認」と明記）。

機能の名前に立ち返れ。名前はその機能が果たすべき役割を示している。

仕組みが機能していない段階で値を弄るな。設計の方向性が正しいと確認できてから値を弄れ。

因果ループを切断するな。「XはYに影響しない」という主張に出会ったら、間接経路を含む因果ループ全体を追え。

【使命（North Star）— 絶対遵守】
zenigame-fx Alpha Factory の使命は「config/alpha_factory/default.yaml → live_criteria を全て満たす FX イントラデイ戦略ゲノム個体を 1 つ見つけ出すこと」。
Stage C 通過は最低条件。使命達成 = live_criteria の全指標（Sharpe, Total PnL, Max Drawdown, Trade Count 範囲）を同時に満たし、Cross-pair (ii-lite) 評価も通過した個体の出現。
達成後は閾値を引き上げて次の水準を設定する（漸進的目標更新）。

【絶対制約】
- イントラデイ前提（オーバーナイト保有を前提にする設計は避ける）
- ロング・ショート両方向許容（FX の性質上）
- スワップ・スプレッドを fitness に反映（見かけの PnL ではなく純利益）

【禁止事項】
1. A・B・C 評価期間を強い根拠なしに延長する（過学習の隠蔽）
2. 見た目の数値をよくしようとする改善（Sharpe / WR 等の数値操作）
3. GA をハックしてステージを進めようとする（fitness 関数の歪曲等）
4. live_criteria 閾値をいたずらに緩和してステージを飛ばす
5. やたらに複雑な案を提案する（大規模リファクタリング、新フレームワーク導入等）
6. 取引回数を削減して見かけの成績を上げようとする（entry_threshold 過剰引き上げ等）
7. オーバーナイト保有前提の設計（スイングトレード化）
8. ゲノム archive スキーマ変更時の値伝搬漏れ（config → GaConfig → meta → consumer の 4 段接続漏れ）

【ツール使用制限】
コマンド実行・ファイル書き込みは一切行わず、提供されたテキストの分析に集中すること。ファイル読み込みは許可。

【レビュー重点項目 — 転記漏れパターン】
zenigame（姉妹プロジェクト）では「値の転記漏れ・伝搬漏れ・記録漏れ」が繰り返し発生した。zenigame-fx でも以下を重点的にチェックすること:
1. 新規パラメータ/カラム追加時: config 定義→GaConfig 読み込み→genome.meta 注入→consumer 参照の 4 段階が全て接続されているか
2. archive 記録: GENOMES_SCHEMA にフィールド定義→_create_row_template 初期値→collect_stage_* 書き込み→flush 出力の 4 点セット
3. 関数パラメータ: 新規パラメータ追加時に全呼び出し元で引数が渡されているか
4. ログ出力: 新規の値伝搬に対応する logger 出力が追加されているか

【監査・レビュー時の必須チェック — False-positive 再発防止】
以下の discipline を全レビュー・監査で遵守すること。

### C1. Design-first 原則 (code grep より先に docs を読む)
コードの bug / 設計欠陥について claim を出す前に、以下を verify:
- docs/alpha_factory/ 配下の該当セクション（stage-gates.md / clause-architecture.md 等）を Read で確認
- devnotes/ 配下の関連 T-number（関数コメントや git log に出てくる T-xxx）を ls devnotes/ | grep T{xxx} で探して読む
- git log --all -S "識別子" で該当 code の変更履歴を辿る
- 該当機能と並行計算される可能性のある経路を grep で広く検索

### C2. 「X が無い = バグ」禁止ルール
関数 Y の signature / body に識別子 X が無いことを根拠に bug 判定してはならない。別経路での計算を grep で広く検索してから。

### C3. Collider bias 必須チェック（相関分析時）
2 つの変数 A, B の相関を計算して report する場合、Conditioning set と collider の有無を必ず明記。

### C4. 前提明示ルール
Claim / verdict を出す前に、prompt の先頭に「本分析の前提」を bullet でリスト化し、各前提が verified であることを明示。

### C5. 並列 sub-agent の framing 独立性チェック
独立検証のつもりで同じ framing の sub-agent を N 個回しても、それは 1 つの誤読の N 倍冗長実行。

### C6. Fact / Interpretation 分離ルール
「観察された事実 (Facts)」と「解釈・推論 (Interpretations)」を明確に区別する。1 文で mix しない。

### C7. Sample size ガード
n < 30 の相関 claim は明示的に因果解釈を避ける。n < 10 は相関 claim 禁止（observation のみ許可）。

### C8. INCONCLUSIVE を第一級 verdict に
INCONCLUSIVE は CONFIRMED / REJECTED と同格の選択肢。データ不足は正当な結論。

### C9. Falsification-first プロンプト
Round 1 は「この hypothesis の反証を探せ」という指示を先に書く。confirmation bias を強制しない。

**作成日時**: 2026-04-22 17:16 (JST)

## 3. 設計方針

### 3.1 spread フィルタ（約定前フィルタ）

**仕様**:
- `max_spread_bps: Decimal | None`（None = 無効）
- 各 bar の spread は `(ask.close - bid.close) / mid.close × 10000` （bps 単位）
- **フィルタ適用タイミング**: `fill_pending` の直前。open 系シグナル（open_long / open_short）について、
  **約定対象 bar の spread が max_spread_bps を超えていた場合、当該 pending シグナルをスキップ**
- close 系シグナル（close_position / close_all）は**常に約定**（エントリー抑制のみ、保有中は強制 close が優先）

**理由**:
- `fill_pending` は次バー open で約定する設計なので、「発注時点（前 bar）」ではなく
  「約定実行 bar」の spread で判定する方が経済的に正確
- Engle & Lange (2001) "Predicting VNET" 系の流動性・スプレッド変動に関する実証研究から、
  スプレッド急拡大時の約定回避は実務上必須（要確認: 実際の OANDA ヒストリカル spread データで典型レンジを検証）
- **spread 計算は close を使う**（open は未観測で約定時点の判断要因に使えない、mid は `(ask + bid) / 2`）
- **約定対象 bar の spread を事前チェック**: 発注 bar の close spread を記録 → 次 bar 約定時に `broker._last_bar_close_spread_bps` で判定

### 3.2 swap コスト（日次按分で bar ごと equity 控除）

**仕様**:
- `swap_cost_per_day_bps: Decimal`（デフォルト 0）
- 各 bar `mark_to_market` 時点で開いているポジションがあれば:
  ```
  per_bar_bps = swap_cost_per_day_bps × (bar_minutes / 1440.0)
  swap_amount = Σ (|notional_home| × per_bar_bps / 10000)  over open positions
  cash -= swap_amount
  ```
- `bar_minutes` は bars のインデックス連続性から算出できないため、**本 TODO は M1 固定** = `1 分 / 1440 分`。
  M5 / M15 対応は config で bar_minutes を受け取る拡張だが本 TODO ではスコープ外。
  保険として `bar_minutes` を `BacktestConfig.bar_minutes: int = 1` として明示フィールド化。
- **控除は `cash` にマイナス加算**（`equity = cash + unrealized` なので実質 equity が下がる）
- **non-negative 契約**: swap が正の数として入力される想定（コストなのでプラス値で「払う」意味）。負の
  swap（受け取り）は本 TODO では未対応、実質 `swap_cost_per_day_bps >= 0` を contract とする

**実務裏付け** (要確認フラグ):
- OANDA のスワップ (finance charge) は日次付与（公式ドキュメント: OANDA JP Pricing & Spec。値は通貨ペア・
  ポジション方向・時期で変動）
- bar 単位への按分は実務では「日またぎ」で一括計上だが、本 MVP では per-bar 線形按分で近似
  （fitness への影響を確定的・滑らかに反映するため）
- 実値は `clause-backtest-integration` のテストでは合成値（例: 2.0 bps/day）を使用。
  現実値の反映は後続の stage-gate-implementation / run-ga-full-rewrite で config 化

### 3.3 session close（イントラデイ強制クローズ）

**仕様**:
- `session_close_utc_hours: frozenset[int]`（空集合 = 無効、engine EOD に委譲）
- 各 bar `fill_pending` → `mark_to_market` の後、**戦略 on_bar 呼び出しの前**に、
  `bar.bar_time.hour in session_close_utc_hours and broker.open_positions` なら
  `broker.close_all(bar, reason="eod")`
- close 後にも `on_bar` は呼ぶ（新規エントリーは通常の entry 判定に従う）
  - ただし同じ bar で close → open は流動性リスクが大きいため、`strategy.on_bar` からの open シグナルは
    該当 bar では **filter** する（= pending に入れない、もしくは強制 close した bar では warm 用 no-op）
  - 簡略化のため、本 TODO では **「強制 close した bar では新規 open を抑制」** 方針を取る
    （engine 側で flag を立てて `submit` を skip）

**なぜ engine 側でやるか**:
- DslStrategy は「同一 bar 内の強制 close」を表現できる（`on_bar` で close_position を返せる）が、
  strategy の責務を「戦略判断」に限定し、「時間ベースの絶対制約」は engine の責務とするほうが綺麗
- 既存の `is_eod` / `close_all(reason="eod")` と同じ責務レベル
- 「DslStrategy.session_close_utc を廃止するか」は残すが、本 TODO では **engine 側を正** にし、
  DslStrategy の session_close_utc は「backward-compat な second fail-safe」として維持（両方有効でも
  engine 側が先に発動するので挙動に影響なし）

### 3.4 PrimitiveEvaluator 注入

- `run_backtest` に `primitive_evaluator: PrimitiveEvaluator` 引数を追加（keyword-only）
- 旧 `Strategy` protocol を実装した `_ScriptedStrategy` などの既存テストは evaluator を
  使わないため、`primitive_evaluator` にはテスト用ダミー（何も返さないプレースホルダ）を渡せる必要がある
- **解決**: `primitive_evaluator` を `PrimitiveEvaluator | None = None` とし、None の場合は `DslStrategy`
  が組み立て時に `evaluator=primitive_evaluator` を渡されるルートでしか使われないため、
  `run_backtest` 内部で evaluator を直接使わない（strategy 側に渡す責任は
  `evaluate_genome` が持つ）

再検討:
- 本 TODO の最小変更は「`run_backtest` は primitive_evaluator を受け取るが、渡された strategy が
  DslStrategy でなければ無視」。単に「`DslStrategy(genome, evaluator=...)` を組み立てる責務を
  `evaluate_genome` に閉じ込める」設計にする
- **最終方針**: `run_backtest` は primitive_evaluator **引数を追加しない**。Strategy コンストラクタ時点で
  evaluator を bake-in する（DslStrategy 設計に準拠）。タスク要求の「evaluator 注入型」は
  `evaluate_genome` の責務として閉じる。`run_backtest` のシグネチャは据え置き＋spread/swap 導入のみ。

### 3.5 `fitness.py::evaluate_genome` 復活

```python
def evaluate_genome(
    genome: Genome,
    bars: list[PriceBar],
    meta: InstrumentMeta,
    backtest_config: BacktestConfig,
    primitive_evaluator: PrimitiveEvaluator,
    *,
    metric: FitnessMetric = "total_pnl",
    warmup_bars: int = 0,
    session_close_utc: time | None = None,
) -> Decimal:
    try:
        strategy = DslStrategy(
            genome,
            primitive_evaluator,
            warmup_bars=warmup_bars,
            session_close_utc=session_close_utc,
        )
        broker = MockBroker(instrument_meta=meta)
        result = run_backtest(bars, strategy, broker, backtest_config)
        metrics = compute_metrics(result.trades, result.equity_curve)
        if metric == "total_pnl":
            return metrics.total_pnl
        if metric == "sharpe":
            return Decimal(str(metrics.sharpe)) if metrics.sharpe is not None else _FAILURE_FITNESS
        if metric == "calmar":
            return Decimal(str(metrics.calmar)) if metrics.calmar is not None else _FAILURE_FITNESS
        raise ValueError(f"unknown metric: {metric}")
    except Exception as exc:
        logger.warning("ga.fitness.failure", genome=genome.name, error=str(exc))
        return _FAILURE_FITNESS
```

- metric は既存の `Literal["total_pnl", "sharpe", "calmar"]` を踏襲
- `BacktestMetrics.sharpe` / `calmar` が `Decimal | None` なので None 時は `_FAILURE_FITNESS` で代替
  （タスク要求の「metric が取れない時 failure」に沿う）
- sharpe は既に `Decimal(str(sharpe_f))` として `BacktestMetrics` に入っているので `Decimal(str(...))` の
  二重変換は不要（既存型を直接使う）

### 6.2 spread フィルタのバッファリング方式

**採用**: 「約定対象 bar の close spread」で判定 = `fill_pending(bar)` の冒頭で bar の spread_bps を
計算し超過なら open シグナルのみ skip、close は通す。

Alternative: 「発注 bar の close spread」で判定（前 bar の情報のみで判定）もあり得るが、
「約定時のコスト」という経済的意味から前者を採用。

### 6.3 swap 方向の解釈

- 本 TODO: **コスト** 固定（`swap_cost_per_day_bps >= 0` を contract）

### 6.4 spread / session close / swap フィールドの Optional 性

全て「なし (0 / None / 空集合) = 無効」のデフォルトにする。既存 `test_engine.py` が壊れない
ことを保証（明示的に BacktestConfig の値を渡さない既存呼び出し互換）。

### 6.5 イントラデイ絶対制約の冗長担保

`session_close_utc_hours` と engine 既存の `is_eod` 判定の両方が無効 = ゲノム評価が
日跨ぎ前提になってしまう。North Star (イントラデイ必須) を engine レベルで担保する不変条件を
`run_backtest` 入口で検査:

- `session_close_utc_hours` 空集合 **かつ** `is_eod` が常に False（bars が単一 UTC date）
  の場合は warning（fail はしない、テストで短期 bar 使う利便性優先）
