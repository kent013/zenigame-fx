# Round 2: Phase C 着手前の grep で T034 禁止事項 #4 ガードを発見

## 重要発見

`src/alpha_factory/stage_gate.py:519-523` に **明示的ガード**:

```python
if (
    lc_trade_count_min >= 1
    and self.min_exposure_trade_count >= lc_trade_count_min
):
    raise ValueError(
        "min_exposure_trade_count must be < live_criteria.trade_count_min "
        f"(禁止事項 #4 ガード)"
    )
```

= **min_exposure_trade_count == live_criteria.trade_count_min も禁止 (strict less than)**。

T034 設計意図 (= docstring `stage_gate.py:504-508`):
> 「Stage A で trade_count_min まで要求 = 事実上 live_criteria.trade_count_min を緩和」 を防ぐ (禁止事項 #4 ガード)。

= Round 1 で APPROVED した「`min_exposure: 1 → 50`」 は **invariant 違反で起動不能** (`ValueError`)。

## T034 設計意図の解釈

設計の根拠 (= 推測): Stage A は短期 (60 日)、 live_criteria 評価期間は dataset 全体 (6 ヶ月)。 Stage A で trade_count >= 50 を要求すると:
- 60 日で 50 trade ≈ 6 ヶ月で 250 trade scaling
- = live_criteria.trade_count_min=50 / trade_count_max=5000 の中間に強制シフト
- = 「Stage A で trade_count を強制 = mission 評価期間との非対称な圧」 = 禁止事項 #4 (= live_criteria 緩和) の派生

これは synthesis § 5 の「Stage A は fast screen、 trade_count_min は live_criteria 専用」 と整合。

## 選択肢 (= Round 2 議論題材)

### 案 A: min_exposure_trade_count: 1 → 49 (= live_criteria.trade_count_min - 1)
- invariant strict less than を尊重しつつ「ほぼ live_criteria 同等」 強化
- 49 trade ≈ 60 日 = ≈ 1 trade/1.2 営業日 = まだ low-trade 寄り
- 補正効果: 限定的 (= 49 と 1 の中間効果しかない)

### 案 B: invariant `<` → `<=` に緩和 (= T034 設計意図に逆らう)
- live_criteria SSOT との同期を優先
- ただし T034 の禁止事項 #4 ガードを破る = 設計意図への抵触
- リスク: synthesis § 5 「Stage A は fast screen」 の役割逸脱

### 案 C: GA elite 経路で feasibility 圧を強化 (= 別経路)
- 既存 `ga.feasibility.entry_count_min: 50` は GA selection_score の feasibility bit
- Run-28 best=g11_i31 trade_count=48 = infeasible だが elite で残った可能性
- 仮説: elite_count=2 で「feasibility=False の elite」 を許容している → elite を「feasibility=True のみ」 に絞る修正

### 案 D: Stage A 判定式で **fold_trade_count_min 整合性** を追加要求 (= 構造的整合性回復)
- Stage A は短期 60 日 / Stage B fold は 10 営業日 → ratio = 6
- Stage A pass の前提として「trade_count >= 6 * fold_trade_count_min = 60」 を要求
- = stage_gate 内で Stage B fold 構造との整合性を見る (= 新 invariant)
- ただし設計修正範囲が広い (= 今 cycle 範囲外の可能性)

### 案 E: Stage A 判定式に **trade_density 要求** を追加
- min_exposure_trade_count とは別に「trade_per_day >= X」 を要求 (= 時間集中防止)
- 反証 (c) (= time-concentrated 取引が真因) を構造的に解消
- 実装範囲: stage_gate に新 condition + config 追加

### 案 F: 何もしない (= cycle 2 を skip、 別観点で次 cycle 進める)
- I1 仮説が config invariant で構造的に実装不能なら、 別観点 (= primitive 改革 / Stage B 判定式緩和) を再検討
- ただし「primitive 改革は post-run-review 担当 / 緩和は禁止事項 #4」 で詰む
- = cycle 2 で得られた learning (= 設計 invariant の発見) を handoff に残して cycle 3 へ
