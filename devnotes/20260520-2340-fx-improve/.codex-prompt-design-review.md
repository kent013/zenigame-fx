# レビュー対象の詳細設計

## C1: Stage B→C gap diagnostic v1

### 設計方針
Stage C の StageResult.metrics["payload"] に分類に必要な全データが既に存在（新規 backtest 不要）:
- payload["live_criteria_pass"]: {sharpe, total_pnl, max_drawdown, trade_count_min, trade_count_max} の bool dict
- payload["total_pnl"], payload["trade_count"]: base(unstressed) holdout 値
- payload["stress"]: {pnl_degradation(=base-stress), trade_count, total_pnl, sharpe_degradation, skipped}
- result.reason_codes: 失敗理由 tuple（system_failure 含む）

### 変更 (1) diagnostics_collector.py
- 新規 module 関数 `_derive_stage_c_gap(result: StageResult) -> dict`（payload を defensive read、全例外を握り潰し fail-soft で安全 default を返す）。
- gap_class enum（固定集合 frozenset）: pass / pnl_only / count_only / both_pnl_count / sharpe_involved / mixed / stress_or_other / system_fail / unknown。
- 分類優先順位（排他）:
  1. reason に system_failure → system_fail
  2. result.passed → pass
  3. base live_criteria 失敗組合せ: both_pnl_count（pnl∧count）/ pnl_only（pnl のみ）/ count_only（count のみ）/ sharpe_involved（sharpe 含む）/ mixed
  4. base lc 全通過だが stress/intraday 等で fail → stress_or_other
  5. payload 不整合 → unknown
- `record_stage_c` のシグネチャを `passed: bool` → `result: StageResult` に変更（record_stage_a と同型）。rec.stage_c_pass = bool(result.passed) を維持しつつ、gap_class と raw 値（base_total_pnl / base_trade_count / stress_pnl_degradation / stress_trade_count）を IndividualDiagnostics に記録。
- IndividualDiagnostics に nullable field 5 つ追加。to_rows に 5 列追加 + gap_class enum invariant assert。

### 変更 (2) diagnostics_sidecar.py
- STAGE_A_PROVENANCE_SCHEMA に nullable 5 列追加（stage_c_gap_class: string, stage_c_base_total_pnl: float64, stage_c_base_trade_count: int32, stage_c_stress_pnl_degradation: float64, stage_c_stress_trade_count: int32）。
- DIAGNOSTICS_SCHEMA_VERSION は 2 のまま据え置き（追加は全 nullable、v2 contract の required field 集合は不変。assert_diagnostics_v2 は required field のみ検証）。
- build_sidecar_table は to_rows() dict を from_pylist(schema=...) するため、schema 列追加で自動出力。Stage A/B 止まり個体は新列 null。

### 変更 (3) swim_lane.py
- record_stage_c 呼出 2 箇所（逐次 688 行 / 並列 888 行）で `bool(c_result.passed)` → `c_result`（StageResult）に変更。両 call site とも有効な StageResult を保持済み。

### テスト計画
- _derive_stage_c_gap の各 gap_class unit test、defensive ケース（stress skipped / payload 欠落 / reason 空）。
- record_stage_c シグネチャ変更に伴う既存テスト更新。
- to_rows 新列 + enum invariant。build_sidecar_table/write_stage_a_provenance の integration（新列出力、Stage A 止まり null、schema mismatch warning なし）。
- 既存 sidecar regression（既存列・行数・metric_stage enum 不変）。

### リスク
低。観測専用・fail-soft。GA 評価/gate/fitness/既存 sidecar 列に影響なし。波及は record_stage_c シグネチャ変更（2 call site + test）。

# 参考: 現行コード抜粋

## diagnostics_collector.py record_stage_c（現行）
```python
def record_stage_c(self, lane_id, generation, individual_name, passed: bool) -> None:
    rec = self._records.get(self._key(lane_id, generation, individual_name))
    if rec is None:
        return
    rec.stage_c_pass = bool(passed)
```

## stage_gate.py evaluate_stage_c の payload 構築（2229-2266 行 抜粋）
```python
metrics_envelope = {
  "stage": "C", "genome_name": genome.name, ...
  "payload": {
    "trade_sharpe_raw": base_sharpe,
    "trade_sharpe_annualized": base_sharpe_annualized,
    "total_pnl": base_total_pnl,
    "max_drawdown_frac": base_max_dd_frac,
    "trade_count": base_trade_count,
    "mission_score": mission_score,
    "live_criteria_pass": lc_pass,   # {sharpe, total_pnl, max_drawdown, trade_count_min, trade_count_max}
    "intraday_compliant": intraday_compliant,
    "overnight_violations": overnight_violations,
    "stress": stress_payload,         # {skipped, sharpe, total_pnl, max_drawdown_frac, trade_count, sharpe_degradation, pnl_degradation}
    "cross_pair": cross_pair_payload,
    "canonical_shadow_c_base": ...,
  },
}
return StageResult(stage="C", passed=passed, metrics=metrics_envelope, reason_codes=tuple(reasons))
```
注: stress_payload は skip 時 {"skipped": True, "pnl_degradation": 0.0, "trade_count": 0, ...}。lc_pass の trade_count は trade_count_min と trade_count_max の 2 key に分かれる。base_failed 時は lc_pass 全 False かつ reason に system_failure。

# レビュー観点
1. コードの正確性（分類ロジックのエッジ: stress skipped 時の degradation=0.0 を「劣化なし」と誤読しないか、base_failed 時の lc_pass 全 False が system_fail で正しく先取りされるか、trade_count_max fail を count_fail に含める妥当性）
2. 既存コードとの整合性（record_stage_a との対称性、IndividualDiagnostics の last-write-wins）
3. schema version 据え置き（v2 のまま nullable 列追加）の妥当性 — 後方互換性、consumer（run-report skill / 既存 parquet reader）への影響
4. テスト網羅性
5. 副作用・後退リスク（観測専用の主張が本当に成立するか、record_stage_c 例外が GA を止めないか）
6. 波及変更の網羅性（docs/skill/config）
7. 前提検証(C4): 「両 call site が有効な StageResult を持つ」は正しいか
8. fail-soft 設計が観測欠損（全 null）を招かないか（success_criterion を自壊させないか）
