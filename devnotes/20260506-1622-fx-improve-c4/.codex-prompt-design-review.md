# cycle 4 詳細設計レビュー

## 概要

cycle 3 sidecar データで verified された **H1 (探索圧不整合)** に対する構造的介入。 当初 plan-and-design で「fitness_pen に fold-aware penalty 追加」 と決めたが、 実装経路調査で archive→cache→GA selection の各層で plumbing が必要と判明。

代替設計: **IndividualCacheEntry の selection_score 8→9 要素化** で同等効果。 GA tournament + elite 両方が `_selection_key` 経由で selection_score を使うため、 1 要素追加で全 selection 経路に効く。

## 設計

### IndividualCacheEntry 拡張

```python
# 現行 (run-36 まで)
selection_score: (feasible, -violation, stage_b_pass, stage_c_feasible, C_pass, B_pass, A_pass, fitness_pen)
# 8 要素

# cycle 4 拡張 (run-37 から)
selection_score: (feasible, -violation, stage_b_pass, stage_c_feasible, C_pass, B_pass, A_pass, fold_robust, fitness_pen)
# 9 要素 (fold_robust を fitness_pen より上位に挿入)
```

### fold_robust 判定

```python
fold_robust = (
    pfre is not None
    and math.isfinite(pfre)
    and pfre >= fold_robust_threshold  # default 0.4
)
```

archive の `positive_fold_ratio_effective` 列を読み、 threshold 比較。 pfre = NaN または不在の場合は False (Stage A 不通過の保守的扱い)。

### threshold = 0.4 の根拠

- Stage B 通過閾値 `positive_fold_ratio_min=0.6` の 67%
- 中間ヘッドルーム (過厳格回避)
- run-36 後期 Stage A 上位 20% 群 pfre_mean 0.296 → 全員 fold_robust=0
- 0.4 を超えるには真の WF robustness が必要 → GA 探索圧シフト

### 変更ファイル
- `scripts/alpha_factory/run_ga.py`: IndividualCacheEntry / selection_score / _archive_row_to_cache_entry
- `src/alpha_factory/config.py`: StageGateConfig.fold_robust_threshold = 0.4
- 新規 tests: 7 件

### 既存 _selection_key 経路 (変更なしで利用)
```python
# run_ga.py 既存実装
def _tournament(pop, cache, rng, k, feasibility_cfg) -> Genome:
    sample = rng.sample(pop, k=min(k, len(pop)))
    fallback = _is_all_infeasible(cache.values(), feasibility_cfg)
    return max(sample, key=lambda g: _selection_key(cache[g.name], fallback))

# elite 選抜も同じ _selection_key を使用
sorted_pop = sorted(prev_pop, key=lambda g: _selection_key(cache[g.name], fallback), reverse=True)
elites = sorted_pop[:elite_count]
```

→ selection_score への 1 要素追加で tournament + elite 両方が fold_robust を考慮するようになる。

## レビュー観点

### 質問

1. **設計妥当性**: 当初の fitness_pen 改修案より selection_score 拡張案の方が望ましいか? (実装経路がシンプル、 副作用範囲が局所的)
2. **fold_robust の binary 化**: gradient (penalty 累積) ではなく boolean で十分か? lexicographic order で fold_robust=1 群が常に fold_robust=0 群より上位に来るのは望ましい挙動か?
3. **threshold 0.4 の妥当性**: Stage B 閾値 0.6 の 67%、 中間ヘッドルームとして適切か?
4. **legacy_selection_score 不変**: fallback (cache 全体 infeasible) 時は legacy 4-tuple が使われる、 そこに fold_robust を入れない判断は妥当か?
5. **テスト網羅性**: 7 件で十分か? 統合テスト (run_ga 経由で次世代の population が fold_robust=1 個体に偏る) も必要か?
