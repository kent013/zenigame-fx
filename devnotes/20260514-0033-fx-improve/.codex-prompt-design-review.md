## 詳細設計 (要点)

### C1 [Critical] live_criteria.sharpe 単位整合性修正

**変更**: `scripts/alpha_factory/run_ga.py:916` `_check_live_criteria`

- 引数 `holdout_days: int` 追加 (= caller `cfg.stage_gate.stage_c_holdout_days` 渡す)
- sharpe 比較値の優先順位:
  1. `trade_sharpe_stage_c` (Stage C scope、 第一優先)
  2. `trade_sharpe_raw` (Stage A scope、 fallback)
- `_annualize_trade_sharpe(sharpe_trade_level, trade_count, holdout_days)` で年率化
- `checks["sharpe"]`:
  - `value` = annualized 値 (SSOT)
  - `value_trade_level` = trade-level 値 (併記)
  - `threshold` = sharpe_min (1.0)
  - `pass` = annualized >= sharpe_min
  - `sharpe_calc_version` = `v2_trade_level_annualized`
  - `sharpe_source` = `trade_sharpe_stage_c` or `trade_sharpe_raw`
  - `holdout_days` = 60

**caller 更新**: `run_ga.py:1015` で `_check_live_criteria(best_row, cfg.live_criteria, holdout_days=cfg.stage_gate.stage_c_holdout_days)`

**テスト**: 8 件新規 (annualize 適用、 trade_sharpe_stage_c 優先、 raw fallback、 None 処理、 value/value_trade_level 併記、 v1 archive skip、 holdout_days 伝搬等)

**root 課題**: Stage C 内部判定 (`stage_gate.py:1902`) は annualize 比較しているのに、 `_check_live_criteria` は trade-level 比較 → 二重基準による不整合。 修正で Run 75 best g60_i46 の live_criteria.sharpe.pass=False → True に変わる (Codex 実測 annualized 2.69 >= 1.0)。

## 質問

### Q1. C1 実装方針

`_annualize_trade_sharpe` の import 経路:
```python
from src.alpha_factory.stage_gate import _annualize_trade_sharpe
```
これは scripts → src への依存だが、 run_ga.py 内に既に多数の src.alpha_factory.* import あり → 整合か?

### Q2. C1 sharpe_source の fallback 順序

`trade_sharpe_stage_c` 第一優先で `trade_sharpe_raw` fallback だが、 archive 列に `trade_sharpe_stage_c` を持つのは Stage C 評価された個体のみ。 Stage A 通過のみ (= Stage C 未評価) の個体は `trade_sharpe_raw` を使う。 この設計で OK か?

**懸念点**: Stage A 通過のみの個体に対して `trade_sharpe_raw` (= Stage A scope) で annualize すると、 `holdout_days=60` でなく `stage_a_window_days=60` 相当が正しい? それとも live_criteria は Stage C を前提とした metric だから fallback 経路は使われない設計か?

### Q3. C1 既存テストへの影響

`_check_live_criteria(row, criteria)` の 2 引数 signature が `_check_live_criteria(row, criteria, holdout_days)` の 3 引数に変わるため、 既存テストで 2 引数呼び出し箇所 (テスト含む) は全て更新必要。 既存テストの数を確認すべきか?

### Q4. C3 retroactive script 配置

scripts/alpha_factory/ に新規 script を置く。 既存の `audit_run_post.py` (cycle 13 で導入された軽量 DSR audit) と機能が近いが、 統合すべきか別 script で進めるか?

### Q5. C4 report への影響

`generate_run_report.py` の出力テンプレが変わる → 既存 run-N.md (74 件) との backward 互換性は? (= テストで run-N.md 形式 assertion している箇所はあるか確認必要)

### Q6. mission_candidate_count の意味整合

過去 19 RUN retroactive 再評価で mission_candidate_count >> 0 が出てきた場合 (= 実は mission 達成個体多数)、 GA selection / archive 集計には影響なしか? それとも別の経路で「再評価結果に基づく selection 修正」が必要か?
