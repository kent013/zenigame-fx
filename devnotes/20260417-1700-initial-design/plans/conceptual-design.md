## 1. 目的

**最終目的**: 短中期の為替変動を捉え、検証可能な取引ルールに基づく自動売買で継続的に利益を獲得する。

**短期目標**: zenigame を参考に、FX 取引を実行する仕組みの**骨格**を構築する。MVP として「1 通貨ペアの価格取得 → シグナル生成 → 擬似発注 → 損益記録」が一気通貫で走る状態を目指す。

**非目標（現段階）**:
- 戦略の最適化・多銘柄展開・多戦略アンサンブル
- 実ブローカーへのライブ発注
- Web UI / 可視化層

MVP が動いてから上に積む。zenigame が 4 年かけて積み上げた構造を最初から写経しない。

## 2. zenigame との構造的差異

zenigame の設計をそのまま移植できない箇所を先に明確化する。

| 観点 | zenigame（日本株） | zenigame-fx（FX） |
|------|-------------------|-------------------|
| 市場時間 | 9:00-15:30 JST、営業日カレンダー依存 | 日曜夕〜金曜夕の 24/5、祝日ほぼ無関係 |
| ユニバース | 4000+ 銘柄、上場/廃止で変動 | 主要 7 通貨 + クロス、ほぼ固定 |
| データ粒度 | 日次 OHLCV が主 | tick / 1m / 5m / 1h / 1d、**bid/ask スプレッド必須** |
| データソース | J-Quants（有料・正規化済み） | OANDA / Dukascopy / Alpha Vantage / MT5 / ブローカー直 |
| ニュース | 銘柄紐付き記事（マイナビ、日経）+ 開示（EDINET） | マクロ中心（中銀、CPI、雇用統計、地政学）。銘柄固有ニュースは存在しない |
| 取引単位 | 100 株単位、現物 / 信用 | 基本単位 1000/10000 通貨、レバレッジ必須、スワップ（ロールオーバー金利）発生 |
| コストモデル | 手数料 + 板スプレッド | スプレッド（bid/ask 差）+ スワップ。手数料は 0 が多い |
| リスク | オーバーナイト GAP、決算ギャップ | GAP は週末のみ、**レバレッジによる強制ロスカットが支配的** |
| カレンダー | `TradingCalendar` テーブル | サマータイム遷移・主要祝日のみ注意。「営業時間帯」概念が連続 |
| セッション流動性 | 取引時間内は概ね一定 | 東京・ロンドン・NY セッションで流動性が大きく異なる。バックテスト評価・シグナル設計に影響する |
| スリッページ | 板状況・約定速度依存 | 経済指標発表時に急変動スリッページが発生。MVP では**固定スプレッドのみ・スリッページなし**と割り切る |
| ロスカット | 信用取引の追証（任意対応） | **証拠金維持率**が閾値を下回ると強制ロスカット。レバレッジが高いほど距離が短くなる。シミュレーションでのモデル化が必須 |
| ロールオーバー時刻 | 翌営業日（カレンダー制御） | 通常 22:00 or 00:00 NY 時間にスワップ付与。業者により異なる。バックテストのスワップ計算に影響する |

**帰結**:
- zenigame の `TradingCalendar` / `DailyPrice` / `Security` モデルは**そのままでは使えない**。FX では `CurrencyPair` / `PriceBar`（bid/ask 含む）/ `SessionWindow` 相当が必要。
- ニュース評価層（`news_eval`）は FX では**マクロイベント評価層**として再設計する必要がある。初期は対象外でよい。
- Alpha Factory（GA×NSGA-II のシグナル探索）の思想は転用可能だが、プリミティブ層は FX 特有の指標（キャリー、金利差、実効レート、COT レポート等）で再定義が必要。
- **タイムゾーン注意**: OANDA 等の FX データは UTC で提供される。NY サマータイム切り替え時期（3 月・11 月）に JST 換算が 1 時間ズレる。バックテストで「何時のシグナルか」の解釈に影響するため、UTC で統一管理する。
- **週末ギャップ方針（MVP）**: 金曜夜クローズ〜日曜夜オープンのギャップはMVPでは**週末ポジションを禁止（金曜終盤に強制クローズ）**として割り切る。週をまたぐスワップ計算と組み合わせた複雑なモデル化は Phase 4 以降に先送り。

## 3. システム構成ブロック（提案）

zenigame の 8 ブロック構造（`concepts/grand.md`）を FX 向けに再編成する。

### A. データ取得・保存

1. **ブローカー/データ API クライアント層** — bid/ask 含む価格、経済指標カレンダー、スワップレートを取得。キャッシュ（diskcache 想定、zenigame と同じ）で重複取得を排除。
2. **価格データ層** — `price_bars`（tick または m1 ベース）を DB 化。bid/ask 分離保存。
3. **通貨ペアマスタ層** — `currency_pair` テーブル（ベース通貨、クォート通貨、pip サイズ、取引単位、スワップ参照元）。
4. **経済指標カレンダー層** — `economic_events`（発表時刻、重要度、予想値、実績値）。マクロ分析の基礎データ。

### B. 分析・予測・評価

5. **シグナル生成層** — テクニカル系・金利差系・イベント駆動系を分離。zenigame の Alpha Factory に相当するが、MVP では**単一の手書き戦略**から始める（GA は Phase 3 以降）。
6. **バックテスト層** — スプレッド・スワップ込みの擬似執行で PnL を算出。zenigame の `backtest/` を参考にしつつ、FX 特有（スプレッド時間変動、レバレッジ、強制ロスカット）を正しく扱う。**設計方針: バックテストも BrokerGateway Protocol を通す**ことで Phase 3 の Paper Trading（MockBroker）と同じ抽象化層を共有し、コスト計算ロジックの重複を避ける。
7. **評価層** — 勝率・Sharpe・MaxDD・プロフィットファクター・ロット効率。tick sensitive な指標が多いので tick データ取得の価値が高い。

### C. 売買実行

8. **Paper Trading → Live Trading** — zenigame の `paper_trading/` の `BrokerGateway` Protocol 抽象化は**そのまま流用する価値が高い**。MockBroker → 実ブローカー（OANDA v20 API / MT5 / 国内 FX 業者 API）の差し替えで移行できる。MockBroker には**証拠金維持率チェック（MVP: 固定維持率閾値割れで強制クローズ）**を最初から組み込む。具体的な閾値は Phase 2 の詳細設計で決定する。

### D. 可視化（Phase5 以降）

9. **運用ダッシュボード** — PnL、保有、シグナル履歴。MVP では対象外。

## 4. 主要な未確定決定

以下は次フェーズで確定させる。

### 4.1 データソース

**候補比較**:

| ソース | ヒストリカル | リアルタイム | tick | コスト | 備考 |
|-------|-------------|-------------|------|-------|------|
| OANDA v20 API | ◯（年単位） | ◯ | ◯ | 口座開設のみ | 最有力。Python SDK あり |
| Dukascopy | ◎（20年+） | △ | ◎ | 無料 | tick まで取れるが API が癖あり |
| Alpha Vantage | △（日次中心） | ◯ | × | 無料（レート制限） | MVP には弱い |
| MetaTrader5 | ブローカー依存 | ◯ | ◯ | 業者次第 | Python ラッパー `MetaTrader5` あり、Windows 依存 |
| 国内 FX 業者（SBI、GMO 等） | ブローカー依存 | ◯ | △ | 口座依存 | API 提供社は限定的 |

**推奨初期選択**: OANDA v20（demo 口座）をヒストリカル・リアルタイム両対応として採用。Dukascopy は tick バックテスト用に補完。**確定は別設計文書で行う**。

### 4.2 初期対象通貨ペア

MVP は **1 ペア** に絞る。候補:
- **USD/JPY** — 流動性最大、スプレッド狭、日本人トレーダーに情報豊富。**最有力**。
- EUR/USD — 世界的流動性最大だが日本時間外のボラが主。
- GBP/JPY — ボラ大きく検証しやすいがリスクも大。

**推奨**: USD/JPY から開始。Phase 4 以降で EUR/USD 追加（Phase 2 はバックテスト基盤構築のため通貨ペア拡張は先送り）。

### 4.3 データ粒度

- MVP: **1分足（m1）** を主データとする（tick は Phase 2 以降）。
- 理由: tick は保存容量・処理負荷ともに MVP に過剰。m1 + bid/ask なら OANDA/Dukascopy いずれでも扱える。

### 4.4 ブローカー（Live 段階）

MVP は MockBroker のみ。Live は Phase 5 の議題。国内業者の API 事情を別途調査する。

## 5. 実装フェーズ（提案）

zenigame の Phase1-5 を FX 向けに再構成。

### Phase 0: 骨格構築（← 次のアクション）
- `pyproject.toml` / `uv` 初期化
- ディレクトリ骨格（`src/` `scripts/` `tests/` `docs/` `devnotes/`、`.env.example`）
- 最小 PostgreSQL 起動（docker-compose）
- Alembic 初期化
- ruff 設定

### Phase 1: データ取得（1ペア m1）
- OANDA v20 クライアント（価格取得のみ、認証は demo 口座）
- `currency_pair` / `price_bar_m1` テーブル（bid/ask 含む）
- キャッシュ層（diskcache）
- ヒストリカル取得スクリプト（1 年分）
- リアルタイム取得スクリプト（polling で可）

### Phase 2: バックテスト基盤
- 単一シンプル戦略（例: ボリンジャーバンド逆張り）— **デイトレ前提（週またぎポジション禁止）**
- スプレッド・スワップを考慮した擬似執行エンジン（BrokerGateway 経由。固定スプレッド・スリッページなし・証拠金維持率チェックを MVP 割り切りとして明示）
- PnL / 勝率 / MaxDD 計算
- **コスト計算の整合性確認**: 手動計算ケースと PnL が一致することをテストで検証
- レポート出力（md 形式）

### Phase 3: Paper Trading 基盤
- zenigame の `BrokerGateway` Protocol を参考に抽象化（Phase 2 のバックテストエンジンと共通化）
- MockBroker 実装（証拠金維持率による強制ロスカット、スワップ計算、週末ポジション禁止を含む）
- 1 分足 polling で「価格取得 → シグナル → 擬似発注 → 決済」を回す。**polling 方式は実運用と遅延差があることを許容する（MVP 割り切り）**。WebSocket 接続は Phase 4 以降の検討事項とする
- シグナル発生根拠・発注内容・決済内容をログに記録（監査証跡の最小限実装）
- **停止コマンド**: Paper Trading 段階からプロセスを安全に停止できるコマンドを持つ（Live 移行準備）
- ここで**短期目標達成**とみなせる状態

### Phase 4: 改善ループ
- 複数戦略の評価
- Alpha Factory 相当の GA 探索（zenigame の実装を参考に FX 版プリミティブで再構築）
- 経済指標カレンダー連携

### Phase 5: Live Trading
- 実ブローカー接続
- リスクガード（レバレッジ、DD キャップ、強制停止）
- 監視・アラート

## 6. MVP（短期目標）の完了判定

短期目標「FX 取引の仕組みの骨格実装」は、**Phase 3 完了時点** をもって達成とする。具体的には:

- USD/JPY の m1 価格が OANDA demo 口座から **1 分間隔（polling）** で取得され DB に保存される（取得成功率 > 99%、欠損時はリトライログが残る）
- **バックテストのコスト計算整合性**: スプレッド・スワップの手動計算値と PnL が一致するユニットテストが通る
- 単一戦略が Paper Trading 環境で **1 週間以上エラー無く稼働**する（プロセス異常終了ゼロ）
- 「シグナル → 発注 → 決済 → PnL 記録」のフローが完結する（シグナル発生理由もログに残る）
- PnL ログが md レポートとして **毎日** 出力される

完了時、次のアクションとして Phase 4（改善）に進むか Phase 5（Live 準備）に進むかを再評価する。
