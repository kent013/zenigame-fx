## 概念設計

# 概念設計: GA 並列ワーカーのメモリ過剰使用の改善

## 背景・課題

### 観察事実 (Fact)

- `config/alpha_factory/default.yaml` の `ga.max_workers` は 2。コメントの想定は「1 worker ~400MB × 2 + main ≈ 1.2GB」。
- `src/alpha_factory/config.py:152` / `scripts/alpha_factory/run_ga.py:1348` も同じ「1 worker ~400MB」前提で `_check_memory_budget` の推奨値式 (`worker_budget_mb // 400`) を組んでいる。
- 一方、本スキルの Codex レビュー env note は「24GB × 6 ワーカー（1 ワーカー最大約 3GB）」と記載。コードベース内で per-worker メモリ前提が 400MB / 3GB と分裂している。
- 実測 `summary.json` → `max_rss_mb_per_worker`（直近 10 Run, run-70〜run-79）: 5,562〜8,718 MB。run-76 が最大 8,718 MB。
- 想定 (400MB) と実測 (5.5〜8.7GB) の乖離は約 14〜22 倍。2 worker + main で実効 15〜20GB、24GB マシンで swap 寸前。
- `run-79.md` の dataset: EUR_JPY M1 bars `bars=328883`、`bars_holdout=60232`、population=96 / generations=60。

### 構造的観察 (Fact)

- `src/domain/price.py`: `PriceBar` は frozen dataclass だが `__slots__` 無し。1 bar が保持するのは `pair_name:str` / `bar_time:datetime` / `bid:Ohlc` / `ask:Ohlc` / `volume:int` / `complete:bool`。`Ohlc` も `__slots__` 無し frozen dataclass で `Decimal` を 4 個保持。1 PriceBar = 親 1 + datetime 1 + Ohlc 2 + Decimal 8 ≈ Python オブジェクト 12 個。CPython の Decimal は 1 個 ≈ 104 byte と重い。
- `src/alpha_factory/parallel_eval.py:566-577`: `multiprocessing.get_context("spawn")` の `Pool` を使い、`_init_worker` の `initargs` で `lane_contexts`（各 lane の `bars_a` / `bars_b` / `bars_holdout` のフル tuple + `aux_bundle`）を worker ごとに pickle で完全コピーして配布。spawn なので fork の copy-on-write 共有は効かない。
- `aux_bundle`（`AuxBundle`）は `aux_pair_bars_index: dict[str, dict[datetime, PriceBar]]` を持ち、cross-pair 用ペア（EUR_USD / USD_JPY 等）の M1 bar を `PriceBar` の dict として保持する。`evaluate_stage_b` には raw `aux_bundle` がそのまま渡され fold ごとに再 align される。
- `parallel_eval.py:230` の `_PROC_AUX_CACHE: dict[int, AuxAlignmentCache]` は process-local。内側 `AuxAlignmentCache._cache` は `id(bars)` キーで `AlignedAuxBundle`（`aux_series` の np.ndarray + `aux_pair_bars` の `list[PriceBar|None]`）をキャッシュする。`_reset_proc_aux_cache()` は定義されているが RUN 中に呼ばれる経路が無い（worker は Pool 寿命 = RUN 全体で生存）。
- 比較対象: 姉妹プロジェクト zenigame の `src/trading/alpha_factory/evaluation/shared_bar_store.py` は分足を SoA numpy 配列で 50 byte/bar の mmap ファイルに連続配置し、全 worker が read-only attach（ゼロコピー共有）。`parallel_eval.py` 側に動的ヘッドルーム計算・メモリ容量チェックも実装済み。

### 仮説 (Interpretation)

GA worker のメモリ肥大の構造的根因は次の 2 つの掛け算と推定する:

1. bar 表現の低メモリ密度: `PriceBar`（Decimal×8 / `__slots__` 無し）は zenigame の SoA 50 byte/bar に対し推定 20〜30 倍重い。
2. spawn による無共有複製: bars / aux を worker 数だけフルコピーし、RUN 中ずっと保持する。さらに `_PROC_AUX_CACHE` が stage / fold ごとの整列結果を RUN 寿命で単調蓄積している可能性がある。

ただし「実測 7GB のうち各要素が何 GB を占めるか」は未計測であり、現時点では INCONCLUSIVE。値を弄る前に内訳を確定させる。

## 改善アイデア

「重い表現 × 無共有複製 × 寿命蓄積」を、計測で内訳を確定 → 効果の大きいレバーから順に適用する 2 段構成で解消する。いきなり大規模なアーキテクチャ改修には踏み込まない。

### Phase 0: メモリ内訳の計測（必須・先行）

worker プロセスの RSS を構成要素別に分解する計測を入れ、1 Run（短縮 generations 可）で内訳表を得る:

- 計測ポイント: `_init_worker` 直後 / Stage A 評価後 / Stage B 評価後（fold 蓄積後）/ Stage C 評価後 / 世代境界。
- 分解対象: ① target pair bars（`bars_a/b/holdout`）② `aux_bundle`（特に `aux_pair_bars_index`）③ `_PROC_AUX_CACHE` ④ backtest engine の作業セット ⑤ その他。
- 手段は `tracemalloc` スナップショット差分、または主要コンテナの実サイズ集計（`sys.getsizeof` 再帰）。決定論を壊さない・既存ロジックを変えない計測専用コードとし、環境変数または CLI フラグで opt-in。
- 成果物: 内訳表（要素 × 計測ポイント の MB）。これが Phase 1 のレバー選択の根拠になる。

### Phase 1: 内訳に応じた構造レバー（Phase 0 結果でゲート）

Phase 0 の内訳に応じて、以下から必要なものを選択適用する。各レバーは独立に効果検証可能:

- レバー A — `_PROC_AUX_CACHE` のライフサイクル管理: stage または世代境界で `_reset_proc_aux_cache()` を呼ぶ経路を追加し、RUN 寿命の単調蓄積を断つ。既存関数の呼び出し追加のみで低リスク。Phase 0 で `_PROC_AUX_CACHE` の蓄積が支配的なら、これ単独で大きく効く可能性。
- レバー B — bar 表現の軽量化: `PriceBar` / `Ohlc` に `__slots__` を付与し `__dict__` を除去。値型（Decimal）の見直しは別途要検討だが、`__slots__` 付与だけでも 1 bar あたり Python オブジェクト 3 個分の `__dict__` を削減できる。`PriceBar` は src/ 配下 36 ファイルで参照されるため外部 API（フィールド名・不変性・`spread_close`）は不変に保つ。
- レバー C — bars の worker 間共有: Phase 0 で「target/aux の bar フルコピーが支配的」かつ A・B で不足する場合のみ検討。候補は (c-1) spawn → fork 切替による copy-on-write 共有（macOS の fork 安全性・`ensure_registered()` 依存を要検証）、(c-2) zenigame の `SharedBarStore` 相当の mmap SoA 共有ストア導入。(c-2) は効果最大だが backtest engine が `list[PriceBar]` を消費する境界をどう保つかの設計が必要なため、Phase 0 の根拠なしには着手しない。

### per-worker メモリ前提の一本化（全 Phase 共通）

`config.py` / `default.yaml` / `run_ga.py` / 本スキルに散在する per-worker メモリ前提（400MB vs 3GB）を、Phase 0 実測値に基づき単一の根拠ある数値に統一し、`_check_memory_budget` の推奨値式と `default.yaml` の `@upper_bound` コメントを実態整合させる。

## 期待効果

- 直接効果: per-worker RSS の実測値を下げ、24GB マシンで swap せず安定動作。`max_workers` を実態根拠のある上限まで引き上げられるようにする。
- 使命への寄与（間接）: 本改善は live_criteria 指標を直接動かすものではない。寄与は「探索基盤の制約解除」である — (1) OOM / swap による RUN 中断・実行時間劣化のリスク除去、(2) AGENTS.md が目標とする複数通貨ペア（AUD_JPY / EUR_JPY / USD_JPY / EUR_USD / USD_CAD / USD_ZAR）への swim-lane 拡張は現状の 7-8GB/worker では物理的に不可能であり、その scaling 前提を作る、(3) population / generations を増やせる余地を生む。使命達成の必要条件ではないが、探索のスループットと安定性の enabler と位置づける。
- 計測（Phase 0）自体が「データに真摯に向き合え」の実践であり、以降のチューニングの判断基盤になる。

## 実装方針（概要）

| 対象コンポーネント | 変更概要 | Phase |
|---|---|---|
| `parallel_eval.py`（計測コード） | RSS 内訳計測の opt-in フック追加（決定論・既存ロジック不変） | 0 |
| `parallel_eval.py` `_PROC_AUX_CACHE` | stage/世代境界での `_reset_proc_aux_cache()` 呼び出し経路追加 | 1-A |
| `domain/price.py` `PriceBar` / `Ohlc` | `__slots__` 付与（外部 API 不変） | 1-B |
| `parallel_eval.py` Pool 生成 / bars 配布 | （Phase 0 でゲート）fork 切替 or mmap 共有ストア | 1-C |
| `config.py` / `default.yaml` / `run_ga.py` | per-worker メモリ前提の一本化・`_check_memory_budget` 式の実態整合 | 0→共通 |

## 制約・前提

- 決定論契約の維持: L1 selection / L2 row-order は worker 数・メモリ実装に依存しない契約（`parallel_eval.py` docstring）。計測コードも共有ストアも、この契約を壊さない。
- look-ahead bias 防止の維持: `aux_loader.align_to` の `bar.bar_time >= effective_from_utc` 契約、`AuxAlignmentCache` の整列ロジックは挙動不変に保つ。レバー A はキャッシュの破棄タイミングのみ変更し、整列結果の値は変えない。
- `PriceBar` 外部 API 不変: src/ 配下 36 ファイルが参照。フィールド名・frozen 性・`spread_close` プロパティを変えない。`__slots__` 付与は ABI 互換だが、動的属性付与に依存する箇所がないことを事前確認する。
- 段階性: Phase 0 の計測結果なしに Phase 1-C（大規模改修）へ進まない。「仕組みが機能していない段階で値を弄るな」。

## スコープ外

- backtest engine 全体の SoA 化（`list[PriceBar]` → numpy SoA への全面移行）。36 ファイル波及の大規模改修であり、本タスクでは扱わない（将来別タスク）。
- `Decimal` → `float` への値型変更（精度・約定計算の正しさに関わるため別途独立検討）。
- zenigame の動的ヘッドルーム計算・chunksize 自動調整の移植（zenigame-fx は単一 instrument 中心でデータ規模が異なるため、まず計測してから要否判断）。
- `max_workers` のデフォルト値そのものの変更（Phase 0 で実態根拠が出てから別途判断。本タスクは「前提の一本化」までで、値の決定は含めない）。
