## 背景

GA 並列 worker の per-worker RSS が実測 5.5〜8.7GB に肥大していた。ライブ RUN の worker を vmmap + 実測で調査した結果、root cause は **pymalloc アリーナの断片化**と確定した:
- worker RESIDENT 5.4GB のうちシステム malloc ゾーンは ~490MB のみ。残りは `VM_ALLOCATE` 7,241 領域 × 1024K = pymalloc アリーナ（CPython 3.11 はアリーナ 1MB）。
- `run_backtest` が genome × fold × 世代ごとに `equity_curve: list[tuple[datetime, Decimal]]` / `trades`（Decimal 多用）を大量 churn → ≤512byte 小オブジェクトが pymalloc アリーナを断片化。pymalloc はアリーナが 100% 空になるまで OS に返さない（再現テストで実証）。
- リーク（参照保持）ではなくアロケータ断片化。

## 本実装の方針

`multiprocessing.Pool` の `maxtasksperchild` を配線し、worker が一定タスク数を処理したらプロセスごと退役 → 新規 spawn でリサイクルさせる。退役時に断片化アリーナが OS に完全返却される。CPython 標準機能による低リスク緩和策。本丸（Decimal churn 削減そのもの）は別タスク。

詳細設計: `devnotes/20260514-2045-ga-worker-memory/detailed-design.md`（root cause 確定版）。必要なら Read で確認可。

## レビュー観点

1. **決定論契約 (L1/L2) の維持**: `maxtasksperchild` による worker リサイクルが selection determinism（fitness_pen / best_name / live_criteria_passed）と row-order determinism を壊さないか。退役 worker の `_init_worker` 再実行で状態が完全同一に復元されるか。`pool.map` の結果順序保証はリサイクル下でも有効か。
2. **パラメータ 4 段接続** (禁止事項 8): `yaml (max_tasks_per_child) → GAConfig → run_ga 実効値導出 → GenomeEvaluator → Pool` の全段が接続されているか。漏れがないか。
3. **エッジケース**: `max_workers=1`（pool is None）で `maxtasksperchild` が無視される経路は正しいか。`max_tasks_per_child=None`（既存挙動）が完全互換か。自動導出式 `max(1, (2*population_size)//max(1,max_workers))` の境界（population_size=1 等）。
4. **後方互換**: `GenomeEvaluator.__init__` の新 keyword-only 引数 / `GAConfig` の新フィールド / summary.json の `parallel_config.max_tasks_per_child` 追加が既存 consumer・既存テストを壊さないか。
5. **コードの正確性**: ロジックエラー、off-by-one、`_derive_max_tasks_per_child` の戻り値利用、summary 記録箇所での再導出の妥当性。
6. **テストの網羅性**: 追加テストが「リサイクル発生」「リサイクル下での決定論維持」を実際に検証できているか。
7. **spawn overhead リスク**: リサイクル時の initargs（`lane_contexts` = bars 実体含む）再 pickle コスト。自動導出値（約 2 世代ごと）は妥当か。
