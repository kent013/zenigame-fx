## 修正済み概念設計

# 概念設計: 無取引優位の遮断設計 (risk-no-trade-fitness-guard)

## 背景・課題

### Run 9 で観測された Verified な現象

- 全 120 行 (6 世代 x 20 個体) で stage_a_pass=0, stage_b_pass=0, stage_c_pass=0
- best 個体: g0_i1, selection_score=[0,0,0,0.0], trade_count=0
- archive 集計: trade_count=0 が 90 個体 (75%)、trade_count>0 が 30 個体
- trade_count>0 個体の sharpe は全て負 (min=-93.10, max=-4.76) → fitness_pen 大きく負
- trade_count=0 個体は archive 上で fitness_pen=0.0
- best_fitness は全 6 世代で 0.0 plateau

### Verified な因果列 (C4)

1. evaluate_stage_a で trade_count<1 の場合、reasons=("no_trades",) で fitness_pen=None のまま payload に格納される (src/alpha_factory/stage_gate.py:302-307)
2. archive collect_stage_a は payload を _required_float(default=0.0) で読み込むため、fitness_pen=None → 0.0 として archive 行に格納 (src/alpha_factory/archive.py:339)
3. run_ga._update_cache が archive 行から fitness_pen を float 化して IndividualCacheEntry.fitness_pen に格納 (scripts/alpha_factory/run_ga.py:456-467)
4. selection_score = (stage_c_pass, stage_b_pass, stage_a_pass, fitness_pen) の辞書式比較で、全員 stage_*_pass=0 の場面では fitness_pen が tie-break (scripts/alpha_factory/run_ga.py:110-118)
5. _tournament / elite sort / _select_best が全てこの selection_score を使うため、trade_count=0, fitness_pen=0.0 個体が trade_count>0, fitness_pen<0 個体に勝つ

### 構造的根本原因

evaluate_stage_a は no_trades reason を出すが、その fitness_pen は None → 0.0 として archive に正規化される。Stage 通過 bit が全員 0 の局面で fitness_pen tie-break が走ると、無取引個体が不当に survive する。これは禁止事項 #6 の構造的・自然発生バージョン。

## 改善アイデア

stage_a の no_trades (および min_exposure_trade_count 未達) 個体について、archive 行の fitness_pen を明示的に大きい負値 sentinel で書き込む。これにより GA selection_score の tie-break で取引する個体が必ず勝つ。

### 具体仕様

- StageGateConfig に min_exposure_trade_count: int = 1 追加 (不変条件: 0 < min_exposure_trade_count < live_criteria.trade_count_min を __post_init__ で強制)
- evaluate_stage_a 内で trade_count < min_exposure_trade_count の判定を行い、payload の fitness_pen に有限な大負値 sentinel を入れる (_NO_EXPOSURE_FITNESS = -1e9)
- _required_float 経路を変更しない (sentinel をきちんと payload に入れることで 0.0 fallback を回避)
- reason_codes に no_exposure を追加
- config/alpha_factory/default.yaml に stage_gate.min_exposure_trade_count を追加し、config.py の loader でも読み込む

### Sentinel 序列の明確化

system_failure (-1e12) < no_exposure (-1e9) < metric_unavailable / below_threshold (実値) < 通常 fitness_pen

意味: system が壊れた個体は取引が成立しなかった個体より厳しく罰する。

### 重要な設計原則

- live_criteria.trade_count_min の閾値は弄らない (禁止事項 #4)
- min_exposure_trade_count 初期値は 1
- fitness_raw は変更しない
- GA 選択ロジック (run_ga.py の selection_score 等) は触らない
- archive schema 変更は今回行わない

## 期待効果

### Verified な効果

- trade_count=0 個体の構造的優位を解消: selection_score tie-break で取引する個体が常に勝つ
- best 個体が trade_count=0 状態で plateau する現象の解消

### 仮説 (反証実験で要確認)

- 正 sharpe 個体の発生
- Stage A pass の改善
- max_drawdown 実測値の出現

### 反証設計

- 3-5 seed で best_no_trade_rate、stage_a_pass_count、trade_count=0 比率を比較
- 成功判定: best_no_trade_rate=0 かつ stage_a_pass_count > 0
- 仮説の追加検証: 正 sharpe 個体出現 / Stage B 到達は次サイクル以降の観察対象

  - 緩和策: 有限値 (-1e9) に統一、sentinel 序列を design doc に明記
