## 概念設計

# 概念設計: T058 — Schema v2 contract (dataset_epoch_id 全経路必須化)

## 背景・課題

zenigame-fx の selection cascade を big-bang baseline で全面再構築するにあたり、 **「epoch-rolling 24m dataset の epoch 識別子が複数経路で永続化される schema」** を最優先で確立する必要がある。

具体的な課題:

1. **既存 archive schema (GENOMES_SCHEMA in `src/alpha_factory/archive.py:54`) には `dataset_epoch_id` が無い**。 zenigame `genome_archive.py:540` も同様 (Round 19 で確認)。
2. **複数の永続化経路 (Parquet archive / calibrate-gate history JSONL / monitor / report / future warmstart filter) が `dataset_epoch_id` キーで scope 分離される必要がある**が、 全経路で必須化する仕組み (schema lint) が無い。
3. **後段 TODO (T059-T075) のすべてが Schema v2 contract に依存する**。 schema が確定しないと epoch manager / canonical 5 engine / archive admission ができない。
4. **禁止事項 8 (ゲノム archive スキーマ変更時の値伝搬漏れ) の最重要ポイント**。 `config → GaConfig → meta → consumer` の 4 段接続が全経路で揃わないと epoch 跨ぎ汚染が起きる (Round 17 検査 6)。

## 改善アイデア

`schema_version=2` を新設し、 以下 4 フィールドを全永続化経路で必須化する。 schema lint で fail-closed。 big-bang baseline のため schema_version=1 (既存) との migration なし、 v2 で空 archive から start。

新規必須フィールド:

| field | 型 | 意味 | 由来 |
|---|---|---|---|
| `schema_version` | int | 2 | スキーマ世代識別 |
| `dataset_epoch_id` | str | epoch-rolling 識別子 (例 `epoch_20260301_p1`) | T059 (Epoch Manager) で生成 |
| `archive_role` | enum | `mission_pass` / `progress_pass` / `score_bypass` | T066 (Archive admission) |
| `source_stage` | enum | `A` / `B` / `C-lite` / `C` | T063-T064 (Stage evaluator) |

対象経路:

1. Parquet archive (`src/alpha_factory/archive.py: GENOMES_SCHEMA`)
2. calibrate-gate history JSONL (`reports/calibrate-gate/history.jsonl`)
3. warmstart filter (T067 で実装)
4. monitor / report 出力 (`reports/run-reports/run-{N}/summary.json` 等)
5. audit report (T073 DSR/PBO/SPA scaffold)

### Schema lint 仕様

- 書き込み時: 必須 4 field 欠落 → `SchemaContractError` raise (fail-closed)
- 読み込み時: schema_version=1 の archive を発見 → `SchemaVersionError` raise (旧 archive は読まない)
- lint 関数を `src/alpha_factory/schema_contract.py` (新規) に集約

## 期待効果

### live_criteria 達成への貢献 (間接)

- epoch 跨ぎ汚染防止: 過去 epoch の archive entry が新 epoch の warmstart で誤注入される事故を fail-closed で防ぐ
- archive admission の意図保持: archive_role で mission_pass / progress_pass / score_bypass を区別、 後段 observability で archive 質低下兆候を検出可能
- stage 由来の identify: source_stage で Stage C-lite と C の通過個体を区別、 graduation lane や mission_pass 判定が誤らない

## 質問事項

以下を [Critical] [Warning] [Suggestion] で診断してほしい:

1. **schema lint の配置**: 各 write 関数冒頭で `assert_v2_schema()` 呼び出し、 read 関数冒頭で `assert_v2_schema_version()` 呼び出し。 これで full coverage か (見落とし経路は?)
2. **enum 値の文字列化**: ArchiveRole / SourceStage を StrEnum で文字列値として archive に書く。 後方互換性なし (big-bang) 前提で問題ないか
3. **dataset_epoch_id の format**: 仕様未定 (T059 担当)。 本 TODO で string 型のみ確定、 format 制約なしで良いか
4. **calibrate_state の scope key 変更**: 既存 `base_config_hash` から `base_config_hash + dataset_epoch_id` への変更。 旧 record は schema_version=1 のため自動排除されるが、 これは正しい挙動か
5. **schema lint の overhead**: 全 write 経路で lint 呼ぶことによる performance impact。 24GB / 6 ワーカー / 1 ワーカー 3GB の制約に収まるか
6. **見落とし経路**: 上記 5 経路 (Parquet / history JSONL / warmstart / monitor / audit) 以外に dataset_epoch_id を書く可能性のある経路があるか

これらに加えて、 設計の本質的な誤り / 禁止事項違反 / 反証可能な仮定があれば identify。
