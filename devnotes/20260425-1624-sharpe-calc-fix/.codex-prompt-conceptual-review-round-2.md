## 更新後の概念設計（Round 2 レビュー対象）

# 概念設計: Sharpe Ratio 計算の根本修正 (bar-level annualized → trade-level + threshold)

## 背景・課題

### 観察事実 (Fact, run-9 / run-10 横断)

- Run 10 best 個体: `trade_count=3`, `total_pnl=18860`, `sharpe=18.49`, `fitness=18.48`
- Run 9 では trade_count=0 個体が 75% を占め、Stage A 全滅
- 現実の戦略の年率 Sharpe は伝説的なファンドでも 2〜4 程度。Sharpe 18 という観測値は計算式の artifact の可能性が高い
- live_criteria は `sharpe_min=1.0` を要求 → 現状の Sharpe 計算ベースでは sharpe>=1.0 が事実上無意味化している

### コード側の前提検証 (C4)

```python
BARS_PER_YEAR_M1 = int(24 * 60 * 365 * 5 / 7)  # ≈ 375,428
# equity_curve は M1 全 bar（ポジ無し時間も含む）から生成
# √375428 ≈ 612.7 で annualize
```

14 日 backtest = 約 20,160 M1 bar。trade_count=3 個体では bar return の 99% 以上が 0 → i.i.d. 仮定崩壊。

**注意 (C8)**: 「Run 9-10 の探索結果がすべてハック個体」とは断定しない。H2 検証（後述）で replay し反証を探すことが先決。

## 採用する指標定義

**trade_sharpe_raw**（名称を `sharpe` ではなく専用名にして意味論の誤読を防ぐ）:
- return 単位 = `net_pnl_base_currency / equity_at_entry`（spread/swap/slippage 控除後 net pnl ÷ entry 直前口座 equity）
- `trade_sharpe_raw = mean(trade_returns) / std(trade_returns)`（annualize なし）
- annualize しない理由: GA fitness 比較には相対順序が重要なため選抜は機能する。短期バックテストでは trades_per_year 推定も不安定
- 業界標準との乖離: live_criteria の閾値は `trade_sharpe_raw` ベースの値に別途再校正が必要（Phase 1B）

### dispatch matrix

| 条件 | trade_sharpe_raw |
|---|---|
| `trade_count < trade_count_min_for_sharpe` (default 30, config 化) | `None` |
| std(trade_returns) == 0 | `None` |
| else | mean / std |

N_MIN=30 の根拠: Andrew W. Lo, 2002 *The Statistics of Sharpe Ratios* が示す推定の不安定性と経験則を参照。ただし arbitrary な面もあるため config 化し、Phase 1B で N=20/30/50 感度分析を実施。

### cross-pair の None 処理

per-pair `trade_sharpe_raw=None` → cross-pair 集計で fail-fast（skip 扱い禁止）。

## 後方互換
