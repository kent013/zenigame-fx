# 議論する論点 (fresh)

## 論点 A: 計算リソース・規模の最適選択

zenigame は pop=192 / gen=60 / max_workers=9 で 1 cycle 30-60 分。 fx で:
- pop, gen, max_workers の組合せをどう決めるか
- 制約: ハードウェア (max_workers の物理上限)、 1 Run wall-time の許容上限 (overnight 可能なら数時間 OK)
- Pareto front rank 1 サイズ確保のため pop は十分大きく必要 (curse of dimensionality)
- 統計検出力のため gen は十分長く必要
- swim_lane.tier1 で 6 lane を並列 or 順次運用するなら、 lane あたり pop が更に変わる

**fresh に最適な (pop, gen, max_workers, lane 並列度) を提案。 zenigame T509 の経験を参考に、 fx 単一通貨 × M1 24/7 の compute profile で再評価。**

## 論点 B: dataset 期間と fold 構造

DB に 3 年分。 選択肢:
- 24 ヶ月 / 35 ヶ月 / sliding window rotation
- fold 構造 (train days / embargo days / test days / step days)
- Stage A 評価期間、 Stage C holdout 期間、 C-lite 3 windows 配置

論点:
- PBO/DSR/SPA の selection inflation vs Lo (2002) Sharpe SE の sample size 要件のトレードオフ
- intraday FX の regime 持続時間 (週単位 / 月単位) と fold 期間の整合
- swim_lane graduation lane 移行を考慮した設計

**fresh に最適な (dataset 期間 / fold 構造 / Stage 期間) を提案。**

## 論点 C: canonical 5 の指標構成

zenigame canonical 5 = `sharpe / net_return / max_dd / trade_count / win_rate`

fx での選択:
- (α) zenigame 完全一致 (graduation lane Phase 4 で win_rate が pair-level 勝率として意味を取り戻す)
- (β) win_rate を profit_factor (or expectancy or 別) に置換
- (γ) canonical 4 にして 5 番目を tie-break / monitor

graduation lane Phase 4 で win_rate の意味が変わる影響:
- tier1 lane (現状): 個別 trade 勝率
- graduation lane: pair-level 勝率 (= zenigame の universe-level)

**fresh に最適な canonical 5 を提案。 graduation lane Phase 4 整合と現 tier1 運用の両立**

## 論点 D: 多目的 GA の構造選択

zenigame T509 = NSGA-II + Cascade-PPS-2Archive (CPPS) で:
- Pareto 軸 (net, dd, margin_inf) 3 軸
- CA + DA Two-Archive (進化母集団 + 外部 archive 両方)
- Push/Pull FSM (探索/収束 自動切替)
- exec_floor (warmup→ramp→hard、 fx では論点 C 由来で対象消失)

fx での選択:
- (a) NSGA-II + CPPS フル採用 (⑥ exec_floor 除く) = zenigame と思想一致
- (b) NSGA-II + 部分 CPPS (Pareto 軸変更のみ、 Two-Archive なし)
- (c) NSGA-III (4+ 軸を直接扱う、 reference points)
- (d) 単目的 margin_inf + crowding
- (e) 別 MOEA (MOEA/D, SMS-EMOA 等)

**fresh に最適な構造を提案。 fx の規模 (論点 A 結論) で各案の量的根拠 (Pareto front size, diversity entropy, feasible discovery rate) を比較**

## 論点 E: Sieve→Archive→Warmstart Loop の量的設計

Loop 構造はカスケード 7 段で固定 (確定事項)。 量的 hyper-parameter を fresh 決定:
- archive total size (CA + DA)
- target_inflow / Run、 per_run_max
- warmstart_share、 内訳 (CA : DA 比率)
- max_per_source_run、 max_per_session_pattern、 max_family
- max_reuse、 cooldown、 rolling window
- score_bypass K の動的式
- eviction_score の加重

**論点 A 結論 (pop, gen) と整合する量的 hyper-parameter を提案。 zenigame の比率 (sieve_share=0.33, max_family=2, K_SEED_MIN=8 等) を参考に、 fx 単一通貨ペア + multi-pair shadow 構成で最適化**

## 論点 F: P2 difficulty 軸の数

session_bucket 3 が P2 主軸 (確定事項) だが、 拡張余地:
- (i) session 3 のみ
- (ii) session 3 × volatility 2 = 6 bucket
- (iii) session 3 + aux factor regime

論点 A 結論 (pop, gen) で各 bucket あたりサンプル数が決まる。 統計検出力で P2 軸数の上限を量的に決める。

**fresh に P2 軸数を提案**

## 論点 G: 適用順序

論点 A〜F の確定後、 実装 Phase の順序を fresh に提案。 dataset 取得 (DB に 3 年分済) は no-op、 思想 docs (selection-cascade-design.md fx 用) 新設、 helper 群、 Stage 再実装、 GA 系統再実装、 Archive Loop 実装、 統合観測。
