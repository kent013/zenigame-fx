### 反論 2: warmstart 量と CA/DA 内訳

Round 11 の warmstart_share=20% は pop=256 で 51 体。 pop=192 なら 38 体。 zenigame の sieve_share=0.33 (pop=192 で 64 体) より少ない。

選択肢:
- (i) warmstart_share=20% (= 38 体)、 zenigame より少ない fresh seed 比率高め
- (ii) warmstart_share=33% (= 64 体、 zenigame と同等)
- (iii) warmstart_share=25% (= 48 体、 中庸)

CA:DA 内訳も pop に応じて調整:
- 通常: CA 比率 60-70%、 DA 残り
- emergency (mission=0 連続): CA 50%、 DA 50% (探索回復)

### 反論 3: target_inflow と per_run_max の比率

Round 11: target_inflow=10 (= 0.04×pop=256)、 per_run_max=16 (= 0.06×pop=256)

pop=192 で同比率: target_inflow=8、 per_run_max=12

論点:
- archive=120, target_inflow=8 → **15 Run で archive 全更新** (記憶半減期 ≈ 15 Run)
- per_run_max=12 → 単一 Run の支配比率 10%

zenigame は archive=100, sieve_inflow ~= 15 (推測) → 7 Run で全更新 (短い循環)。 fx で長めの循環は selection inflation に弱いか。

### 反論 4: score_bypass K の動的式

Round 11: `K = clamp(target_inflow - n_mission - n_progress, 2, 4)` (target=10 前提)、 emergency で K=12

pop=192 で target_inflow=8 なら:
- `K = clamp(8 - n_mission - n_progress, 2, 4)`
- mission=0, progress=0 なら K=4 (= 8-0-0 clamp 4)、 archive に 4 だけ流入
- archive total 120 だと、 4 体 / Run × 30 Run で 120 体 (極端ケース)

emergency 値: `K = clamp(12 - n_mission - n_progress, 4, 6)` 等?

## 論点 F: P2 軸数

### Round 11 提案: session 3 bucket のみ、 vol/aux は monitor 降格

### 反論 5: pop=192 / gen=64 で 6 bucket 解禁条件

Round 11 の 6 bucket 解禁条件: 「Stage B median trades_per_bucket >= 30、 C-lite >= 50、 front-1 >= 48、 session entropy >= 0.8」

これらは pop=256 前提の数字。 pop=192 で再校正必要。

論点 12 確定の sample 計算:
- Stage B pooled (5 fold × 5w test): 125 blocks/bucket (3 bucket、 1 block = 1 営業日)
- C-lite (6w × 3 disjoint): 30 blocks/bucket (single window)
- C (12w contiguous): 60 blocks/bucket

6 bucket 化なら半減: B pooled 62 / C-lite 15 / C 30。 C-lite 15 は C7 (n<30) 違反。 → **6 bucket は C-lite で疎化、 採用不可**。

session 3 bucket 維持で確定。

### 反論 6: aux factor regime を別 layer で監視

session_bucket は selection 圧 (主軸)。 vol/aux は monitor だが、 monitor として archive に何を記録するか:

- (a) archive entry に各 individual の `vol_regime_pass_pattern`、 `aux_factor_pattern` を保持、 eviction で diversity 軸として使う
- (b) monitor のみで archive には記録しない (purely diagnostic)

Codex Round 11 の役割マトリクスでは archive metadata で persist。 (a) 採用。

### 反論 7: cross_pair_pass_tag の運用

Round 11 で cross-pair shadow = validation + archive metadata 確定。 ただし具体的に:

- (i) cross_pair_pass = (mean_sharpe_cross >= 0.15 AND min_sharpe_cross >= -0.20) の binary tag
- (ii) cross_pair_robustness_score (= スカラー、 5 通貨での Sharpe 平均/min/std から合成) で連続値
- (iii) per-pair tag (5 通貨それぞれの pass/fail)

eviction CA で `shadow_robustness` に使うので連続値 (ii) が良い。 ただし計算複雑度を下げるなら (i) binary でも可。
