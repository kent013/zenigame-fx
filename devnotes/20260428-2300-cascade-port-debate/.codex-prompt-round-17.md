## Round 17 で検査する cross-cutting 論点

### 検査 1: gate (canonical 5 worst) と search (Pareto 3 軸) の relationship

確認:
- gate fail (canonical 5 worst > 0) でも search 圧 (Pareto 3 軸) で個体は selection 残存可
- mission_inf_gap (Pareto 3 軸 f3) と gate worst gap は相関するが分離
- session_block_win_rate は gate のみ、 search 圧には反映されない

論点: gate fail 個体が **archive に流入する条件**は?
- mission_pass: gate 全 stage 通過
- progress_pass: C-lite 2/3 windows pass
- score_bypass: gate 通過個体不足時、 worst_gap 昇順 top-K を強制流入

archive 流入 = stage gate 通過 OR bypass。 つまり gate fail でも search で生存している個体は **bypass 経由でしか archive 入りしない**。 これで gate と search の独立性が担保される。

確認: この理解で正しいか。 もし「stage gate 完全 fail 個体も search 圧で残ったら archive 入る」 となると、 archive 質が search 評価軸 (mission_inf_gap) のみで決まってしまい、 gate (canonical 5 worst の win_rate / Sharpe_session) が archive に反映されない。

### 検査 2: Stage A 時間配置 (時間軸 B→A) と warmstart の整合

partition: `[B 62w][A 8w][emb][C-lite × 3][emb][C 12w]`

時間軸: B が古い、 A が中、 C-lite が新しい、 C が最新。

selection cascade 順 (A→B→C-lite→C) は時間順と逆 (B→A→C-lite→C)。

論点: 個体評価:
- Stage A は最新 8w (recent proxy) で短期 viability 確認
- Stage B は train 36w + embargo + test 5w で fold 単位 OOS
- Stage C-lite は B より新しい時期で long-term OOS
- Stage C は最新 12w で final holdout

warmstart 注入された個体は **古い epoch 由来**だが、 評価対象は **現 epoch の各 stage**。 これで時間整合性は OK。

ただし: warmstart の archive entry は前 epoch の Stage A/B/C-lite/C で評価された個体。 現 epoch ではゼロから再評価する。 warmstart は genome (戦略) を引き継ぐだけで、 評価結果は引き継がない。 これで OK。

### 検査 3: 5 fold pooled が Stage B の主判定 と 多目的圧の整合

Stage B 5 fold pooled で canonical 5 worst を計算。 これが gate (Stage B 通過判定) の主基準。

GA selection 圧 (Pareto 3 軸) は **gen 単位**で計算。 つまり毎世代の個体評価で:
- canonical 5 (gate 用): 5 fold pooled 計算が必要 → 1 個体評価あたり 5 fold × backtest = 重い
- Pareto 3 軸 (search 用): mission_inf_gap が live_criteria 4 指標から計算、 これも 5 fold pooled が必要

つまり毎世代で **全個体に 5 fold pooled backtest**が必要。 これは Stage A 8w (1 backtest) より圧倒的に重い。

逆ピラミッド再発の懸念。 zenigame の Stage B も per-fold backtest を全個体に走らせていた? もし zenigame が「Stage A 通過個体のみに Stage B fold backtest」 とフィルタしているなら、 fx も同じにすべき。

確認: Stage A → Stage B のフィルタ率は (q_force_dynamic) で決まる。 Stage A pop=192 中、 q_force=0.15-0.30 で 29-58 体が Stage B 進出。 これに 5 fold = 145-290 backtest / Run。

vs Stage A: pop=192 × gen=64 = 12,288 backtest / Run。

つまり Stage B は Stage A の 1-2.4% の compute。 cascade として正しい (重い処理が後段で少数個体に)。

OK、 cascade は機能している。 ただし「**毎世代の Pareto 3 軸 search 圧計算に何の評価値を使うか**」 が論点:
- (i) Stage A 8w 結果のみ (= 全個体評価可能だが mission_inf_gap が短期 proxy)
- (ii) Stage B 5 fold pooled (= Stage B 通過個体のみ評価可能、 cascade として正しい)
- (iii) Stage A + Stage B のハイブリッド (= Stage A 全員評価、 Stage B 通過者のみ更新)

(ii) なら mission_inf_gap は Stage B 通過者のみ計算、 Stage A 不通過者は selection 圧に Pareto 3 軸 を効かせられない (= 単純除外)。

(iii) は段階的更新で「Stage A 単独で評価された短期 mission_inf_gap」 と「Stage B 5 fold pooled で評価された長期 mission_inf_gap」 が混在。

zenigame は (iii) ハイブリッドだった気がする (Stage A pass のみ Stage B 評価、 Stage A fail は短期評価のみ で selection)。

Codex の見解は？

### 検査 4: 緊急モードと epoch-rolling の整合

緊急モード: mission_pass=0 連続 3 Run + MA3 < MA6 - 0.05 で発動、 warmstart_share 増加。

epoch-rolling: 4w stride、 max_runs/epoch=6。 epoch 内の 6 Run のうち 3 Run 連続で緊急条件成立すると、 残り 3 Run で緊急モード継続?

論点:
- 緊急モード中 archive_share 35% で warmstart 強化、 ただし archive entry は前 epoch 由来 (epoch_age >= 1 が大半)
- prev_epoch entry は通常 20% only (Stage A quick recheck 通過時) という Round 14 制約
- 緊急時 35% への増加は prev_epoch 制約と整合するか

整理:
- 緊急モード時 warmstart_share 35% = 67 体 (pop=192 で)
- 内訳 emergency CA:DA = 1:1 で 33-34 体ずつ
- このうち prev_epoch 20% = 13-14 体は許可、 残り 53 体は current_epoch でないと埋まらない
- ただし current_epoch archive は緊急発動時にはまだ薄い可能性 (= 質低下 archive)

これだと緊急モードで意図通り動かないリスク。 改修案:
- (a) 緊急時は prev_epoch 制約を一時緩和 (35% allowed)
- (b) 緊急時 share は 25% に抑える (現 archive で埋められる範囲)
- (c) 緊急モード発動時 epoch_age=2 entries も限定的に許可

### 検査 5: profit_factor tie-break 位置の運用

Round 13 確定: profit_factor は archive lexicographic 末端 tie-break のみ。

論点: lexicographic eviction は CA/DA 別 (Round 14)。 profit_factor は両方の末端 tie-break として置く。

ただし profit_factor 計算は GP/GL 比なので、 GL=0 (全勝 trade) で +inf になる。 zenigame T508 では log_pf で安定化していた。 fx でも log_pf を使うか、 raw pf でも tie-break なら問題ないか。

提案: log_pf = log((GP+1e-6)/(GL+1e-6)) clip(-2, 2) を tie-break 用 metric として保持。

(4) `win_rate は trade 勝率`: 解消 (session_block_win_rate に semantic 上げ)
(5) `archive は weighted sum で掃除`: 解消 (lexicographic eviction)
(6) `35m は 24m より優`: 解消 (24m primary 確定)
(7) `max_workers config 定数`: 解消 (clamp 式で実機自動)
(8) `shadow pair selection 圧化が robust`: 解消 (validation axis 維持)
