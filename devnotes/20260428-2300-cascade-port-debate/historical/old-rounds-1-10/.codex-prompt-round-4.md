## Claude の反論・突き詰めポイント

### 反論 1: volatility regime と session bucket は冗長か独立か

Andersen & Bollerslev (1998) の Deutsche Mark-Dollar volatility 論文は、 **intraday volatility patterns と session が強く相関** することを示している。 Tokyo session は low_vol、 London open + NY overlap は high_vol、 等。 つまり:

(i) volatility regime と session bucket は**同一情報の異なる表現**で、 両方 P2 に入れると冗長
(ii) session bucket は **時刻** で決定論的に分けられるので、 各 bar が必ず 1 session に所属する。 一方 volatility regime は計算窓に依存する

**Claude の主張**: 単一通貨ペア (EUR_JPY) の intraday は session が **causal 構造** で、 volatility はその **observable 結果**。 P2 に入れるなら **session を主軸**、 volatility regime は session 内 sub-bucket に。 もしくは「session × vol」 の cross-bucket で 6 cells を作る。

候補:
- (A) volatility 3 bucket (Codex Round 1 案)
- (B) session 3 bucket (Tokyo / London / NY、 closer to causal structure)
- (C) volatility 3 × session 2 = 6 cross-buckets (rich だが pop=40 で疎)
- (D) session 3 + volatility tag (session を主軸、 volatility は archive metadata)

Codex はどれを推すか。 Andersen & Bollerslev / Ito & Hashimoto の知見と合わせて。

### 反論 2: regime 計算の look-ahead bias

P2 軸として regime label を使う場合、 **regime 判定タイミングの look-ahead** が問題:
- 各 bar の regime label を確定するには、 **その bar 時点で確定している情報のみ**で判定する必要がある
- volatility regime: 過去 N bars の realized vol で判定 → look-ahead なし、 ただし bar 時刻で判定済の必要
- session bucket: bar 時刻 (UTC hour) のみ → look-ahead なし
- aux factor regime (VIX, DXY): `effective_from_utc` 契約 (T057) で daily +24h / 月次 +35d 遅延済 → look-ahead なし

**Claude の主張**: session が一番安全 (look-ahead 不可能)、 volatility は窓設計で安全化、 aux は契約済み。 ただし regime _bucket_ ごとの統計を計算するときに「全期間集計から bucket を切る」 ような実装は look-ahead bias なので、 **regime_label は per-bar 確定値**である必要。 これは原則 0 (lookahead 排除)。

Codex の見解は？ regime taxonomy を入れる際に最も危険な lookahead 経路は？

### 反論 3: P2 の「適用ステージ」 範囲

Round 1 で P2 は 「Stage C-lite の 3 disjoint windows」 で使う想定だった (zenigame の C-lite 設計をポート)。 しかし fx で P2 を導入する場合、 **どの stage まで** 適用するか:

(a) Stage C-lite のみ (window-level の regime aware)
(b) Stage B + C-lite (fold-level + window-level)
(c) Stage A + B + C-lite (gen-level も含めて)
(d) Sieve のみ (post-RUN の archive 判定だけ)

zenigame は (c) に近い (RASI = adaptive_live_criteria が gen-level で計算される)。 ただ pop=40 で 3 regime × 600 evaluations = bucket あたり 200 evaluations だから、 regime ごとの 5 指標 worst gap 計算は statistically OK。

**Claude の主張**: (b) Stage B + C-lite + Sieve が適切。 Stage A は短い window (60d) なので regime split しても各 regime の trade_count が薄くなる (60 × p_regime = 20 日でしかない)。 Stage A は単一 regime 視点で評価し、 Stage B 以降で regime aware に。

Codex の見解は？ Stage A まで regime aware にする利益と害は？

### 反論 4: spectral weight の決定方式

Codex Round 1 案: `[0.40, 0.35, 0.25]` の傾斜上限。 これは個体の各 regime gap を desc sort して spectral weighted average する zenigame 方式。

しかし fx で 3 regime + 24 ヶ月 dataset の場合:
- 各 regime の出現頻度は不均等 (Tokyo 約 1/3、 London 1/3、 NY 1/3 だが volatility は high_vol が少ない)
- spectral weight が **fixed** だと、 出現頻度の少ない regime (high_vol) を **必ず最重要**として扱うため、 個体の「全体平均は良いが high_vol で苦戦」 と 「全体は低いが high_vol で頑張る」 が同 score
- **support-aware weight** (各 regime のサンプル数で正規化) の方が pop=40 では妥当

**Claude の主張**: spectral weight は固定ではなく、 **support-aware** にすべき:
```
weight_i = sample_count_i / sum(sample_count) × adjustment_factor
```
ただし調整係数で「高難度 regime には微増 weight」 を与える (zenigame の意図に近い)。

Codex の見解は？ fixed [0.40, 0.35, 0.25] vs support-aware vs その他案。

### 反論 5: regime_pass_pattern を P2 に絶対入れない理由の精査

Codex Round 1 で「(f) regime_pass_pattern は collider なので P2 にしない」 と明言。 これは「outcome-derived な軸を difficulty normalization に使うと、 selection の結果で regime を定義する循環」 になる、 という主張。

しかし archive diversity tag としては有用 (zenigame の「同一 family が複数 regime で pass」 という pattern は warmstart 注入の多様性指標として使える)。

**Claude の主張**: (f) は P2 (selection 圧の正規化軸) ではなく、 **archive diversity 軸**で使うのが正しい。 これは Round 6 (論点 5) で詳細議論するが、 ここで「P2 ではない」 と確定させたい。

Codex の confirm。

### 反論 6: cross-pair shadow を P2 軸にしない代わりに何にするか

Codex Round 3 で cross-pair shadow は「Stage C/AS の validation axis」 と確定。 ただ validation axis は selection 圧から外れるので、 「単一通貨ペア edge を超えた多様性」 を捕捉する別経路が要る。

候補:
- cross-pair shadow が C で常態的に落ちるなら、 archive 投入時に「cross-pair pass tag」 を付け、 warmstart で使う (= archive diversity tag)
- cross-pair が落ちる個体は archive に入れるが warmstart には使わない (= negative selection axis)

**Claude の主張**: cross-pair shadow は **validation axis + archive metadata**。 selection 圧では使わないが、 archive eviction や warmstart 注入の優先度に使う。

Codex の confirm。
