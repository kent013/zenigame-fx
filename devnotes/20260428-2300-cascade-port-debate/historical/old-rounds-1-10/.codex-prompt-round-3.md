# Round 3 — 論点 2 deep dive (Objective Taxonomy: canonical 5 × FX 固有指標)

論点 1 は Round 2 で確定 (D' 先行延長 24ヶ月、 Stage B = WF-OOS gate (γ)、 train 45 + embargo 1 + test 20)。 **論点 2 に移る**。

## Round 1 の Codex 暫定整理

- canonical 5 (sharpe / net_return / max_dd / trade_count / win_rate) を worst のまま維持
- FX 固有 (`spread_consumption_ratio` / `session_close_drop_count` / `negative_equity_drop_open_count`) は worst に入れず、 **constraint / tie-break / invariant** に分離
- `negative_equity_drop_open_count` は invariant breach なので **fail-fast** (selection 対象ではなく simulator/accounting bug)
- `win_rate` は将来的に demote 候補 (mission に無い指標)

## Claude の反論・突き詰めポイント

### 反論 1: win_rate を canonical 5 に残す根拠の弱さ

Mission (live_criteria) は `Sharpe / total_pnl / max_dd / trade_count 範囲` の 4 指標のみ。 `win_rate` は無い。 zenigame は universe=64 銘柄で win_rate が「個別銘柄の勝ちトレード比率」 として意味を持つが、 fx は単一通貨ペアで、 win_rate は「個別 trade の勝率」 になる。

**Claude の主張**: fx では `win_rate` を **canonical から外す**。 代替として何を入れるか、 もしくは canonical を 4 指標 (sharpe / net_return / max_dd / trade_count) で運用するか。

候補:
- (a) canonical 4 指標で運用 (mission-faithful)
- (b) canonical 5 指標 (zenigame faithful、 win_rate を残す)
- (c) win_rate を **profit_factor** (gross profit / gross loss) に置換 — Lo (2002) Sharpe は skew を捕捉しないので、 P&L 形状の 5 番目指標として profit_factor は意味がある
- (d) win_rate を **expectancy** (= avg_pnl_per_trade × trade_count, 既に sharpe と相関高い) に置換

Codex はどれを推すか。 mission-faithful の (a) と zenigame-faithful の (b) は **どちらが正しいか** ではなく、 **fx の selection 圧として何を捕捉したいか** で決まる議論。

### 反論 2: spread_consumption_ratio を constraint に置く具体形

Codex は「spread_consumption_ratio は exec-floor 候補 or tie-break」と言うが、 具体的な閾値設計が曖昧。

提案:
- (α) **hard constraint**: `spread_consumption_ratio > 0.7` で **fail-closed** (取引の 70% 超が max_spread_bps に達した個体は invalid)
- (β) **soft constraint**: spread_consumption_ratio > 0.5 で `worst_gap` に penalty (例: gap = max(0, ratio - 0.5))
- (γ) **tie-break**: canonical 5 worst が同 rank の個体間で spread_consumption_ratio 昇順
- (δ) **monitor only**: archive 記録のみ、 selection 圧から外す

**Claude の主張**: (α) は禁止事項 6 (取引回数を削減して見かけ成績を上げる) の温床。 spread_consumption_ratio を hard constraint にすると、 entry threshold を釣り上げて取引数を絞った個体が pass する逆効果がありえる。

(β) の soft penalty も同じリスク。 (γ) tie-break or (δ) monitor が安全寄り。

Codex の見解は？ 「spread を fitness に反映」 (絶対制約) と 「取引回数削減を防ぐ」 (禁止 6) の両立をどう設計するか。

### 反論 3: session_close_drop_count の意味論

run-26 で session_close_drop_open_count=1361, pending=4。 これは「session_close_utc_hours で drop した持ち越し試行」 の件数。 **drop された = overnight 持ち越しを試みたが intraday 制約で close された** という意味で、 **絶対制約 (intraday 前提) の breach 検出**。

**Claude の主張**: session_close_drop はそもそも 0 が正しい。 0 でないなら simulator 側の bug ではなく、 **戦略が overnight 持ち越しを学習している** = 絶対制約違反。 invariant breach と同じく **fail-fast** にすべき。

具体的には:
- session_close_drop_count > 0 の個体は `is_feasible = False` で確定 infeasible
- selection 経路から完全排除

Codex は同意するか。 もしこれが「simulator の自動処理 (drop して PnL を確定させる)」 で正常動作と解釈するなら、 selection 圧から外すべきだが、 invariant breach と解釈するなら fail-fast。 どちらが正しいか。

### 反論 4: negative_equity_drop_open_count の解釈

run-26 で **9311 件**。 9311 / total_bars=86400 ≈ 10.8% の bar で「equity_at_entry < 0 で entry が drop」 されている。 つまり**個体は何度も entry signal を出すが、 equity が枯れて entry できない**状態。

Codex は「invariant breach なので fail-fast、 simulator/accounting 問題」 と整理したが、 fx の場合これは別の意味も持ちうる:
- (i) 戦略が drawdown 中に逆張り entry を出し続けている (loser-averaging)
- (ii) leverage 設計と equity の保守的判定 (`equity_at_entry < 0`) が噛み合っていない (simulator design)
- (iii) 戦略が equity を顧慮しない pure signal-driven で、 drawdown 中も entry 試行を続ける

**Claude の主張**: 9311 件は (i) も (iii) もありうるが、 selection 圧の方向性として 「entry 失敗が**多い個体は infeasible**」 とするのが妥当。 spread_consumption と違い、 negative_equity_drop は「取引回数を削減して回避」 ではなく「リスク管理を学習」 する方向に圧をかけられる。

具体策:
- `negative_equity_drop_open_count > N` (N = trade_count × 2 とか) で `worst_gap += penalty`
- もしくは `(negative_equity_drop_open_count / trade_count)` ratio を canonical 5 の 5 番目指標に置換 (= 戦略の「risk discipline」 metric)

Codex の見解は？ これを canonical に上げる根拠 vs constraint に留める根拠は？

### 反論 5: cross-pair shadow と objective taxonomy

cross_pair (T016) は config に shadow mode で枠あり (`mean_sharpe_cross_min: 0.15` など)。 これは Stage C の判定軸として **canonical 5 とは別経路**で評価される。

**Claude の主張**: cross-pair shadow は**論点 2 の objective taxonomy では「validation axis」として明確に分離**すべき。 selection 圧 (Stage A/B/C-lite) には cross-pair を入れず、 Stage C 通過後の最終 gate もしくは AS (Sieve) 判定で使う。

これは Codex の Round 1 の (d) 評価と整合 (「validation axis、 P2 主軸ではない」)。 確認したい。
