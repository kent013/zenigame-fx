## Claude の反論・突き詰めポイント

### 反論 1: archive 流入経路の階層化

zenigame は C→AS で **4 層流入** (adaptive_pass + adaptive_progress + transition_pass + score_bypass)。 fx で何層必要か:

(a) **2 層**: mission_pass (canonical 5 worst gap = 0) + score_bypass (worst_gap 昇順 top-K)
(b) **3 層**: mission_pass + progress_pass (3 windows のうち 2 windows pass = majority) + score_bypass
(c) **4 層**: zenigame 完全ポート (transition_pass を fx 文脈で何かに対応させる)

論点 4 で C-lite = 3 disjoint windows × 15 cells worst が確定。 majority (2/3 windows pass) という「中間ゲート」 は fx でも意味あり。

**Claude の主張**: (b) 3 層が現実的。 transition_pass は zenigame の W3 mixing 由来で fx に対応物が無い。 ただし、 fx で「session 3 bucket のうち 2 bucket で pass」 という session-majority が transition_pass の代替候補。

### 反論 2: archive eviction の優先順位

archive=100 (CA 50 + DA 50) で over capacity になった時、 何を evict するか:

zenigame:
- run_quota (sieve_pass top-K) を保護
- per_seed_min=8 を保護 (各 seed から最低 8 件残す)
- それ以外は sieve_score 最低を evict

fx で何を保護するか:
- (i) `family_key` ごとの最小残存数 (= per_family_min)
- (ii) `source_run_id` ごとの最大数 cap (= per_run_max、 単一 Run 由来の支配を防ぐ)
- (iii) `session_pass_pattern` ごとの最低残存数 (= 各 P2 bucket の生存個体保証)
- (iv) `cross_pair_pass_tag` がある個体を保護 (validation pass の希少性)
- (v) 直近 N Run 以内の個体を保護 (stale archive 防止)

**Claude の主張**: (ii) per_run_max + (iii) per_session_pattern_min + (v) recency_floor の組み合わせ。 (i) family_min は warmstart 注入時の制約で代替できるので archive eviction では不要。

Codex の見解は？ archive 100 体の何を保護し、 何を eviction 対象にするか。

### 反論 3: warmstart 注入時の多様性制約

zenigame の warmstart 制約:
- max_family=2 (同一 family_key 最大 2 体)
- max_per_source_run=3
- max_per_source_seed=4 (fx では seed 概念なしで読み替え必要)
- 2 段階緩和 (strict → relax_run → relax_seed)

fx 版:
- (i) max_family=2 はそのまま
- (ii) max_per_source_run=2 に縮小 (pop=40 で 8 体注入なら 2 体/run cap で 4 run 由来を要求)
- (iii) max_per_source_seed の代わりに max_per_session_pattern (各 session pass パターンから注入数 cap)
- (iv) max_per_period (period rotation を採用するなら) - だが論点 4 で period_bucket は archive metadata のみと確定

**Claude の主張**: (i) + (ii) + (iii) の 3 制約。 (iv) は不要。

### 反論 4: score_bypass K の決定

Codex Round 1 で K=2-3 を提案。 fx の archive_inflow=8〜12 / Run に占める割合は K=2 だと 17-25%、 K=3 だと 25-37%。

zenigame では「strict は無制限、 progress + transition + bypass 合計が top_n」 という構造。 fx では:
- mission_pass (strict) は 0 体の Run が頻発する想定 (fx は元々難しい)
- progress_pass (2/3 windows) で 4-6 体程度入る想定
- bypass で 残り 2-4 体

**Claude の主張**: bypass は K=3 で固定 (= 約 25-30% 流入比率)。 進入閾値は worst_gap 昇順 top-3 で機械的に決める。 mission_pass + progress_pass + bypass 合計 8-12 体になる調整。

Codex の見解は？

### 反論 5: archive→warmstart の cycle 健全性

zenigame は `max_reuse=2, cooldown=2` で 「直近 Run での連投制限」。 fx でも同様に必要:
- (i) `max_reuse=2`: 同一 archive entry を最大 2 回連続 run で warmstart に使う上限
- (ii) `cooldown=1`: 1 Run 空けないと再注入できない (re-cooling period)

これは **同一個体の遺伝的支配を防ぐ**。 fx では Run 間隔が短い (1 cycle ~ 1-2 時間) ので、 cooldown=1 程度が妥当。

**Claude の主張**: 採用。 ただし archive にあっても warmstart に**再使用しない**個体を増やすので、 archive 100 体のうち実効的に warmstart に使われるのは 40-60 体程度になる。 これは想定内。

Codex の confirm。

### 反論 6: cycle 全滅時の最終安全網

論点 1, 2 確定後、 mission_pass=0 + progress_pass=0 の Run が出る可能性が高い (fx は元々難しい + canonical 5 worst で厳しめ)。 そのとき:

(a) **score_bypass で必ず 8-12 体流入させる**: archive は枯れない (cycle 健全性)
(b) **archive を更新しない (skip)**: その Run の貢献を 0 にする
(c) **warmstart のみ archive 由来に振り切る**: 新規 fresh population を 8 体に減らし、 archive 由来 32 体で次世代を埋める (= 復活モード)

**Claude の主張**: (a) を主、 (c) は緊急用。 (a) で archive が「失敗 Run の bypass 個体で薄くなる」 リスクは、 archive entry の `quality_score` を保持することで eviction で淘汰できる。

Codex の見解は？

### 反論 7: regime_pass_pattern の使い方

論点 4 で「regime_pass_pattern は archive diversity 軸」 と確定。 具体的に何に使うか:

- (i) **archive eviction**: 同一 pass_pattern が archive で N 個以上いるとき、 quality_score 最低を evict (= pattern 多様性確保)
- (ii) **warmstart 注入の優先度**: 各 pass_pattern から最低 1 体注入 (= regime 多様性 seed)
- (iii) **DA archive の選抜基準**: DA に入る個体は pass_pattern が CA と異なるものを優先

**Claude の主張**: (i) と (iii) を採用、 (ii) は強制すぎるので採用しない。
