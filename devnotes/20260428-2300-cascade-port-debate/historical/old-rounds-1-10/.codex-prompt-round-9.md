# Round 9 — 適用順序の骨子提案 + risk score

論点 1〜5 + cross-cutting + 未解決 gap すべて確定。 ここから**適用順序**の議論に入る。

## 確定済み構成 (Round 1〜8 統合最終版)

### A. Topology + Dataset
- dataset = 24 ヶ月先行延長 (M1 価格 + 各種 aux)
- pop=40, gen=15, max_workers=2
- Stage 構成: A → B (WF-OOS gate) → C-lite → C → AS → Archive (CA/DA 分離) → Warmstart → 次 Run の A
- Stage A = 末尾 60 日 short-term screen、 regime aware にしない
- Stage B = WF-OOS gate (train 45 + embargo 1 + test 20)、 fold-median worst gap、 IS monitor 撤廃
- Stage C-lite = 3 disjoint temporal windows × 5 指標 = 15 セル worst + top 30% 強制通過
- Stage C = 60 日 holdout + spread stress + cross-pair shadow (validation)

### B. Objective Taxonomy
- canonical 5 = sharpe_ann / net_return / max_dd_adj / trade_count / log_pf
- denom_m = threshold-based 固定 (horizon 補正 + log_pf 安定化)
- spread_consumption_ratio = tie-break + monitor
- session_close_drop / negative_equity_drop > 0 = invariant fail-fast
- cross-pair shadow = validation axis + archive metadata

### C. Regime Taxonomy (P2)
- 主軸 = session_bucket 3 (Tokyo/London/NY)
- spectral weight = support-aware clip [0.25, 0.45] (development span のみ計算、 holdout 除外)
- 適用 = Stage B + C-lite + Sieve、 Stage A 除外
- Stage B trade_count は全体評価、 session は share >= 0.15
- total_trades_B < 30 で session 評価 INCONCLUSIVE
- volatility / aux / period / regime_pass_pattern = archive metadata only
- cross_pair_pass_tag = validation + archive metadata

### D. CPPS Scope
- 3 軸 Pareto (net, dd, margin_inf) + crowding
- one-switch push→pull (`feasible_ratio_ema >= 0.15` 主条件、 `gen >= 10` 安全弁)
- external archive のみ CA/DA 分離 (CA 50 + DA 50)
- 強制通過率 = clamp(0.15 + 0.15 × max(0, 0.10 - feasible_ratio_ema)/0.10, 0.15, 0.30)
- trade_count 下限段階制御 (push >= 0.5×TC_min, pull >= 0.8×TC_min)
- bypass 候補品質床: invariant_feasible AND margin_inf_percentile <= 70

### E. Loop Closure
- archive=100 (CA 50 + DA 50)、 target_inflow=10、 per_run_max=10
- 3 層流入: mission_pass + progress_pass (C-lite 2/3 windows pass) + score_bypass
- bypass K = clamp(10 - n_mission - n_progress, 2, 4)
- warmstart_share=0.20 (CA 5 + DA 3)
- warmstart 制約: max_family=2, max_per_source_run=2, max_per_session_pattern=2
- max_reuse=2 (rolling 10 run), cooldown=1
- eviction ハード: per_run_max=10, pattern_max_share=0.25, recency_floor=12 (last 3 runs)
- eviction ソフト: 加重和 0.70Q + 0.15R + 0.15D + 0.05X
- 緊急モード: mission=0 3 連続 + MA3 < MA6 - 0.05、 warmstart_share 0.20→0.35 1 run
- calibrate 凍結: 3 Run 凍結、 4 Run 目更新、 |Δ| <= 0.03

### 適用順序候補

(I) **Phase A → B → C → D → E → F (linear)**: 単純、 各 Phase 完了後 next。
(II) **Phase A 並行 + B/C 並行 + D + E + F**: A は 24 ヶ月データ取得が長く、 並行で B/C の評価層は実装可能
(III) **Phase A → B+C+D 一括 → E → F (大改修)**: 評価層と GA 系統は依存が深いので一括書き換え
(IV) **Phase A → B → C → E (部分) → D → E (完成) → F**: archive 構造を先に作り、 GA は後付け

### Round 9 で Codex に求めるもの

1. **適用順序の判定**: (I)(II)(III)(IV) のどれを推すか + 反証
2. **Phase 内の依存グラフ**: A-1〜A-4, B-1〜B-6, C-1〜C-5, D-1〜D-5, E-1〜E-7, F-1〜F-4 の dependency 解析
3. **Critical path 特定**: 全体 wall-time を最小化する実装順序
4. **risk-ordered top 5 phase 内項目**: 最も実装上のリスクが高い項目 5 つ + 緩和策
5. **「最小スマートな smoke 構成」**: Phase F-1 を最初に通すための最小実装範囲 (= cascade が回る最小単位)
6. **fail-fast 設計の保証**: 各 Phase で「これが動かなかったら次に進めない」 という gate 条件
7. **Phase 進行中の検証ポイント**: 各 Phase の完了基準 (Definition of Done)

quantitative argument 必須。 各 Phase の wall-time 推定 (人間時間)、 リスク評価、 並行可能性。 確証ない部分は INCONCLUSIVE で明示。
