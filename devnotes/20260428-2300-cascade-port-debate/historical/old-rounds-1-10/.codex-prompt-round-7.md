# Round 7 — Cross-cutting consistency check (5 論点確定後の整合性検査)

5 論点すべて Round 1〜6 で確定。 ここまでの確定案を**全体として再点検**する。 個別論点は煮詰まったが、 横断的に矛盾や lookahead 経路や硬直化リスクが残っていないか検査する。

## 確定案 全体マップ (Round 1〜6 統合)

### A. Topology + Dataset
- dataset = **24 ヶ月先行延長** (M1 価格 + 各種 aux)、 6 ヶ月運用は配線検証のみ archive 本流に流さない
- pop=40, gen=15, max_workers=2 (現状維持)
- Stage 構成: `A → B (WF-OOS gate) → C-lite → C → AS → Archive → Warmstart → 次 Run の A`
- Stage A = 末尾 60 日 short-term screen (regime aware にしない)
- Stage B = WF-OOS gate (train 45 + embargo 1 + test 20)、 fold-median worst gap、 IS monitor 撤廃
- Stage C-lite = 3 disjoint temporal windows × 5 指標 = 15 セル worst + top 30% 強制通過
- Stage C = 60 日 holdout + spread stress + cross-pair shadow (validation)

### B. Objective Taxonomy
- canonical 5 = sharpe / net_return / max_dd / trade_count / **profit_factor** (win_rate 降格 → monitor)
- spread_consumption_ratio = tie-break + monitor (hard/soft constraint にしない)
- session_close_drop_count > 0 = invariant fail-fast
- negative_equity_drop_open_count > 0 = invariant fail-fast
- cross-pair shadow = validation axis + archive metadata (selection 圧から除外)
- live_criteria = Stage C の hard constraint (mission gate)

### C. Regime Taxonomy (P2)
- 主軸 = session_bucket 3 (Tokyo/London/NY)、 時刻ベースで lookahead 安全
- spectral weight = support-aware clip [0.25, 0.45] + 再正規化
- 適用 stage = Stage B + C-lite + Sieve (Stage A 除外)
- volatility = 副次タグ (P2 主軸外、 metadata)
- aux_regime / period_bucket = Sieve のみ
- regime_pass_pattern = archive diversity 軸 (P2 禁止、 collider)
- cross_pair_pass_tag = validation + archive metadata

### D. CPPS Scope
- 3 軸 Pareto (net, dd, margin_inf) + crowding (NSGA-II 系 rank)
- one-switch push→pull (`feasible_ratio_ema >= 0.15` 主条件、 `gen >= 10` 安全弁)
- 進化母集団 CA/DA 分割なし (pop=40 のまま)
- external archive のみ CA/DA 分離 (CA 50 + DA 50)
- 強制通過率 0.25 → 0.15 線形減衰
- trade_count 下限段階制御 (push 緩 / pull 厳: push >= 0.5×TC_min, pull >= 0.8×TC_min)
- exec_floor は不採用 (論点 2 確定で対象消失)

### E. Loop Closure
- archive=100 (CA 50 + DA 50)、 target_inflow=10 / Run (許容 8〜12)
- 3 層流入: mission_pass + progress_pass (C-lite 2/3 windows pass) + score_bypass
- bypass K = clamp(10 - n_mission - n_progress, 2, 4) 動的
- warmstart_share=0.20 (8 体)、 内訳 CA 5 + DA 3
- warmstart 制約: max_family=2, max_per_source_run=2, max_per_session_pattern=2
- reuse 制約: max_reuse=2 (rolling 10 run), cooldown=1
- eviction ハード: per_run_max=8, pattern_max_share=0.25, recency_floor=12 (last 3 runs)
- eviction ソフト: cross_pair_pass_tag ボーナス、 quality 優先
- 全滅時: (a) bypass 補充主、 3 run 連続悪化で (c) 緊急モード (warmstart 比率 0.20→0.35 一時増)

## Round 7 で検査する cross-cutting 論点

### 検査 1: Stage 間の指標スケール整合

論点 2 確定の canonical 5 = `sharpe / net_return / max_dd / trade_count / profit_factor`。 各 Stage で計算される時のスケール・単位が**整合しているか**:

- Stage A 60 日: trade-level Sharpe (zenigame で T042 の rescale 経験あり、 fx 側 docs/alpha_factory/sharpe-rescale.md)
- Stage B fold (test 20 日): per-fold trade-level Sharpe + fold-median worst gap
- Stage C-lite 3 windows (各 30-45 日想定): per-window trade-level Sharpe
- Stage C 60 日 holdout: live_criteria 比較は **annualized Sharpe** (T042 換算後)

**懸念**: live_criteria.sharpe_min=1.0 (annualized) と Stage A/B/C-lite の trade_sharpe_raw (trade-level) が**異なるスケール**で worst gap 計算される。 zenigame では T508/T511 でこの整合化に苦労した経緯あり。

Codex に確認:
- canonical 5 の各指標が Stage 横断で **同一スケール**で gap 計算される設計になっているか
- profit_factor は Stage A (60 日) と Stage C-lite (30 日 window) で**期間長の差**による不安定性が出ないか
- max_drawdown は dataset 期間で正規化するか absolute value か

### 検査 2: lookahead bias の cross-stage 経路

論点 4 で per-bar regime label の lookahead 防止は確認済み。 cross-stage で残る危険経路:

(i) **Stage B fold の閾値を Stage C 通過個体で再校正**: archive 側で「過去 Run の Stage C 結果」 を使って Stage B 閾値を更新すると、 archive (= Stage C 通過個体由来) → Stage B threshold → 新 Run の Stage B → Stage C という circular dependency
(ii) **session_bucket support-aware weight を全期間集計で決定**: Run 開始時に dataset 24 ヶ月全体で weight を決定すると、 holdout 60 日も含めた集計になる。 holdout 期間は除外して weight 計算が必要
(iii) **archive→warmstart で「将来 Run 由来の archive entry」 が現 Run に注入される**: archive 更新タイミングと warmstart 注入タイミングが整合しているか確認
(iv) **calibrate-gate (T027) の history.jsonl 由来 threshold が新 Run に**: Stage A threshold を**過去 Run の Stage A pass 率で決定**するのは look-ahead ではないが、 同 dataset 上で circular に最適化される懸念

Codex に確認:
- 上記 (i)〜(iv) のうち、 確定案で抑止される経路はどれか
- 抑止されない経路があれば、 追加の安全装置が必要か

### 検査 3: 過度な硬直化リスク

確定案で固定値が多い:
- archive 100 / inflow 10 / warmstart 8 / CA 50 / DA 50 / max_family 2 / max_per_source_run 2 / max_per_session_pattern 2 / recency_floor 12 / per_run_max 8 / pattern_max_share 0.25 / max_reuse 2 / cooldown 1 / target_inflow 10

これらが**全部組み合わさると、 archive entry が制約で動けなくなる** 可能性:
- 例: Run 直後 inflow=10 で per_run_max=8 違反 → 2 体は eviction → でも recency_floor=12 で直近 3 Run 保護 → 矛盾発生

Codex に確認:
- 制約間の組み合わせで **発生しうるデッドロック**はあるか
- 緩和順序 (session_pattern → source_run → family) は十分か
- 量的 hyper-parameter で「論理的に到達不能な状態」が無いか

### 検査 4: cycle 健全性 (原則 3) と selection 圧 (原則 1) の trade-off

確定案では:
- 原則 1 (絶対閾値=破綻排除のみ): canonical 5 worst gap で相対 ranking
- 原則 3 (強制流入): bypass K 動的 + 強制通過率 0.25→0.15

しかし以下の懸念:
- Stage A 強制通過率 0.25 (= pop 40 × 0.25 = 10 体) は zenigame の 15% (= pop 192 × 0.15 = 29 体) より**緩い割合**だが体数では少ない
- canonical 5 worst gap で 5 指標 AND を要求するため、 fx の難しい dataset では feasible 個体が出ない Run が頻発しうる
- bypass で必ず 8-12 体流入するため、 archive は枯れないが、 **archive の質が悪化** する循環リスク

Codex に確認:
- archive 質を保ちつつ cycle 全滅を防ぐ trade-off の bound 設計
- 強制通過率 0.25 の根拠は zenigame 15% との比較で十分か
- bypass 個体の `quality_score` で eviction 優先される設計で archive 質は保たれるか

### 検査 5: 5 論点間の前提の連鎖

論点 1 (dataset 24 ヶ月延長) → 論点 2 の P2 sample size 前提
論点 2 (canonical 5 = profit_factor 含む) → 論点 3 の margin_inf 定義
論点 3 (3 軸 Pareto + CA/DA 分離 archive) → 論点 5 の流入階層
論点 4 (session 主軸) → 論点 5 の max_per_session_pattern

各論点の確定が**他論点の前提を満たすか**:
- (a) dataset 24 ヶ月で session 3 bucket × 600 evaluations / Run = 200 evaluations / bucket だが、 Stage B fold (test 20 日) では各 bucket trade_count >= 15 を満たすか
- (b) profit_factor は trade_count <= 5 だと不安定 (gross_loss=0 で +inf)、 Stage A の trade_count 下限 (push 期 0.5×TC_min) で profit_factor 計算が安定するか
- (c) margin_inf = canonical 5 signed worst slack だが、 各指標の単位差を吸収する正規化は確定しているか (= 各指標の denom 設計)

Codex に確認:
- 5 論点の前提連鎖で**カバーされていない gap**があるか
- 量的に矛盾する組み合わせが残っているか
