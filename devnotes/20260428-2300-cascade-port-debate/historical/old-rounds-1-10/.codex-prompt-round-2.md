# Round 2 — 論点 1 deep dive (Topology + dataset plan + Stage B 役割)

Round 1 を踏まえ、 まず **論点 1** に集中する。 Claude (主担当) からの反論・突き詰めポイント:

## R1 への反論 1: hybrid (D) は逃げではないか

Codex は「6カ月で再設計を進めつつ 18-24カ月化を別タスク」と整理したが、 これは Bailey/Lopez de Prado の PBO/CSCV や Deng (2023) の time-series CV 論点と整合的か疑わしい。

具体的に:
- 現状 6 ヶ月 ≈ 約 127 営業日。 zenigame の `3 disjoint windows × 30日` も `2 windows × 60日` も embargo を入れたら**物理的に成立しない**。
- 「6カ月で C-lite の最小構成に落とす」 とは具体的に何窓 × 何日にするのか？ 1窓 30日や 2窓 重複ありなら、 zenigame の C-lite (3 disjoint windows + bucket rotation) の **本来の機能 (window 過学習防止)** を満たさない。
- 別タスクに切ると言っても、 dataset 延長していない状態で C-lite を入れた cascade は**設計として未完**で、 「動くがガード機能していない」 zombie cascade になる。

**Claude の主張**: dataset 延長を**先行必須**にすべき。 cascade の設計は dataset_18m 前提で書き、 6ヶ月で実装する移行段階は「Stage A + Stage B (簡易) + Stage C」の 3 段に縮退した版を経由するのが正しい。 つまり:

(D') Phase 0: dataset 延長 (24ヶ月) を先行必須。 aux データ (FRED 等) の 24ヶ月 history が既に取れる前提なら technical blocker は薄い。
(D'') Phase 1: 24ヶ月前提で cascade 完成形を設計 + 実装。 6ヶ月運用は撤廃。

Codex の hybrid は「実装を早く進める」 メリットはあるが、 **設計の方向性が間違っているまま値を弄るな** (思考原則) に抵触しないか。 6ヶ月のままの cascade は方向性自体が崩れている設計ではないか。

## R1 への反論 2: Stage B 撤廃寄りの主張の精査

Codex は「Stage B を gate として撤廃、 残すなら上位少数個体への global audit に役割変更」と提案。 ここを煮詰めたい:

(α) **完全撤廃**: Stage A → C-lite 直結。 中間 gate は dataset 全体ではなく 「複数 fold WF」 で代替
(β) **役割変更**: Stage B は Stage C 通過後 (or top-K 候補) に対する diagnostic 専用、 selection 圧から外す
(γ) **WF gate 化**: dataset を train/test 領域で切り、 Stage B = WF-OOS の per-fold 5 指標 worst の median を gate にする (現状の median_oos_sharpe を 5 指標 worst median に拡張)

**Claude の主張**: (γ) が筋。 理由:
- zenigame の Stage B 役割は「IS/OOS 比較で IS overfitting を検出する gate」。 fx 文脈では IS monitor は不要だが、 「OOS robustness を multiple folds で検査する gate」 自体は必要。
- pop=40, gen=15 の中流 gate を完全撤廃すると、 Stage A (60d 短期) → Stage C (60d holdout) 直結になり、 中間の 「fold 間頑健性」 検査が消える。
- 完全撤廃 (α) は Stage A の short-term 過学習が C で初めて落ちる構造になり、 cycle 健全性 (原則 3) を破る危険がある。

Codex は (α)(β)(γ) のどれを推すか、 反証は何か。

## R1 への反論 3: dataset 延長と 1 fold = 71d の前提の見直し

「1 fold = train 60 + embargo 1 + test 10 = 71 営業日」 は config 値。 これ自体が長すぎる可能性:
- train 60 日 = canonical 5 指標を計算するのに必要な最小サンプル数か？ Andrew W. Lo (2002) の Sharpe SE 論文では trade_count >= 30 で SE ≈ √((1+0.5·SR²)/N) が安定。
- 60 日中 trade rate が 1 trade/day なら 60 trades で sufficient だが、 0.3 trades/day だと 18 trades で fold-level Sharpe が unreliable。
- **train 30 日 + embargo 1 + test 10 = 41 日**にすれば、 6ヶ月 (127 営業日) で disjoint fold 数 (127-41)/10 + 1 = 10 fold 確保可能。

**Claude の主張**: dataset 延長と並行して、 **fold 構造の見直し**も論点。 dataset 延長 → fold 数 16 (24ヶ月) と、 fold 短縮 → fold 数 10 (6ヶ月) のどちらが学習効率上正しいか。

Codex の見解は？ Lo (2002) の SE 公式と PBO の selection inflation の trade-off で。

## R1 への反論 4: aux データ (FRED) の history 制約

Codex は「dataset 延長」 を簡単に言うが、 fx の preflight は aux 必須 (T057 で導入済み)。 aux データの history 制約:
- VIXCLS (FRED): 1990 年から。 OK
- DTWEXBGS (FRED): 2006 年から。 OK
- EUR_USD/USD_JPY M1 bars: 取得元次第。 24ヶ月分が取れる前提か要確認
- effective_from_utc (daily +24h / 月次 +35d) 契約で look-ahead 防止しているので、 aux history が取れれば period extension に technical blocker は無い (はず)

**Claude の主張**: 24ヶ月延長は aux 取得 24ヶ月分が前提。 もし M1 bars 24ヶ月の取得が困難なら、 dataset 延長案は崩れる。

Codex はこの constraint をどう評価するか。 「6ヶ月のままで凌ぐ」 案 (B/C) を再考すべきデータ取得制約はあるか。
