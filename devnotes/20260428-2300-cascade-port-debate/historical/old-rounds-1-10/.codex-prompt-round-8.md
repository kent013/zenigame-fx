# Round 8 — 未解決 gap の詰め (denom_m / session bucket / eviction / 緊急モード)

Round 7 で 5 つの重要な未解決 gap が identify された。 これらを定量的に確定させる。

## 未解決 gap

### Gap 1: margin_inf 正規化分母 denom_m の最終仕様

Round 7 で「margin_inf の分母設計」 が未確定と指摘。 canonical 5 各指標は単位が異なるため、 signed slack を比較可能にする denom が必要:

```
gap_m = signed_slack_m / denom_m  (m ∈ {sharpe, net_return, max_dd, trade_count, profit_factor})
margin_inf = min over m of gap_m   (signed: 正なら mission 達成、 負なら未達)
```

候補:
- (a) **threshold-based**: denom_m = live_criteria 値の絶対値 (zenigame の T508 GAP_DENOM_FLOOR=1e-6 floor 付き)
  - sharpe: |sharpe_min| = 1.0
  - net_return: |total_pnl_min| = 50000 (JPY)、 もしくは 50000/initial_cash = 0.05
  - max_dd: |max_dd_max| = 0.2
  - trade_count: trade_count_min = 50
  - profit_factor: 1.0 (= break-even、 ただし log_pf スケールで 0)
- (b) **scale-based**: denom_m = 各指標の typical scale (例: dataset 内 std)
  - 利点: dataset 性質に応じて自動 scaling
  - 欠点: dataset 切替で denom 変動 (run 間比較が崩れる)
- (c) **hybrid**: threshold ベースだが、 各指標の典型 IQR で floor 補正

zenigame の T508/T513 では (a) を採用 + GAP_DENOM_FLOOR で 0 除算回避。 fx でも (a) で十分か。

**Claude の主張**: (a) で行く。 ただし profit_factor は **log_pf** で扱うので denom_m は zenigame と異なる。 提案:
- profit_factor: live_criteria に**追加**しない、 但し canonical 5 の 5 番目として gap_m 計算
- log_pf threshold = 0.0 (= profit_factor=1.0 で break-even)、 denom_m = log(2.0) ≈ 0.693 (= profit_factor=2.0 が「pass」 の典型値)

Codex の見解は？ (a)(b)(c) の選択 + profit_factor の denom 設計

### Gap 2: Session 3 bucket の trade_count 密度検証

Round 7 で「Stage B fold (test 20 日) で各 session bucket の trade_count >= 15 は未確証」 と指摘。

定量推定:
- M1 24/7 で test 20 日 = 28800 bars
- Tokyo session (UTC 0-7) = 33% / London (UTC 7-16) = 38% / NY (UTC 12-21) = 38% (※ overlap あり、 純粋 Tokyo / pure London / pure NY で再分割すれば各 25-30%)
- 各 bucket bars ≈ 8000-9000
- trade_count_min = 50 / dataset (= 6 ヶ月 × 1440 / 60 = 50 trades / 6 月 ≈ 8.3 trades/月)
- test 20 日 = 約 0.67 ヶ月 → trade_count 期待 ≈ 5.6
- session 3 分割で 各 bucket trade_count ≈ 1.9 → **明らかに不足**

**Claude の主張**: trade_count_min は live_criteria の dataset 全体値。 fold per-bucket では trade_count 不足が常態化する。 修正案:
- (i) trade_count_min を dataset 期間 24 ヶ月で再計算: 50 trades / 24 ヶ月 = 2 trades/月 → fold test 20 日 ≈ 1.3 trades/fold/bucket、 さらに不足
- (ii) trade_count 制約を session bucket 別に**絶対値ではなく比例**で評価: 各 bucket trade_count >= total_trade_count × 0.20 (3 等分の最低 20% 確保)
- (iii) Stage B では session 不問、 C-lite で session aware に切替
- (iv) trade_count_min を dataset 期間 24 ヶ月で再校正 (例: 200 trades / 24 ヶ月)

Codex の見解は？ Stage B の session aware 化を諦めるか、 trade_count 制約を再設計するか

### Gap 3: Eviction score の最終式

Round 6 で eviction ハード制約 (per_run_max=10, pattern_max_share=0.25, recency_floor=12) は確定。 その上で **ソフト ordering** に使う `eviction_score` の式が未定義:

候補:
- (α) `eviction_score = quality_score (= margin_inf_normalized)`
  単純、 quality 最低を evict
- (β) `eviction_score = α × quality + β × (1 / age_in_runs) + γ × (1 / pattern_rarity)`
  quality + recency + rarity の加重和
- (γ) `eviction_score = quality × recency_decay × rarity_bonus`
  乗算型 (各因子の効果が独立に効く)
- (δ) `eviction_score = quality - α × age_in_runs - β × pattern_share`
  時間減衰 + 過密 penalty

zenigame は (α) ベースに近い (sieve_score 単独)。 fx で **多軸 archive (CA/DA)** を採用しているので、 (β) or (δ) で多様性を加味する設計が必要かもしれない。

**Claude の主張**: (β) 加重和:
```
eviction_score = 0.6 × quality_norm + 0.2 × recency_factor + 0.2 × rarity_factor
                  - 0.1 × per_run_share - 0.1 × per_pattern_share
```
ただし weight tuning は別の話。

Codex の見解は？ 加重和 (β) vs 乗算型 (γ) vs 減算型 (δ) のどれが堅牢か

### Gap 4: 緊急モード発動条件の定量化

Round 6 で「3 run 連続で mission=0 かつ best_margin_inf 悪化が続く場合」 と緊急モード発動条件があるが、 「悪化」 の定量定義が無い。

候補:
- (i) `consecutive_run_count >= 3 AND mission_pass_count_per_run = 0 for all 3`
  単純 mission 全滅条件
- (ii) `(i) AND best_margin_inf_run_N < best_margin_inf_run_(N-1) for all 3`
  margin_inf monotone 悪化要件
- (iii) `(i) AND moving_avg(best_margin_inf, 3) > moving_avg(best_margin_inf, 6)`
  moving avg ベース
- (iv) `(i) AND archive_quality_75th_percentile_decline > threshold`
  archive 質劣化ベース

**Claude の主張**: (ii) は厳しすぎる (1 run でも margin_inf 改善すると非発動)。 (iii) が堅牢:
- 過去 3 run の best_margin_inf 平均が、 過去 6 run の平均より悪い (= recent 3 が long-term より悪化)
- AND mission_pass=0 が 3 連続

Codex の見解は？ どれが堅牢か

### Gap 5: calibrate-gate の凍結窓

Round 7 で「calibrate-gate (T027) は lookahead ではないが同一 dataset 過適応の懸念」 と INCONCLUSIVE 判定。 fx の確定案では:
- Stage A threshold は canonical 5 worst gate_score (= 1/(1+worst_gap)) の世代内 top 強制通過率で運用
- calibrate-gate は実質**強制通過率の動的調整**に役割変更
- 「凍結窓」 = threshold (or 強制通過率) を一定期間更新しない仕組み

候補:
- (a) 凍結なし: 毎 Run 更新
- (b) 短期凍結: 直近 3 Run は更新しない、 4 Run 目以降のみ history 適用
- (c) 長期凍結: dataset 切替 (=24ヶ月 + 60日 stride で次の dataset に進むタイミング) でのみ更新
- (d) 適応凍結: feasible_ratio が安定したら更新 (= meta-stability detection)

**Claude の主張**: (b) 短期凍結。 直近 3 Run の Stage A 結果は新規 archive entry に反映済み (warmstart 経由)、 さらに threshold 更新を即時反映すると **double counting**。 3 Run 凍結で archive 周期 (10 Run で全更新) と整合。

Codex の見解は？
