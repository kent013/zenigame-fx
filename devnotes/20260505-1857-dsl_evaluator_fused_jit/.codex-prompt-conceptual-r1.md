## 入力: 概念設計

# 概念設計: DSL composite all-bars fused JIT (T053 拡張)

## 背景・課題

profile-optimize cycle 1/3 で profile RUN を計測した結果:
- `evaluator.evaluate_all_bars` cumtime 5.236s / 56 calls / 0.327s/eval (eval 内 25%)
- 内部の `compute_composite_at_bar_jit` (T053 既存 Numba 化済 per-bar fused kernel) は per-bar dispatch で呼ばれ、 N bars 分 dispatch overhead が積算

実 RUN 投影 (直近 RUN 102 分 baseline、 profile→実 RUN 295.9 倍):
- 1530s = 25.5 分 (本番の 12.5%)

zenigame パターン 7 (Numba dispatch overhead 削減、 clause-composite 46s→18s = 60% 削減) と同様、 per-bar dispatch を **all-bars batch dispatch** に変換することで dispatch overhead を 1/N に削減できる。

## 改善アイデア

既存の `compute_composite_at_bar_jit(idx, ...)` (T053) を per-bar 呼び出しから、 **新規 `compute_composite_all_bars_jit(n_bars, ...)`** で全 bar を 1 回の Numba dispatch で計算する。 既存 per-bar 関数は backward compat 用に残す。

シグネチャ案:
```python

    """全 bar を 1 dispatch で計算。 内部は既存 per-bar ロジック × n_bars loop."""
```

## 期待効果

- DSL composite eval の dispatch overhead 削減: 86400 bars × N clauses → 1 dispatch
- 本番 RUN 削減: 25.5 分 → 12-15 分 (50-60% 削減見込み)
- 累積効果: cycle 1/3 単独で本番 100 分 → ~88-90 分 (12.5% 削減)

## 実装方針 (概要)

### 変更コンポーネント
1. `src/dsl/composite.py`: `compute_composite_all_bars_jit` 新規追加
2. `src/dsl/strategy.py` (or evaluator 周辺): per-bar dispatch を all-bars dispatch に
3. `src/alpha_factory/primitives/evaluator.py`: `evaluate_all_bars` で経路変更

### 数値同値性
- 内部ロジック完全同一、 ループ範囲のみ拡張
- bit-identical: 同じ演算順序 (clause loop 内側、 bar loop 外側)
- `np.allclose(per_bar, all_bars, atol=1e-12)` で完全一致確認

### Stage A/B/C 評価不変性
- Stage A/B/C pass count + best fitness_pen が完全同一であること既存テストで確認

## 制約・前提

- FX 絶対制約 (イントラデイ / ロング・ショート / swap・spread): composite 計算は signal 値計算のみで影響なし
- メモリ: out_clause_scores 拡張 86400 × 32 (max_clauses) × 8 bytes ≈ 22 MB/lane → 6 worker = 132 MB OK
- Numba dispatch overhead 削減効果: zenigame 実証だが per-bar loop の Python overhead 規模 (0.169s/eval) で類推適用可能か検証要

## スコープ外
- `_indicators.py` Numba 化 (cycle 2/3)
- broker mock Decimal 改善 (型故 Numba 不可)
- `compute_composite_at_bar_jit` の削除 (backward compat)
