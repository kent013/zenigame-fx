# Post-Run Review: テーマ別戦略レビュー

RUN完了後に独立したセッションとして起動し、指定テーマについてCodexと議論し、最も有望な改善アイデアを選定して **`/zenigame-alpha-design`** で設計ファイル生成 → **`/zenigame-todo-add`** でTODO登録まで完結する。

ユーザーの確認・介入は一切不要。完全自律動作。

---

## 監査・レビュー時の必須 discipline (全 Phase 共通)

`zenigame-codex-review` スキルの「監査・レビュー時の必須チェック C1-C9」を Phase 2 の全 Codex 議論で厳守すること。 特に以下:

- **C1 Design-first**: 新規改善提案の「背景」は docs/alpha-factory/ と devnotes/ の関連 T-number を先に読んでから書く
- **C3 Collider bias**: 相関・予測を根拠にする提案は conditioning set を明示し、 collider の有無を検討する
- **C4 前提検証**: 提案が依拠する config 値 / code 状態が最新と一致しているか先に verify する
- **C6 Fact / Interpretation 分離**: 観察事実と解釈を別セクションで書く
- **C7 Sample size ガード**: n<30 のサンプル claim は因果解釈を禁止する
- **C8 INCONCLUSIVE を選択肢に**: データ不足の場合は提案を捻り出さず INCONCLUSIVE と述べる
- **C9 Falsification-first**: Round 1 の先頭は「この仮説の反証を探せ」から始める

背景: 2026-04-14 の pipeline 徹底監査で約 9 割が false-positive だった反省から追加された discipline。 詳細は `devnotes/20260415-0100-pipeline-audit-postmortem/postmortem.md`。

## 思考原則 — 全議論に適用

**まず仮説を立てろ。** 何を検証したいのか、なぜそう考えるのか、どうなれば成功と判断するのかを明確にしてから手を動かせ。仮説なき改善はただの試行錯誤であり、結果から学ぶことができない。

探索空間は広い。今いる場所が正しいのか、もう少し先に進むべきか、横に移動すべきか、戻って別の道を探るべきかは、これまでの試行と観察の蓄積からしか判断できない。

**データに真摯に向き合え。** 成果だけでなく、多様性の変化、構造の揺らぎ、想定外のパターン — 全てが判断材料になる。数値を見て即座に閾値を弄るな。何が起きているのかを理解し、なぜそうなったのかを考え、どの方向に進むべきかを判断してから手を動かせ。

**先人の知恵を探せ。** 自分たちだけで登る必要はない。乗るべき巨人の肩があるなら乗れ。

**機能の名前に立ち返れ。** 名前はその機能が果たすべき役割を示している。現在の設計がその役割を果たしているか、常に問え。

**仕組みが機能していない段階で値を弄るな。** 閾値チューニングやフィールド追加（KAIZEN）は、設計の方向性が正しいと確認できてから行え。方向性が間違っているなら、値をいくら調整しても意味はない。設計そのものを見直せ（INNOVATION）。成果が出なければ早期に見切り、次の仮説へ進め。

**因果ループを切断するな。** 「XはYに影響しない」という主張に出会ったら、間接経路を含む因果ループ全体を追え。このシステムは観測→判断→介入→GAの結果→観測…のフィードバックループで動いている。ループの一部を「直接影響しないから無関係」と切断する主張は、ほぼ常に間違いである。主張の真偽ではなく、**切断された経路が本当に存在しないか**を検証せよ。

### Bad / Nice 例

**Bad**: Directorのfallbackがactiveより良い結果 → 「抑圧下限を0.03→0.10にしよう」「max-clipを入れよう」
**Nice**: Directorのfallbackがactiveより良い結果 → 「Directorという名前は"方向を示す"という意味だ。今の設計は毎Runの重み計算機でしかない。方向を示すとはどういうことか？」→ Multi-Run実験計画 + メモリ + 非同期深掘り分析という本来の役割を再定義

**Bad**: BollingerRevertのB効果が負 → 重みを0.03に抑圧
**Nice**: BollingerRevertのB効果が負 → だがfallback時にC-PASS最強クラスタの核になっている → 単独B効果で判断する設計自体が組み合わせシナジーを殺している → Directorに渡す情報と判断基準の再設計が必要

**Bad**: 10 Runの結果を集計 → 「C-PASS平均: active=5.14 vs fallback=6.33、Directorはnet-negativeです」
**Nice**: 10 Runの結果を集計 → ゲノム系譜を追跡 → fallbackのC-PASS個体の半数はwarmstart経由でDirector-active期の構造を継承している → 「fallbackの好結果はDirector由来の揺らぎが伝播した結果かもしれない」→ 単純比較では因果関係を見誤る

**Bad**: Codexと11ラウンド議論 → 閾値・スキーマ・ガードレールの詳細設計で合意
**Nice**: 「そもそもDirectorにメモリがないのはおかしくないか？選択→結果→学習→次の選択のループがない」→ 機能の本質的な欠陥を指摘してから設計を議論

## 使命（North Star）— 絶対遵守

> **Alpha Factoryの使命は「`config/alpha_factory/default.yaml` → `live_criteria` を全て満たすイントラデイ戦略個体を1つ見つけ出すこと」である。**
>
> Stage C通過は最低条件。使命達成 = `live_criteria` の全指標を同時に満たすC-PASS個体の出現。
> 達成後は `live_criteria` の各閾値を引き上げて次の水準を設定する（漸進的目標更新）。

**絶対的な制約（イントラデイ）**: スイングトレード（オーバーナイト保有）は行わない。

## 禁止事項（全フェーズで厳守）

| # | 禁止事項 |
|---|---------|
| 1 | ショート（空売り）売買の導入 |
| 2 | A・B・C評価期間を強い根拠なしに延長する |
| 3 | 見た目の数値をよくしようとする改善（数値操作） |
| 4 | GAをハックしてステージを進めようとする |
| 5 | 閾値をいたずらに緩和してステージを飛ばす |
| 6 | やたらに複雑な案を提案する |
| 7 | 取引回数を削減して見かけの成績を上げようとする（entry_threshold過剰引き上げ、max_pos過度縮小、time_stop極端短縮等でtcを減らす方向の施策。使命の「取引回数が多い」に反する） |

## 分析方針（AGENTS.md「戦略的経緯と分析方針」と同一・厳守）

1. **取引回数削減による見かけの改善を追わない**: Q-band分析の全個体平均で「Q1最良」→「tc減らせ」は統計的錯覚。弱いシグナルの分散上振れに過ぎない
2. **全個体の平均値を追わない — Top個体の特性を見よ**: A-PASS/B-PASS全体の平均ではなくTop 5-10個体のシグナル構成・パラメータ・TC・Netが重要
3. **シグナル予測力の根本強化が最優先**: Run 79でTNVルックアヘッド修正後に成績90%消失。現在はプリミティブの予測力が取引コストを上回れない状態

## フェーズ構成

```
Phase 1-0: 早期スキップ判定（Open≥1→即終了 / Open=0→Obsoleted再設計候補収集）
Phase 1: コンテキスト読み込み（前回申し送りを含む）
Phase 2: テーマ別Codex議論 → 上位2-3件選定 + 残りを申し送り保存
Phase 3: /zenigame-alpha-design で設計 → /zenigame-todo-add でTODO登録（2-3件順次実行）
Phase 4: 申し送りファイル更新
```

**1セッションあたりのTODO生成数: 2〜3件**（それ以上は次セッションへ申し送り）

## Phase 1: コンテキスト読み込み

### 1-0. Open TODOセルフチェック（即終了ガード）

**呼び出し側のフィルタリングに依存せず、自分自身で必ずチェックする。**

```bash
if bash scripts/todo_manager.sh has-open-theme "{theme}"; then
  echo "[SKIP] post-run-review {theme}: Open TODOが存在するためセッションを終了します"
  # セッション完了処理（必須）
  uv run python scripts/cleanup_claude_sessions.py --complete
  # ここでセッション終了
fi
```

`has-open-theme` が exit code 0（= Open TODOあり）を返した場合、**Phase 1以降を一切実行せず即終了する**。
セッション完了処理（`cleanup_claude_sessions.py --complete`）は終了前に必ず実行すること。

`has-open-theme` が exit code 1（= Open TODOなし）を返した場合のみ、以下の 1-0b 以降を続行する。

### 1-0b. Obsoleted再設計候補の収集

`scripts/todo_manager.sh` を使って、Obsoletedテーブルから同テーマの再設計候補を取得する（`Read` でファイル全体を読み込む必要なし）:

```bash
redesign=$(bash scripts/todo_manager.sh list-obsoleted --theme "{theme}" --reason-contains "再設計を推奨")
reevaluate=$(bash scripts/todo_manager.sh list-obsoleted --theme "{theme}" --reason-contains "再評価を推奨")
```

該当行を「再設計候補リスト」として収集する。

各候補について以下を抽出する:

| 項目 | 内容 |
|------|------|
| TODO ID | 元のID（例: T016） |
| タイトル | 元のタイトル |
| 問題の要点 | Obsoleted理由の「問題は残存するため再設計を推奨: ...」部分 |

このリストはPhase 2のCodexプロンプトに「再設計候補」セクションとして含め、新規提案の候補とする。

**再設計候補が0件の場合**: Phase 2のCodexプロンプトから「再設計候補」セクションを省略する。

### 1-1. 直近Runレポートの特定・読み込み（最新3件）

**run_id が指定された場合**: そのrun_idに対応するRunレポートを起点に、それ以前の2件も合わせて読み込む。

**run_id が省略された場合**: 最新3件のRunレポートを自動検出（SSoT + find 解決）:
```bash
latest_n=$(uv run python scripts/alpha_factory/get_latest_run_number.py) || exit 1
# 直近3件: latest_n, latest_n-1, latest_n-2（欠番があれば get_latest_run_number.py --max-below で解決）
for n in "$latest_n" $((latest_n-1)) $((latest_n-2)); do
  find reports/run-reports -maxdepth 2 -name "run-${n}.md" -not -path '*/old/*' | head -1
done
```

各ファイルを `Read` で読み込み、以下を把握する:
- 実行結果（Stage A/B/C通過数、Best B-Sharpe等）
- ゲノムアーカイブ分析（シグナル分布、パラメータ分布、コスト構造）
- 考察・次のアクションへの示唆

**直近3Run の傾向分析**（Codexに渡す前に自分でまとめる）:

```markdown
## 直近Run傾向サマリー

| Run | Stage B通過 | Stage C通過 | Best B-Sharpe | 主な施策 |
|-----|-----------|-----------|--------------|---------|
| run-N   | X件 | Y件 | Z.ZZ | ... |
| run-N-1 | X件 | Y件 | Z.ZZ | ... |
| run-N-2 | X件 | Y件 | Z.ZZ | ... |

**改善トレンド**: [上昇/横ばい/悪化] （根拠: ...）
**繰り返し現れる問題**: [複数Runで共通して見られるボトルネック・パターン]
**最近実装した施策の効果**: [Closed TODOのうち直近で実装されたものの実効果]
```

このサマリーはPhase 2のCodexプロンプトに含める。

### 1-1b. プロファイリング判定（theme=`speed` のみ）

**① 前回セッションが起動したプロファイリングrunの進行チェック**:

```bash
# 前回セッションが残したPIDファイルを確認
cat .cache/alpha_factory/post-run-review-speed-profiling.pid 2>/dev/null
```

PIDファイルが存在する場合:
```bash
# そのPIDが生存しているか確認
kill -0 {PID} 2>/dev/null && echo "running" || echo "finished"
```

- `running`（まだ動いている）→ **このセッションをスキップ**:
  ```
  [SKIP] theme=speed: プロファイリングrun（PID:{PID}）が進行中。完了後の次RUNでレビューします。
  ログ: .cache/alpha_factory/profile_run.log
  ```
  Phase 2以降を実行せず終了。

- `finished`（完了済み）→ PIDファイルを削除してPhase 2へ進む（プロファイル結果を次の議論に活用する）:
  ```bash
  rm -f .cache/alpha_factory/post-run-review-speed-profiling.pid
  ```

**② 実行時間増加チェック**（PIDファイルが存在しない場合）:

1-1の直近3Run傾向サマリーから各Runの総実行時間（Runレポートの「実行時間」または開始〜終了のタイムスタンプ）を比較する。

**直近Runの実行時間が過去2Runの平均より15%以上長い**場合:

最新RunレポートのRunコマンド（`実行設定`セクション）から `--dates-a`, `--dates-b`, `--is-dates`, `--oos-dates` を取得し、プロファイリングrunを起動する:

```bash
mkdir -p .cache/alpha_factory
unset CLAUDECODE
nohup uv run python scripts/trading/run_alpha_factory.py \
    --dates-a {最新Runと同じ} --dates-b {最新Runと同じ} \
    --is-dates {最新Runと同じ} --oos-dates {最新Runと同じ} \
    --pop-size 48 --generations 3 --workers 6 \
    --profile --profile-top 100 \
    > .cache/alpha_factory/profile_run.log 2>&1 &
echo $! > .cache/alpha_factory/post-run-review-speed-profiling.pid
```

以下を出力して終了（Phase 2以降はスキップ）:
```
[PROFILE_LAUNCHED] theme=speed: 実行時間 {前2Run平均}分 → {最新Run}分（+{増加率}%）を検出。
プロファイリングrunを起動しました（PID: {PID}）。
ログ: .cache/alpha_factory/profile_run.log
次RUNのpost-run-reviewでボトルネックを分析します。
```

**実行時間が正常範囲内**の場合（増加率15%未満）: Phase 1-1cへ進む。

### 1-1c. フォーカスポリシーの読み込み

`.cache/alpha_factory/focus-theme.json` を `Read` する。ファイルが存在すれば `policy` フィールドの値を `focus_policy` 変数として保持する（`policy` が存在しない or `null` の場合は `focus_policy = null`）。ファイルが存在しない場合は `focus_policy = null`。

フォーカスポリシーが設定されている場合、Phase 2のCodex議論においてポリシーの指示を新TODO生成の制約として反映する。例えば「EVALフィルタの新規追加を禁止」というポリシーなら、評価フィルタを強化するTODOは提案しない。

### 1-2. 重複チェック情報の構築

**注**: Phase 1-0のセルフチェックで同テーマのOpen TODOは0件であることが確認済み。

各Open TODOの概念設計ファイルを `Read` して重複チェック情報を構築する:

```
TODO.md の Open テーブルの「概念設計」列のリンク先ファイルを全件 Read する
例: devnotes/20260222-1135-ga-diversity-correlation-penalty/conceptual-design.md
```

各概念設計から以下を抜粋して「既存カバー済みトピック一覧」を作成する（「テーマ関連」列はTODO.mdのテーマ列から転記する）:

```markdown
## 既存カバー済みトピック（重複禁止リスト）

| ID | タイトル | 背景・課題（概念設計より） | 改善アイデアの要点 | テーマ関連 |
|----|---------|----------------------|----------------|---------|
| T013 | ga-diversity-correlation-penalty | [概念設計から抜粋] | [改善アイデアの要点] | performance |
| T014 | capital-allocation-integrity | [概念設計から抜粋] | [改善アイデアの要点] | live-trading |
...
```

**Closed TODOも確認する**（直近10件）: `scripts/todo_manager.sh` で Closed テーブル末尾10件のみ取得し、実装済みの内容と重複しないために参照する:

```bash
closed_recent=$(bash scripts/todo_manager.sh list-closed-tail 10)
```

この「既存カバー済みトピック一覧」（全Open TODO）はPhase 2のCodexプロンプトに含める。
同テーマのTODOも含まれており、重複チェックはテーマ内外を問わず全件対象となる。

### 1-3. 前回追加TODOの実装確認（申し送りファイルから）

申し送りファイルが存在する場合、「今回登録したTODO」セクションを確認する:

```bash
cat .cache/alpha_factory/post-run-review-{theme}-deferred.md 2>/dev/null
```

**「今回登録したTODO」に記載されたTODO IDがあれば**:
1. `docs/alpha-factory/TODO.md` を `Read` して、そのIDがClosed になっているか確認する
2. **Closedになっている場合**: そのTODOが実装されたRun IDを確認する。`reports/run-reports/**/run-{N}.md`（ブロック配下、`find` で解決）を `Read` し、「適用した施策」にそのTODOが含まれているか確認する
3. **実装後Runが存在する場合のみ**: 実装前後のRunレポートを比較し、テーマ観点での変化（speed: 実行時間、live-trading: コスト精度、performance: Stage C通過率等）を確認する。この効果確認結果をPhase 2のCodexプロンプトに追記する

**申し送りファイルがない、またはTODO IDセクションがない場合**: このステップをスキップ。

**注意**: 実装されていないTODO（まだOpen）は効果確認しない。

## Phase 2: テーマ別Codex議論 → アイデア選定

### 2-1. テーマ別システムプロンプトの選択

テーマに応じて以下のいずれかを使用する:

#### theme=`speed`（高速化）

```
あなたはHigh-Performance Computingとイントラデイ取引システムの専門家です。

- 前回申し送り候補がある場合は、それも候補リストに含めて再評価し、優先度に従い他の提案と競合させること
- 再設計候補がある場合は、問題の有効性と新アプローチの実現可能性を評価し、有望なら新規提案として含めること
- フォーカスポリシーが設定されている場合、ポリシーに矛盾する提案は不可
- 優先度順にランク付けして出力すること（1位が最優先）
```

Codexの回答から提案リスト（5〜6件、優先度順）を取得する。

### 2-3. アイデアの選定と申し送り分け

Codexの提案リストを上から順に確認し、**自分自身で**各候補に以下のチェックを適用する:

| チェック項目 | 確認内容 |
|------------|---------|
| **使命適合性** | イントラデイNet+・取引回数多・高成績に本質的に寄与するか |
| **禁止事項非該当** | 6つの禁止事項のいずれにも違反しないか |
| **重複なし（厳格）** | 1-2で作成した「既存カバー済みトピック一覧」と照合し、同一問題・同一アプローチ・上位互換・下位互換のいずれにも該当しないか |
| **実装済み不重複** | Closed TODOで既に実装された内容と同じではないか |
| **実現可能性** | 現行コードベースで技術的に実装可能か |

**theme=`speed` の場合の追加チェック**（上記に加えて必須適用）:

| チェック項目 | 確認内容 |
|------------|---------|
| **速度インパクト** | 単独実装でRun全体の10%以上の速度向上が見込めるか。見込めない場合は「バンドル候補」として申し送りにし、今回実施には含めない |
| **GA安全性（✅のみ可）** | Phase 2-2bのGA安全性議論で「✅ 安全」と判定されたか。「⚠️ 条件付き」は条件が明確かつ実装ガイドに落とせる場合のみ可。「🚫 要注意」は今回実施に含めず申し送りにする |

**重複判定の基準**:
- 「同じファイルを変更する」だけでは重複ではない
- 「解決しようとしている問題が実質的に同じ」場合が重複
- 「アプローチが異なれば同じ問題でも新規」として扱う

チェック通過した候補を上から順に取り出し、以下に振り分ける:

| カテゴリ | 件数 | 説明 |
|---------|------|------|
| **今回実施** | 0〜3件 | 全チェック通過した上位候補 |
| **申し送り** | 残り全件 | チェック通過したが今回は選外、またはバンドル候補・次回再評価したい候補 |
| **却下** | 0件以上 | 重複・禁止事項違反・実現不可のもの（申し送りに含めない） |

**今回実施は0件でも構わない。** 十分なインパクトと安全性が確認できた案がなければ、無理に立案せず申し送りのみとすること。
