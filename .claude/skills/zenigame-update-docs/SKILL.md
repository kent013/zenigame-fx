# Alpha Factory ドキュメント更新

`docs/alpha-factory/` 配下のドキュメントを、ソースコードの現状と突き合わせて陳腐化・欠落・用語未定義を検出し、更新する。

## 引数

| 引数 | 必須 | 説明 |
|------|------|------|
| `scope` ($1) | No | 更新対象のスコープ（省略時は docs/alpha-factory/ 全体）。特定コンポーネント名やファイル名で絞り込み可能 |

**出力**:
- 更新されたドキュメントファイル群
- 必要に応じて新規ドキュメント
- `glossary.md` への用語追加
- `README.md` 目次の更新

**独立利用**: YES — 単体で実行可能。

---

## 基本原則

### ハルシネーション防止

**ドキュメントに書く内容は必ずソースコードで裏取りすること。** 推測で書かない。

- 閾値・デフォルト値は `config/alpha_factory/default.yaml` またはソースコードから直接引用
- アーキテクチャ記述はソースコードのクラス・関数構造と一致させる
- 「〜と思われる」「〜の可能性がある」は禁止。確認できないなら書かない

### 用語定義の徹底

**初出の専門用語は必ず定義してから使う。** LLMがドキュメントを読む際にハルシネーションを起こす主因は、用語の曖昧さ。

- 各ドキュメントの冒頭に「本ドキュメントの主要用語」テーブルを設ける
- 他ドキュメントで定義済みの用語は `glossary.md` への参照で代替可能
- 略語（IS/OOS, TC, IC, CRN等）は初出で必ず展開する

### パラメータ記載方針（ハイブリッド方式）

`config/alpha_factory/default.yaml` が全パラメータの Single Source of Truth（SSOT）。ドキュメントとの二重管理による陳腐化を防ぐため、以下のルールに従う。

**ドキュメントに値を残すもの（アルゴリズム理解に不可欠）:**
- 計算式・擬似コード中の閾値（例: TC制約 `min=2.0, max=4.0`）
- ソースコードにハードコードされた定数（例: Failure Memory の `Q_SUPPRESS=0.10`）
- ゲート条件の閾値（例: Stage B Sharpe ≥ 0.2）
- アルゴリズムの分岐条件に使われる値（例: Guardrail閾値）

**ドキュメントから削除し `default.yaml` 参照に置換するもの:**
- チューニング可能なデフォルト値テーブル（`| パラメータ | デフォルト | 説明 |` 形式）
- フラグの on/off 状態（機能の存在のみ記述）
- `default.yaml` の `@why` を読まないと誤解するパラメータ

**置換時の記載形式:**
```markdown
## パラメータ

全パラメータのデフォルト値・変更根拠は `config/alpha_factory/default.yaml` の `{セクション}:` セクションを参照。
```

複数カテゴリにまたがる場合はカテゴリ参照テーブルを使用:
```markdown
| カテゴリ | configパス | 主な設定項目 |
|---------|-----------|------------|
| GA基本 | `ga:` | population_size, n_generations, ... |
```

**判断基準（迷ったとき）:**
1. その値を消すと、計算式・アルゴリズムの動作が曖昧になるか → 残す
2. 単なる現在の運用デフォルト値で、アルゴリズム説明は値なしでも成立するか → 消す
3. `@why` を読まないと誤解するか → `default.yaml` 参照に置換

### 最小変更の原則

- 正確な記述は変更しない
- 構造が変わっていない部分の書き直しは不要
- 新規ドキュメント作成は、既存ドキュメントに統合できない場合のみ

## Step 1: 現状把握

### 1-1. ドキュメント目次の確認

```
Read docs/alpha-factory/README.md
```

README.md の目次から、現在どのドキュメントが存在するか把握する。

### 1-2. ソースコード構造の確認

`scope` 引数に応じてソースコードを探索する。

**全体スコープ（デフォルト）の場合:**

```
src/trading/alpha_factory/ 以下の主要ディレクトリ構造を確認:
- ga/          — GA本体（NSGA-II、遺伝演算子、集団管理）
- ga/nsga2/    — NSGA-IIコア
- ga/director/ — Director & Analyst
- evaluation/  — 評価パイプライン（Stage Gate、バックテストブリッジ）
- ensemble/    — アンサンブル
- learning/    — LLM変異、Reflector
- signals/     — シグナルプリミティブ
- runner/      — Runner（E2Eオーケストレーション）
- exit_engine.py — エグジットエンジン
```

**絞り込みスコープの場合:**
指定されたコンポーネントに関連するディレクトリ・ファイルのみ探索。

### 1-3. 設定ファイルの確認

```
Read config/alpha_factory/default.yaml
```

ドキュメント内の閾値・パラメータが設定ファイルと一致しているか照合するための基準値を取得。

## Step 2: 陳腐化チェック

各ドキュメントについて、以下の観点でソースコードとの乖離を検出する。

| チェック観点 | 方法 |
|------------|------|
| **閾値・デフォルト値の変更** | ドキュメント記載値 vs `default.yaml` / ソースコード |
| **クラス・関数の追加・削除・リネーム** | ドキュメント記載のファイル名・クラス名 vs 実ファイル |
| **アーキテクチャ変更** | ドキュメント記載のフロー vs ソースコードの処理順序 |
| **新機能の未反映** | ソースコードにあるがドキュメントにない機能 |
| **削除済み機能の残存** | ドキュメントにあるがソースコードにない機能 |

**手順:**

1. ドキュメントを1つずつ `Read` する
2. ドキュメントに記載されているファイルパス・クラス名・関数名・閾値を抽出
3. 対応するソースコードを `Read` / `Grep` で確認
4. 乖離を検出したら記録する

**scope指定時**: 指定スコープに関連するドキュメントのみチェック。

### 検出結果の記録

チェック結果を以下の形式で整理（内部メモ、ファイル出力不要）:

```
[陳腐化] {ドキュメント名}: {記載内容} → 現在は {実際の内容}
[欠落]   {コンポーネント名}: ドキュメントなし。{概要}
[用語]   {ドキュメント名}: {未定義用語} が定義なしで使用
[削除]   {ドキュメント名}: {記載機能} はソースコードから削除済み
[OK]     {ドキュメント名}: 最新の状態
```

## Step 3: 欠落コンポーネントの検出

### 3-1. ソースコードのディレクトリ走査

`src/trading/alpha_factory/` 以下の全ディレクトリ・主要ファイルを走査し、ドキュメントでカバーされていないコンポーネントを特定する。

**判定基準:**
- 独立したディレクトリ（`__init__.py` を含む）にドキュメントがない → 欠落候補
- 主要な機能を持つ単体ファイル（200行以上）にドキュメントがない → 欠落候補
- 既存ドキュメントのセクションとして記載可能なら新規ドキュメントは不要

### 3-2. 新規ドキュメントの要否判断

欠落候補ごとに:
- 既存ドキュメントに追記で対応可能か？ → 追記
- 独立したドキュメントが必要か？ → 新規作成
- 内部実装詳細でドキュメント化不要か？ → スキップ

---

## Step 4: ドキュメント更新の実施

### 4-1. 既存ドキュメントの更新

Step 2で検出した陳腐化・乖離を修正する。

**更新ルール:**
- `最終更新` 日付を今日に更新する
- 閾値・デフォルト値はソースコードの値に合わせる
- 削除済み機能の記述は削除する（コメントで「削除済み」と残さない）
- 新機能は適切なセクションに追記する
- パラメータテーブル（`| パラメータ | デフォルト | 説明 |` 形式）が残っている場合は、ハイブリッド方式に従い `default.yaml` 参照に置換する（基本原則「パラメータ記載方針」参照）

### 4-2. 新規ドキュメントの作成

Step 3で新規作成が必要と判断したコンポーネントのドキュメントを作成する。

**テンプレート:**

```markdown
# {コンポーネント名}

**最終更新**: {today}
**実装**: `{ソースファイルパス}`

### 本ドキュメントの主要用語

| 用語 | 定義 |
|------|------|
| **{用語1}** | {定義} |
| **{用語2}** | {定義} |

その他の用語は [glossary.md](glossary.md) を参照。

## 概要

{1-3文でこのコンポーネントが何をするか}

## アーキテクチャ

{処理フロー、主要クラス・関数}

## パラメータ

全パラメータのデフォルト値・変更根拠は `config/alpha_factory/default.yaml` の `{セクション}:` セクションを参照。

## 関連ファイル

| ファイル | 役割 |
|---------|------|
```

**作成時の注意:**
- 概要の冒頭でコンポーネントの役割を明確に定義する
- 専門用語は「本ドキュメントの主要用語」テーブルで定義してから使う
- パラメータのデフォルト値はソースコード/設定ファイルから直接引用する

### 4-3. 不要ドキュメントの削除

以下に該当するドキュメントは削除する:
- 対応するソースコードが完全に削除されている
- 歴史的な経緯記録（Run XX分析結果等）で現在の設計に無関係
- 他のドキュメントに統合済み

**削除前にユーザーに確認すること。**

## Step 5: 用語定義の整備

### 5-1. 未定義用語の検出

各ドキュメントを走査し、以下に該当する用語を検出:

- 「本ドキュメントの主要用語」テーブルがないドキュメント
- テーブルはあるが、本文中に未定義の専門用語が残っている
- 略語（2-5文字の大文字）が展開されていない

### 5-2. 用語テーブルの追加・更新

**既存テーブルがないドキュメント**: 冒頭（概要セクションの直前）に追加

**既存テーブルがあるドキュメント**: 不足している用語を追加

**テーブルフォーマット（統一）:**

```markdown
### 本ドキュメントの主要用語

| 用語 | 定義 |
|------|------|
| **{用語}** | {定義} |

その他の用語は [glossary.md](glossary.md) を参照。
```

### 5-3. glossary.md の更新

新しい用語が登場した場合、`docs/alpha-factory/glossary.md` に追加する。

**追加ルール:**
- 既存のカテゴリ（システム構造、ゲノム構造、シグナル・プリミティブ、評価・Stage Gate、メトリクス、GA・進化計算、バックテスト・取引、統計・ML）に分類
- 既存カテゴリに収まらない場合は新カテゴリを追加
- 用語はカテゴリ内でアルファベット順・五十音順
- 定義はソースコードに基づく。推測で書かない

---

## Step 6: README.md 目次の更新

### 6-1. 目次の同期

ドキュメントの追加・削除・統合を `docs/alpha-factory/README.md` に反映する。

**目次構造（現行カテゴリ）:**
- システム全体
- ゲノム構造・シグナル
- 適応制御
- GA評価・運用
- データ・分析
- リファレンス
- タスク管理

新規ドキュメントは適切なカテゴリに配置。カテゴリに収まらない場合は新カテゴリを追加。

### 6-2. 最終更新日の更新

README.md の `最終更新` 日付を今日に更新する。
